# EvernightCommit 操作行为规格

本文按操作逐条记录**实际会执行什么、什么情况下拒绝、拒绝时说什么**，是给开发者与
审阅者的稳定参考；面向普通用户的说明在仓库根目录 `README.md`。文中的「实测」结论
均来自同一台 Windows 11 x64 开发机（UTF-8 代码页），PATH 上的 Git 在不同开发时期
分别为 2.56.0.windows.1 与 2.53.0.windows.3；更旧的 Git 版本未在实机上验证。

各操作的**用例分组与授权边界**（哪几组可直接跑、哪一组含真实 `git commit`/`git push`
只由项目维护者运行）见 `testing.md`；本文不再逐节罗列测试用例清单。

## 1. Git 程序定位与验证

运行本程序需要一个 Windows 版 Git（推荐 [Git for Windows](https://git-scm.com/download/win)）；
程序本身不携带也不安装 Git。`Git 程序` 的确定流程：

1. **自动发现**：启动时按当前进程的 Windows PATH 逐目录查找 `git.exe`（效果对应 `where git`
   的搜索意图），不扫描磁盘、不读注册表；多个候选按 PATH 顺序去重（大小写不敏感）后进入下拉列表。
   发现结果自动选中第一个候选并立即验证。
2. **手动选择**：直接在组合框键入路径（裸名 `git` 也会按 PATH 解析），或用 `浏览…` 选择 `git.exe`。
   有效路径统一规范化为绝对路径；后续所有 Git 调用都使用该确定的程序路径，不再依赖 shell 再次搜索。
3. **后台验证**：在工作线程直接以参数数组执行 `<git.exe> --version`（`CreateProcessW` +
   `CREATE_NO_WINDOW`，不弹命令窗口、不经 cmd 拼接），限时 3 秒，捕获退出码、输出与启动错误；
   确认路径是文件且程序确实报告 Git 版本后保存版本号供后续步骤使用。
4. **失败与恢复**：找不到 Git、文件不存在、无法启动、超时、输出不是 Git 版本，或程序正常退出但
   **它的输出没能完整读回**（读管道失败、超过保留上限、没读到结尾）时，“任务状态”显示具体原因；
   确认不了版本就不会开始使用它。改正路径后自动重新验证并恢复，无需重启程序。连续输入有
   0.5 秒防抖；旧验证结果按序号丢弃，不会覆盖新选择。“输出没读全”与“这不是 git.exe”是两种
   说法：版本行可能在没读到的那一段里，程序不会据此断定用户选错了程序。

## 2. 仓库路径选择与识别

1. **初值与输入**：初值是程序启动时的工作目录，取绝对路径后填入输入框；不修改进程的工作目录。
   支持直接键入（0.5 秒防抖）与 `浏览…` 选择目录；带空格、中文的路径按 UTF-16 原样处理。
2. **只问 Git，不看 `.git`**：识别一律以 Git 的回答为准，不用“目录里有没有 `.git`”推断，
   因为链接工作树与子模块的 `.git` 是文件，裸仓库根本没有 `.git` 子目录。查询全部是只读的
   `rev-parse` / `symbolic-ref` / `for-each-ref`，以参数数组在隐藏窗口子进程中执行，
   每条查询都显式 `-C <仓库目录>` 并同时把子进程工作目录绑定为该目录，因此切换仓库不会影响
   正在运行的其他查询，也不依赖 shell 二次搜索。
3. **形态区分**：普通工作区、链接工作树（`--git-common-dir` 与 `--absolute-git-dir` 不同）、
   子模块仓库（`--show-superproject-working-tree` 有值）、裸仓库、`.git` 目录内部、非仓库目录。
   分支维度另外区分“尚无提交”（HEAD 不可解析但有分支名）与“游离 HEAD”（给出短提交 ID）。
   裸仓库与 `.git` 内部**没有可用工作区**：识别本身算成功，但不会进入面向工作区的提交流程，
   “任务状态”会说明原因；链接工作树与子模块则照常可用，只是额外说明来历。“来历”与
   “分支状态”（游离/尚无提交）可能同时成立，标签会把两者一起讲清楚。上游为空时显示
   “未设置上游”，不会让仓库整体加载失败。
4. **错误恢复与连续切换**：识别在工作线程执行，GUI 线程不冻结；每次提交带递增序号，较慢完成的
   旧结果作废。路径不存在、不是目录、被 Git 的 `safe.directory` 安全检查拦截、权限不足、超时或
   输出不合预期，都会在“任务状态”里给出具体原因，改正后自动恢复。
5. **边界**：绝不在用户选中的目录执行 `git init`，不修改仓库或全局配置，不自动修复
   `safe.directory` 与目录所有权，不执行 `fetch`，也不把真实仓库路径写进测试。识别用到的
   Git 查询都是本地只读操作，不访问远端。

依赖 Git 的按钮要同时满足三个条件才会启用：功能已接通（每个按钮各有单独的接通开关，见
`app_state`）、Git 程序验证可用、仓库已识别为可用工作区。`status` 另外要求“同一时刻只有
一个操作在跑”。

## 3. 外部命令窗口执行器

用户主动点击的 Git 操作不在本进程里静默执行，而是**新开一个命令窗口**。

### 3.1 启动链路与窗口形态

执行器用 `CreateProcessW` 启动**本程序自己的命令窗口辅助入口**（显式 `lpApplicationName`、
可写的命令行缓冲、工作目录设为所选仓库、Unicode 环境块）。辅助进程先 `AllocConsole` 开一个
新控制台窗口，用 `SetConsoleTitleW` 写上标题，把控制台输入/输出码页显式设为 UTF-8，原样回显
即将执行的 Git 命令行，再用 `CreateProcessW` 直接启动 `git.exe`（输入输出都接到同一个控制台，
所以凭据提示、GPG 口令提示都在这个窗口里原生交互）。Git 退出后辅助进程把窗口交给
`cmd.exe /d /v:off /e:on /k`：`/d` 跳过注册表 AutoRun，`/v:off` 与 `/e:on` 显式固定保留窗口
的交互形态（`!` 保持字面量、命令扩展行为不受注册表开关摆布；本次操作的参数本来就不经过这个
cmd，这些旗标只约束用户之后在窗口里手输的内容），`/k` 让窗口留在交互提示符，用户可继续翻看输出。

### 3.2 编码链路：一条链路上没有码页转换

系统 ANSI 代码页、控制台输入/输出代码页、脚本文件编码与 Git 自己的 UTF-8 输出是四件不同的事，
本执行器只碰最后一件：

- 路径、参数、窗口标题全部以 UTF-16 形态经 Unicode API 传递（`CreateProcessW`、
  `SetConsoleTitleW`、`CreateFileW`），不经过批处理字节流；
- 一次操作的语义写进操作目录里的 `spec.txt`（**严格 UTF-8**：编码由我们自己校验，孤立代理项等
  非法码元直接失败，绝不写成问号、`U+FFFD` 或“最佳匹配”顶替原值）；
- 命令窗口的控制台码页被显式设为 UTF-8，与 Git 输出的 UTF-8 对齐。

因此中文用户名下的临时目录、中文/空格/`&` 的仓库路径、含 `%`、`!`、中文的文件名、中文窗口
标题，以及超出传统代码页的字符（西里尔、emoji）都能正常工作，不需要用户改用户名、搬仓库，
也不需要开启或关闭“Beta: Unicode UTF-8”来绕过。旧实现要把路径与参数按系统 ANSI 代码页编码后
写进批处理，因此这三类情形会被整次操作拒绝；那段编码（`ansi_text`）已删除，系统代码页不再参与判定。

### 3.3 成败判定与操作目录

每个操作有自己的独占临时目录（`%TEMP%\GcOp<进程ID>x<随机段>`，父目录可以是非 ASCII 路径；
随机段每次新生成，只有亲手把目录新建成功的那一次才算认领它，撞名就换一个猜不到的名字重来，
绝不采纳已经存在的目录，也不复用其中已有的任何文件）。里面有五个文件：`spec.txt`（操作说明书，
由本程序写入）、`start.txt`（辅助进程确实已开始执行，内容带着本次操作的随机口令）、
`result.tmp` 与 `result.txt`（Git 的退出码，同样带着本次口令；先写 `result.tmp` 再改名为
`result.txt`，所以观察端要么还没有结果，要么读到的是完整一条）、`lease.txt`（执行器一直握到
操作结束的租约）。结果行的最后一列是辅助进程创建 Git 进程时 `CreateProcessW` 的直接事实
（`started` / `notstarted`）：「Git 未能启动」据此判定，不再从任何退出码数值反推——Git 自己
返回 9009 也只算它的一次普通回答。

观察线程轮询这些文件与进程状态，把“进程启动 / 进程退出 / 标记文件 / 结果文件”四路事实合成
唯一终态：`启动失败`、`已启动`、`执行中`、`执行完成`（含 Git 退出码）、`Git 未能启动`
（无退出码可言）、`结果未知（窗口被提前关闭）`、`结果未知（辅助进程未能开始执行）`、
`结果未知（超过观察期限）`。判定器给出终态的那一刻就结案并释放操作槽位，**不等保留的命令窗口
关闭**：Git 跑完后窗口按设计一直开着，界面照样能立刻发起下一项操作。

**绝不匹配 Git 输出里的某句话来判断成功**，也不把命令窗口自身的退出码当作 Git 的退出码；
标记与结果里写的口令必须是**本次操作**的那一份，格式不对、只写了一半、或属于另一次操作的记录
一律当“没有这条痕迹”，所以陈旧残骸不可能被认作这一次的成功。

用完由本程序删除：正常结束时观察线程落账之后就收尾，启动前失败的那几次也不会把目录留下。
应用退出时还有操作在跑，本程序**不会**去删它（那个命令窗口还要往里写结果），界面把它记成
“结果未知”，绝不停在“执行中”。下一次启动会回收这类残留，但条件是两条都满足：最后写入时间
超过 60 分钟，**并且**目录里本程序自己写出的那几个文件没有一个还被别的进程持有（执行器的租约、
辅助进程握着的开始标记都是“还在用”的可查证据）。因此超过一小时的长操作、正在等你输入口令的
操作、以及另一个实例正在用的目录都不会被误删；查不出结论的（权限不足、目录被做成链接、里面有
来历不明的文件）保留不动，只留下诊断记录，回收也从不递归删除目录内容。

### 3.4 GUI 不等待、不冻结

`Start` 在界面线程只做“规划 + 写说明书 + 创建进程”，每个进行中的操作由独立观察线程等待，
结束后向主窗口 `PostMessage`（消息只携带操作 ID，结果由执行器保管），界面线程不打开管道、
不 `WaitForSingleObject`。关闭窗口时若还有操作在跑会先征求确认；无论用户怎么选，本程序都
**不会终止正在运行的 Git**，已结束的窗口还开着也不会阻止应用退出。

### 3.5 注入防护与辅助入口的自有约束

程序路径与每个参数都用引号包起来，并且要求路径与参数**不含双引号与控制字符**、引号区域之外
不出现 `& | < > ^`、参数数量与命令行长度不超过上限——这类输入在启动进程之前就被拒绝，而不是
“加个双引号当安全脚本”。现在没有任何 shell 参与 Git 的调用，所以 `%`、`!`、括号、`&` 都只是
参数里的普通字符，实测原样送达 Git；上面那道引号区域校验仍然保留，为的是让“同一份输入在执行
边界上只有一种合法形态”成为可测试的不变量，也防止日后又有人把这些值拼进某条 shell 命令。
多行提交信息等正文走临时文件传给 `git commit -F`，不进命令行。

**辅助入口不是通用命令执行器**：命令行上只有“操作目录 + 本次操作的随机口令”两项数据，
要执行什么只来自该独占目录里的说明书；辅助进程会核对目录名的形态、说明书所在目录与说明书
声明的目录名是否一致、口令是否与启动时传来的一致，然后用与界面同一套校验重新复核说明书内容，
任一项不合格就不执行（也不写任何结果文件）。如实说明边界：这套绑定防的是“用别的目录来驱动
这个入口”，能以当前用户身份在临时目录里造文件、造进程的第三方本来就拥有同样的执行能力，
它不是同身份攻击者之间的隔离手段。

### 3.6 集中环境策略

后台预检与命令窗口执行共用同一份策略（`git/git_environment.h`）：继承环境里能改写命令语义的
「重定向」变量一律不带走——仓库定位（`GIT_DIR`、`GIT_WORK_TREE`、`GIT_NAMESPACE`）、索引与
对象库（`GIT_INDEX_FILE`、`GIT_OBJECT_DIRECTORY`、`GIT_ALTERNATE_OBJECT_DIRECTORIES`）、
配置注入与重定向（`GIT_CONFIG_PARAMETERS`、`GIT_CONFIG_COUNT` 与逐条
`GIT_CONFIG_KEY_<n>`/`GIT_CONFIG_VALUE_<n>`、`GIT_CONFIG_GLOBAL`、`GIT_CONFIG_SYSTEM`、
废弃别名 `GIT_CONFIG`）、身份与时间（`GIT_AUTHOR_NAME/EMAIL/DATE`、`GIT_COMMITTER_NAME/EMAIL/DATE`）
都被移除，实际仓库、索引与身份因此始终由「界面选中的目录」和表单决定，从终端或其他 Git 工具里
启动本程序不会把操作搬到别的仓库上。移除确实在继承环境里存在的重定向变量时，操作结论会按变量名
告知用户（只列名字，绝不显示值）。其余变量照常保留：用户的真实 Git 配置、凭据助手、`PATH`、
`HOME`/`USERPROFILE`、SSH 相关（`GIT_SSH`、`GIT_SSH_COMMAND`、`SSH_AUTH_SOCK`）一概不动，
正常认证与工具链不受影响。

命令窗口在此之上再落交互契约：设 `GIT_TERMINAL_PROMPT=1` 并删除 `GIT_ASKPASS` / `SSH_ASKPASS`，
以免提问被搬成 GUI 弹窗而偏离“在命令窗口里原生交互”；并设 `GIT_PAGER=cat`——新建控制台是
交互式 TTY，Git 默认把 `status`/`log` 之类输出交给 `less`，辅助进程会停在等用户按键的那一屏上，
退出码迟迟拿不到、临时目录也被窗口占用，而命令窗口本来就保留全部输出供滚动查看，分页没有价值。

「创建提交」表单的作者身份与两个时间作为操作覆盖排在策略之后，只进那一次子进程的环境块，
不回写任何配置，也不改动本进程环境。

界面侧的“刷新”“路径选择”“仓库识别”等只读动作仍走隐藏窗口子进程（`subprocess`，
`CREATE_NO_WINDOW`、分别捕获 stdout/stderr），**不弹命令窗口**；两种模式刻意分开：命令窗口
模式不截获任何管道，以免破坏 Git 的终端输入；后台捕获模式不弹窗、不交互，环境按同一份集中策略
装配并额外设 `GIT_TERMINAL_PROMPT=0`——只读探测绝不停留在看不见的问题上（凭据助手照常保留，
那是看得见的交互）。环境块装配不起来时（进程环境读不出或为空、覆盖名不合法）查询明确失败并
给出原因，绝不退回“裸继承环境”去猜。

## 4. 工作区状态解析（未暂存 / 已暂存两个列表）

仓库识别成功且该形态有可用工作区时，主窗口在后台再发只读查询填充列表（`git status` 填两块
文件列表，HEAD 可解析时紧接着一条 `git log` 填“最近提交”；都是隐藏窗口子进程，不弹命令窗口）。

1. **取的是 Git 的机器可读输出，不是给人看的文本**。参数固定为
   `--porcelain=v2 -z --untracked-files=all --ignore-submodules=none`（外加 `-C <工作区根>`、
   `--no-optional-locks`、`--no-replace-objects`），全部以参数数组提交：
   - `--porcelain=v2`：每条记录用两栏 `XY` 分别描述“索引相对 HEAD”和“工作区相对索引”，因此
     **同一文件可以同时出现在左右两块列表**（暂存一次修改后又继续编辑，两侧状态互不覆盖）；
   - `-z`：记录以 NUL 分隔，且**路径原样输出、不做任何引号转义**——含空格、中文、`&`、`^`、`%`
     的文件名可原样还原，也不依赖 `core.quotepath` 与本机 ANSI 代码页。重命名/复制记录的目标路径
     与来源路径之间同样是 NUL，解析按记录类型成对消费，绝不按行或按空格拆文件名；同时要求这份
     输出**每条记录都以 NUL 收尾**：非空输出末尾少了那个 NUL，说明最后一条是残缺的（半个文件名），
     整份按“读取不完整”拒绝；完全空的输出才是合法的“干净工作区”答复；
   - `--untracked-files=all`：未跟踪目录展开成一条条可单独选择的文件，而不是只列一个目录；
   - `--ignore-submodules=none`：覆盖用户自己的 `submodule.*.ignore` / `diff.ignoreSubmodules`
     配置，子模块状态一律如实回报。

   不请求 `--ignored`：被 Git 忽略的文件不进列表，程序也不会用任何强制加入手段。
2. **索引状态与工作区状态分开建模**。解析结果是两个独立列表；每条记录同时保留 Git 原始 `XY`
   状态码、仓库相对路径、重命名的来源路径与相似度字段。界面上的“状态/相对路径”文字**只用于显示**，
   构造暂存或提交命令时一律取这些原始字段，不从单元格文本反解。
3. **未合并项是冲突，不是删除**。`u` 记录（如 `UU`、`UD`）作为**一条**带“冲突”标识的条目落在
   未暂存那一侧：它需要在工作区里被解决，而解决它的动作正是暂存；程序不会把它拆成“一次删除 +
   一次新增”冒充两侧都有的普通变化，也不会在读取摘要里把它当成干净状态。
4. **子模块区分“提交指针”与“内部状态”**。`<sub>` 栏位为 `S<c><m><u>`，分别是提交指针已移动、
   内部已跟踪文件有改动、内部有未跟踪文件。父仓库对子模块只有**一条 gitlink 记录**：在父仓库
   暂存子模块只会记录它指向哪个提交，子模块内部的文件属于那个仓库自己的改动，必须进入子模块
   工作区另行暂存与提交。因此父仓库列表里不会出现 `子模块内/某文件` 这种条目，程序也不会递归
   提交或把内部修改伪装成可在父仓库一次暂存的内容；读到子模块变化时，底部状态条会直接说明这条
   范围限制（鼠标停在列表上也有完整说明）。
5. **读取在后台执行，切换仓库不会串数据**。读取在工作线程跑，GUI 线程不冻结；每次提交带递增
   序号，较慢完成的旧结果按序号作废。开始新一轮仓库识别时**立刻清空**上一份列表，识别失败、
   目录不是仓库、裸仓库与 `.git` 内部这些没有可用工作区的形态同样清空，界面上不会出现“看着像
   当前仓库、其实是上个仓库”的条目。
6. **成功、干净、失败各有说法**。读取成功但两侧都没有条目时显示“没有未暂存的更改 / 没有已暂存的
   更改”，读取过程中显示“正在读取”，失败时显示归类原因（超时、启动失败、被 `safe.directory`
   拦截、权限不足、`index.lock` 已存在、输出没读全等）。**输出不符合约定或没读全时整份丢弃并
   报告失败**，绝不交出解析出来的一半——一份缺文件的列表会让人在看不见的改动上做提交决定。
   所有读取都是只读的，失败信息里也据此说明“没有对仓库做任何改动”。

## 5. 刷新与任务状态协调

界面上有两类完全不同、但都叫“看仓库怎么样了”的动作：

- **内部刷新（只读，不弹窗口）**：“刷新”按钮与操作结束后的自动重读都走这条路径，在本程序的
  后台线程里执行只读 Git 查询（仓库识别 + `git status`），只更新界面，**不会**打开 `cmd.exe` 窗口。
- **命令窗口操作（用户主动执行）**：`status`、加入/移出暂存区、`创建提交`、`撤回最近提交`、
  `fetch`、`pull`（获取与整合两条）、`推送`，都在命令窗口里跑真实命令并保留输出。

一次刷新的覆盖范围与并发规则：

1. **一次刷新同时更新顶部摘要与两个列表**。分支、上游、仓库形态都可能被外部终端改掉（切分支、
   在别处提交、`git pull`），只重读 `git status` 会得到“半新半旧”的界面，因此刷新先重新识别仓库、
   识别成功后接着读取工作区，两步都在后台。“最近提交”（`git log`）挂在同一次工作区读取里：
   `git status` 成功后紧接着追问一条只读 log（仅当 HEAD 可解析），不另建触发机制。
2. **短时间内的多次刷新合并成一轮**。连点“刷新”、几个操作接连结束、切换仓库这几路触发共用一个
   防抖定时器（0.3 秒）；若请求到达时已经有一次读取在途，就只登记“读完再补一次”，合并槽是一个
   布尔标记而不是队列，**不会无限排队**，也不会让列表反复闪。
3. **过期结果一律丢弃**。每次请求都捕获仓库身份（Git 程序路径 + 工作区根）与身份版本号：切换仓库、
   改用另一个 `git.exe`、或识别失败/变成没有工作区的形态时版本号递进，迟到的旧结果被判定为过期后
   **不落地**，当前列表保持原样，等属于新身份的那一次读取来填。刷新（身份未变）时摘要与列表留在
   原位，等新结果就地替换，不整屏清空。
4. **操作结束后无论成败都重读一次**。失败的操作同样可能已经改动仓库（提交到一半、`push` 被拒、
   合并留下冲突）。成功与否只认 Git 的退出码：**命令窗口开起来不算成功**，只有拿到退出码且为 0
   才报“成功”；状态栏会同时给出“刚才的操作怎么样”与“仓库现在怎么样”，详细输出仍留在命令窗口里。
5. **保留你的选择与视图**。列表按“条目身份”记忆多选（更改列表按仓库相对路径、提交历史按完整
   对象 ID），就地增删改行而不是整列清空——报表视图不响应 `LVM_SCROLL`，清空重建后没有任何消息
   能把视口放回去，所以“不清空”是保住滚动位置的唯一办法。某文件被暂存后从左栏移到右栏，选择跟着
   它走；已经被提交或被外部删除的条目自然不再被选中，也不会把选中状态挪到别的文件上。**刷新不会
   重置提交表单**：标题、描述、作者、合作者与两个时间都保持你输入的内容，时间也不会被改回“现在”。
6. **同一工作区同时只允许一个由本程序发起的操作**。操作在跑时 `status`、暂存/取消暂存、创建提交、
   撤回提交、`fetch`、`pull`、`推送` 都禁用（互相抢仓库锁没有意义），而“刷新”这类只读动作按条件
   继续可用。**已结束但保留下来的命令窗口不会锁住界面**：结果一到账就释放槽位；万一完成通知丢失
   （执行器已不再认识该操作），轮询会把它判为“结果未知”、释放槽位并安排一次刷新，而不是永远显示
   “执行中”。
7. **失败要能被再次刷新恢复**。读取失败、`git status` 因 `index.lock` 已存在而报错、命令窗口被
   提前关闭（拿不到退出码）、通知丢失，都会给出明确状态并允许再点刷新。本程序**绝不删除 Git 的
   锁文件**，也不代为 `reset`/`checkout`：锁是 Git 自己的并发保护，只能由持有它的那个进程结束后
   自然消失。
8. **外部改动靠手动刷新恢复**。用户完全可以在别的终端里改仓库（本项目不做文件监听，也不引入
   复杂的监视机制）：只要点一下“刷新”，界面就会回到 Git 回答的真实状态。
9. **后台读取的输出：先完整读回，才拿来判断**。所有只读查询（仓库识别、`git status`、`git log`、
   作者默认身份、`fetch`/`pull`/`推送` 前的预检与核对）都在隐藏窗口里读 Git 的标准输出与标准错误，
   要求是“要么完整、要么不算答案”：
   - 标准输出与标准错误**分别**读取，各自记录收尾形态：正常读到结尾、超过保留上限被截断、读取
     本身失败、子进程结束后管道迟迟不关（它的子孙还占着写端）而主动放弃，是四种不同的结果，
     界面上说的就是哪一种，不写成“没有输出”；
   - 每一路保留上限为 16 MiB（够装二十万条上下的变化记录）。超过之后只留开头一段并明确判为
     “读取不完整”，**不会把少了若干条当成一份完整快照**；同时仍把管道排空，不把子进程卡在写不上；
   - 子进程退出后先把管道里已缓冲的输出排空再收工，等到结尾才算完整；放弃读取也有期限，不会让
     界面永远停在“正在读取”；
   - 字节必须是**有效的 UTF-8** 才会被解码使用。遇到不合法的字节（例如某个仓库里的文件名本来
     就不是 UTF-8 编码），这一次读取按“输出不完整”失败处理，**不会**用替代字符拼出一个看起来
     能用、其实与磁盘上不同的路径去暂存或提交；
   - NUL 分隔的机器输出还必须满足“每条记录都以 NUL 收尾”。末尾缺那个 NUL 就是半条记录（半个
     文件名、半条配置值、少字段的提交记录），整份拒绝；完全空的输出仍然是合法的“干净答复”
     （干净工作区、没有匹配的条目），不会被误判成失败；
   - 因此某一次读取不完整时，界面显示“Git 输出读取不完整（原因…）”并提示重新读取，而不是一个
     空列表或“0 项”。**推送与 `pull` 的确认框在配置或冲突清单读不全时直接拒绝发起**：半条 URL
     也像一条 URL，本程序不在看不清实际发布地点的前提下推送。

## 6. 加入暂存区（`git add`）

把“未暂存的更改”里**选中的**条目交给命令窗口里真实的 `git add`，执行结束后自动重读两侧列表。

1. **没有选中就是“什么都不做”**。点击时如果一行都没选，只在“任务状态”里给一句说明，绝不把
   “没有选择”理解成“暂存全部”：程序构造的参数里不会出现 `.`、`-A`、`-u`、`--all`，也不会用
   `git add -p`/`-i` 这类要人按键的形态。
2. **只处理选中的变化**。修改、删除（记下删除本身就是暂存的一部分，无需 `-A`）、类型变化、
   未跟踪新文件、子模块 gitlink 与未合并条目都按各自条目处理；没选中的条目原地保留，同一路径
   已暂存的那一份改动也不会被顺带动到（可重复点：索引内容更新为工作区当前内容）。
3. **路径按字面语义交给 Git**。实测本机 Git 2.56：`--pathspec-file-nul` 的 NUL 分隔只关闭
   “引号/C 转义”这一层，**pathspec 的 glob 魔法仍然生效**——清单里直接写 `brk[x].txt` 会连带
   命中同目录的 `brkx.txt`。因此每条路径都带 `:(literal)` 前缀，实测加前缀后只命中自己；`#`
   开头不是注释、`!` 开头不是取反、`%` 原样保留、前导 `-` 不会被当成选项，中文与含空格、`&` 的
   文件名同样按原样送达。
4. **多选很多文件不受命令行长度限制**。所选路径写进 `%TEMP%` 下一个 NUL 分隔的 UTF-8 清单文件
   （文件名含进程号与进程内序号，用 `CREATE_NEW` 独占创建，绝不覆盖别人的同名文件），命令里只
   出现 `--pathspec-from-file=<路径>` 与 `--pathspec-file-nul`；实测 1200 条路径一次完成。清单在
   Git 退出（拿到退出码）之后删除；若命令窗口被提前关闭而 Git 可能还在读它，宁可留一个临时文件
   也不删。旧版本 Git（`git --version` 解析不出 2.25 及以上）退回“字面 pathspec 直接进参数数组”
   的形态，范围与清单形态完全一致；条目数或长度超出参数形态的承受能力时**直接拒绝执行**并说明
   原因，不静默退化成 `git add .`，也不自作主张分批。
5. **重命名按一次变化处理**。索引侧的重命名条目会同时给出旧路径与新路径，两条一起交给同一条命令；
   工作区里改名的真实形态是“.D 旧路径”+“?? 新路径”两条未暂存条目，要暂存这次改名请把两条都
   选中（实测选中两条后 Git 记成 `R100`，只选新文件则旧路径的删除仍留在未暂存侧）。
6. **未合并（冲突）条目必须先由用户确认**。`git add` 会把该文件**工作区里的当前内容**写进索引并
   记为已解决——实测连 `<<<<<<<` 标记也会一起进索引。程序不判断冲突是否真的解决完，只在执行前把
   这句话原样讲出来，由用户选择继续或取消；取消不会打开命令窗口，也不会改动仓库分毫。
7. **子模块只记录提交指针**。父仓库对子模块只有一条 gitlink：指针已移动时这一次 `git add` 记录
   新的提交 ID；指针未移动、只有内部改动时这一次实际上是空操作（实测退出码仍为 0，内部脏文件一个
   都不进父索引）。程序把范围限制说在前面，绝不递归进入子模块暂存或提交，也不改子模块任何东西。
8. **失败保留 Git 的原始回答**。选中的某条路径在点击之后才消失（外部删档/移动）时，Git 报
   `fatal: pathspec ... did not match any files`（退出码 128），实测此时**整条命令没有任何内容
   进索引**，是全有或全无，不会出现“一半暂存成功”；程序只转述这条错误与退出码，绝不改成更大范围的
   `add` 重试，也绝不删除 `index.lock` 之类的锁文件。
9. **并发与后续动作**。点击瞬间按行号核对条目身份并拷成选择快照，之后的刷新不会改变本次范围；
   工作区根与协调器身份不一致时拒绝执行（避免把上一个仓库的路径用到新仓库上）；同一时刻只允许
   一个命令窗口操作，按钮在操作进行期间禁用；命令窗口里的 Git 结束后照常自动重读一次，窗口本身
   保留供查看输出。

## 7. 移出暂存区（`git restore --staged` / `git reset -q --`）

把“已暂存的更改”里**选中的**条目从索引撤回，工作区一个字节都不动，执行结束后自动重读两侧列表。
范围控制、字面 pathspec、清单文件与旧版本退回这些机制与上一节完全同一套代码，只是命令方向相反。

1. **只写索引**。有最近一次提交时命令是 `git restore --staged -- <所选路径>`：实测已暂存的修改退回
   HEAD 的内容而磁盘上仍是最新字节（条目回到“未暂存的更改”）、已暂存的删除把路径放回索引而磁盘上
   依然没有那个文件（不会“顺手把文件捡回来”）、已暂存的新增从索引移除而文件原样留在磁盘上变成未跟踪。
   绝不使用 `git restore`（不带 `--staged`，那会改写工作区）、`git reset --hard`、`git checkout --`
   或 `git clean` 这类会丢弃改动的命令，也没有任何“命令失败就换破坏性后备”的路径。
2. **没有 HEAD、或者 Git 太旧没有 `restore` 时，换一条同样只写索引的命令**。仓库还没有任何提交时
   `git restore --staged` 会当场失败（实测 `fatal: could not resolve 'HEAD'`，退出码 128，索引分毫
   未动）；而 `git restore` 这个子命令本身是 2.23 才有的，更旧的 Git 只会回
   `git: 'restore' is not a git command`。两种场合都改用 `git reset -q -- <所选路径>`：实测效果与
   前者一致——所选路径的索引条目退回最近一次提交的版本（没有提交时即从索引移除）、磁盘文件原样保留
   并回到未跟踪，未选中的索引内容不受影响。**带路径的 `git reset` 只动索引**；只有不带路径的那种
   形态才会改动 HEAD，本程序绝不构造（没有选中时直接不执行，并说明这一点）。HEAD 是否可解析取仓库
   识别时 Git 自己的回答（`headResolved`），`restore` 是否存在取 `git --version` 的回报值（解析不
   出来就当作不支持，宁可用保守的那条命令，不猜）。
3. **重命名必须成对撤回**。索引侧的重命名条目会同时交出旧路径与新路径两条 pathspec：实测只撤新
   路径会留下“旧路径仍是暂存的删除”这种半成品状态，界面上就变成一半已撤、一半还暂存着。
4. **内容只存在于索引里的条目先要用户点头**。X 为新增/重命名/复制（HEAD 里没有这个路径）而 Y 为
   删除（磁盘上已经没有那个文件）时，索引是那份内容唯一的容身之处，取消暂存等于把它删掉。程序把
   这句话讲明白并允许取消；取消不碰仓库，也不会为了让命令“看起来成功”而去写文件或改用别的命令。
5. **冲突条目一律拒绝**。实测 `git restore --staged` 作用在未合并路径上会成功执行，并把三份 stage
   记录收拢成 HEAD 的那一份、留下 MERGE_HEAD 与工作区里的冲突标记——这等于悄悄改写了冲突现场。
   取消暂存不是解决冲突，因此选中条目里出现任何未合并状态都整份拒绝（连合法的那条也不单独执行），
   并说明该走的正路（在工作区改好后“加入暂存区”，或明确地中止合并）。反过来，冲突仓库里取消暂存
   另一个已暂存的文件时，实测 `UU` 记录、MERGE_HEAD 与冲突标记全部原样保留。
6. **子模块只退回提交指针**。取消暂存只把父仓库索引里的 gitlink 退回最近一次提交记录的值；实测命令
   不会进入子模块工作区，内部未提交的文件与未跟踪文件都不动，而因为子模块检出的提交没变，父仓库
   随后仍会把这条指针改动显示在未暂存一侧。这段范围限制写在确认框里，由用户先看到再决定。
7. **成败只认 Git 的退出码**。操作在保留的 `cmd` 窗口里执行，程序按结果文件取退出码：
   `git restore --staged` 遇到点击之后才消失的路径会**先校验再动手**，实测整条命令失败且没有半个
   路径被撤回；失败后不重试、不换命令，只转述 Git 的原始错误并立即重读两侧列表。带路径的
   `git reset` 对匹配不到的路径是静默跳过（实测退出码 0），所以界面同样以刷新后的真实状态为准，
   而不是“命令跑完了”。
8. **范围绝不扩大**。没有选中什么都不做；多选只处理选中行；清单形态下路径不进命令行，旧 Git 退回
   参数形态时超出承受能力就直接拒绝执行，不改成不带路径的全量取消，也不分批。文件名里的 `[ ] # ! %`、
   前导 `-`、空格与中文都按字面 pathspec 送达。

## 8. 提交表单：提交信息、作者与合作者

本模块只做“表单数据 + 校验 + 消息合成”；多行正文走临时文件传给 `git commit -F`，不会把表单文字
拼进命令行。表单校验通过后，`创建提交` 按钮的行为见下一节。

1. **不润色用户的文字**。标题单行、必填、不能全为空白；描述可空、可多行。不检查任何前缀风格
   （`feat:`/`fix:` 之类一概不管），不翻译、不改写、不修剪描述中间的行——只做三件确定性的事：
   行尾统一成 LF（多行编辑控件插入的是 CRLF）、去掉首尾空行、按“标题 / 空行 / 描述 / 空行 /
   trailer 段”排版。
2. **身份格式“姓名 <邮箱>”**。校验规则刻意比 Git 严：实测 `git commit --author=...` 对坏形态几乎
   不检查，只会静默把身份拆成另一个样子写进提交（本表在本机 Git 2.56 实测）：

   | 输入 | Git 实际记下 | 本程序 |
   |---|---|---|
   | `Name <a@b> extra` | 姓名 `Name`，邮箱 `a@b`（尾端文字丢掉） | 拒绝 |
   | `Na<me <a@b>` | 姓名 `Na`，邮箱 `me a@b`（拆错） | 拒绝 |
   | `A <a@b> <c@d>` | 姓名 `A`，邮箱 `a@b`（第二组丢掉） | 拒绝 |
   | `Name <a@b`（缺 `>`） | 照样接受 | 拒绝 |
   | `  <a@b>`（缺姓名） | 拒绝（退出码 128） | 拒绝 |

   另一方面刻意不苛刻：邮箱只要求“有 `@` 且不在首尾、不含空白”，因此 `a@b`、`user+tag@host`、
   非 ASCII 信箱、`& % " $ ; |` 等 shell 特殊字符一律接受——它们的风险在“怎么交给 Git”，不在格式本身。
   换行、CR、Tab、NUL、C1 与 U+2028/U+2029 一律拒绝：一条身份里塞进换行，就能在提交信息里凭空多出
   一行 trailer。
3. **作者初值向 Git 问，不自己读配置文件**。仓库本体的 `.git/config`、用户层（含 XDG 与
   `GIT_CONFIG_GLOBAL`）、系统层、`include`/`includeIf` 的优先序是 Git 的规矩，本程序只发
   `git -C <工作区根> --no-optional-locks config --null --get user.name`（`user.email` 同理，实测
   2.56 一次问两个 key 不成立：第二个参数被当成值样板），照它的答复合成 `姓名 <邮箱>`。实测语义：
   退出码 0 输出“值+NUL”（头尾空白原样保留，用作身份时 Git 自己会修剪，界面同样修剪）、退出码 1
   是“没设过”而不是失败、配置档语法坏了是 128 并带 `fatal: bad config line N`、同一 key 多值时取
   最后一个、**在非仓库目录里也照样回答用户层身份**（所以只在已识别出的工作区根上发起查询）。回答
   必须是“值 + 结尾那个 NUL”才作数：值读到一半就断（缺结尾 NUL）或那一路输出根本没读全，按
   “查不到”报告，不会把半条值当成一个完整身份。用户在界面里改作者只影响本次提交，程序绝不写回任何
   配置；提交者身份仍由有效配置决定，界面按同一次查询报告它现在“可用 / 缺失 / 还不知道”。
4. **合作者是一条条独立的条目**，通过模态输入框添加（Enter 确定、Esc 取消），双击列表某一行修改，
   `删除` 按选中行（可多选）。格式不对或与已有条目是同一位时，输入框**不关闭**，把原因写在框里；
   同一位的判定是“姓名与邮箱都折叠空白后、按 ASCII 大小写不敏感相同”（`ZS@Example.Invalid` 与
   `zs@example.invalid` 算同一位）。列表内部模型与行号一一对应，收进去的是修剪过头尾空白的写法。
5. **trailer 去重只看描述的最后一段**。判定顺序：描述按空行分段，最后一篇每行都是 `键: 值`（或空白
   开头的续行、且最后一行不是续行）才算 trailer 段；段内 `Co-authored-by` 的条目与表单里的合作者按
   上面的同一位规则比较，重复的**在原位置换成表单写法**，不在表单里的 `Co-authored-by` 与其它键
   （`Signed-off-by` 等）原样保留、顺序不变，表单里剩下的依顺序追加在段末。全形冒号“说明：”这类
   中文散文行不会被当成 trailer 键，正文中间的引用也就不会被删——程序不做任何全局字符串替换。
6. **表单内容属于哪一个仓库要讲清楚**。作者初值是后台查回来的，所以“程序填的”和“你打的”分开记：
   你没动过作者栏时，默认值可以落地；你动过之后默认值绝不覆盖（只把配置里的身份报给你看）；把作者
   栏清空就是主动退回“用配置里的身份”。切换仓库时如果表单里已有你输入的内容，先弹框问“保留 /
   放弃 / 取消”，只有明确选“否”才丢弃（关闭对话框等同取消，不会吃掉你打的字）；选保留后那段旧默认
   作者转成你的内容，不会被新仓库的配置悄悄盖掉。刷新则完全不动标题、描述、合作者与时间。
7. **说明分两条通道**。表单自己的话（校验结论、合作者增删、作者值的来路）显示在底部说明栏，
   “任务状态”那一行继续留给仓库状态与命令窗口操作的结论——两边都是要看的，谁也不该把谁抹掉。
8. **纯函数承担全部格式处理**。`git/commit_identity`、`git/commit_message`、`git/author_config`、
   `app/commit_form_session` 都不依赖 Win32，可用纯字符串与桩输出完整测试；界面只做“搬运 + 显示”，
   不从单元格文本反解任何参数。

## 9. 日期时间与创建提交（`git commit`）

规则分两层：`git/commit_date` 与 `git/commit_plan` 是纯逻辑，时区换算、信息文件写出与 Git 目录
痕迹探测在 `platform/windows`，界面只做搬运与显示。

1. **两个时间各自独立，值都带明确时区**。作者时间进 `GIT_AUTHOR_DATE`，提交者时间进
   `GIT_COMMITTER_DATE`；日期与时分秒都能用键盘直接改，控件年份限 1970–2099。本机 Git 2.53 与
   自建临时仓库实测：

   | 交给 Git 的写法 | 实测结果 |
   |---|---|
   | `1759219200 +0800`（10 位秒数 + 偏移） | 接受，`%ad` 原样显示该偏移 |
   | `0 +0800`、`10000000 +0800`（不足 9 位） | `fatal: invalid date format`，退出码 128 |
   | `@0 +0800`、`@1 +0000`（带 `@` 的内部形态） | 接受，秒数没有位数门槛 |
   | `-1 +0800`、`-100000000 +0800`（负数） | 一律拒绝 |
   | `4294967295 +0800`、`253402300799 +0800` | 一律拒绝（贴近 32 位秒数边界） |
   | `1969-07-20T20:17:00+00:00`（ISO 带 `T`） | 拒绝 |

   因此一律采用 `@<UTC 秒> <±hhmm>`：秒数取该墙上时间真正的 UTC 瞬间，偏移取**那一刻**在本机实际
   生效的偏移（`TzSpecificLocalTimeToSystemTime` 按那一天的夏令时规则判定），界面右侧的说明显示的
   就是它。带明确偏移是为了不让 Git 按“读这个环境变量的进程所在时区”补默认值——那种默认值会把用户
   挑的时刻挪掉几个小时。夏令时“跳过的那一小时”与“重复的那一小时”由系统给出确定映射，本程序照实
   回报系统给的那个偏移，所以显示的偏移与交给 Git 的值永远是一对，不存在“界面说 A、Git 记 B”。
2. **默认值取“提交那一刻”，不是程序启动那一刻**。没人动过时间控件时，点 `创建提交` 会先把两块控件
   改成此刻（改完让你亲眼看到要用的时间），再进入核对；你手动改过之后就一律用你改的值，刷新列表、
   切换分支结论、命令窗口回来都不重置它。改错了要退回此刻，点 `恢复当前时间`——它同时清掉“你改过
   时间”的记号，这是那条明确的退路。切换仓库时选“放弃表单内容”，时间也回到此刻。
3. **`时间同步修改` 默认勾选，且联动看得见**。勾着时提交者那两块控件置灰，改作者时间即同步过去，
   交给 Git 的两个值取同一个时刻；取消勾选后两侧各改各的（例如让提交时刻晚于作者时刻）。勾选状态
   改变时底部说明栏会写清现在适用哪条规则。
4. **身份分工不变，且只覆盖本次子进程**。作者来自表单（拆成 `GIT_AUTHOR_NAME` 与
   `GIT_AUTHOR_EMAIL`），提交者仍由这个仓库的有效 Git 配置决定，本程序一概不覆盖
   `GIT_COMMITTER_NAME` / `GIT_COMMITTER_EMAIL`，也不写任何配置文件、不改你自己的环境变量（覆盖
   只进那一次 `CreateProcessW` 的环境块）。配置凑不出提交者身份时直接拒绝并说明原因（缺失与“还没
   读到”是两句话），不替用户写配置。
5. **点击之后先重读，再给确认框；确认框绑的是刚问回来的那一份现状**。顺序是：表单校验（标题/作者/
   合作者）→ 时间换算 → 后台只读重读仓库摘要与 `git status`（复用刷新链路，不弹窗口、不阻塞界面）→
   紧接着再问一组“这次提交该绑定的事实”：工作区根与绝对 Git 目录、完整分支引用（`refs/heads/…`）、
   HEAD 的完整对象 ID、**索引内容标识**、有效配置里的提交者身份，以及 Git 目录里的流程痕迹。这一组
   同样在工作线程里问，不弹窗口。索引内容标识取 `git write-tree` 给出的树对象 ID：它是 Git 自己对
   “索引里现在是这样一堆内容”的签名，路径、模式、内容任何一处变化都必然换出一个不同的 ID，而未
   暂存的工作区改动动不了它。这一步唯一的可观察副作用按实写在确认框里：`write-tree` 会把算出的树
   对象写进仓库的对象库（没有任何引用指向它，之后由 Git 自己的垃圾回收清理），并可能顺手刷新索引里
   过期的文件状态信息（条目与内容一字不动）；不产生提交、不移动分支或标签、不改工作区文件、不写配置。
   确认框里能看到：实际要执行的命令与工作目录、上面这一组事实（含完整的树对象 ID）、本次提交的
   暂存条目（超过 15 项折成“另有 N 项”）、未暂存条目数（明确说它不会进入本次提交）、提交信息前
   20 行与字节数、两个身份、两个时间与偏移。点下按钮那一刻界面显示的 HEAD 与暂存条目数会被留下做
   对比：与刚读回的**不一致时，提示写在确认文字最前面**（“HEAD 从 X 变成 Y”“已暂存的条目从 M 项
   变成 N 项”），并列出现状已就地更新，绝不假装旧列表还成立。切换仓库、识别失败或这一轮根本没能
   发起读取时，这次待确认的提交直接作废。
6. **点了“确定”还要再核一遍，核不过就作废**。发出命令之前，程序把上一组只读查询**原样重发一遍**，
   逐处与确认框上写的那一份比对：工作区根或 Git 目录换了、完整分支引用换了（哪怕 HEAD 一个字符
   没动，例如同一份提交上切到另一条分支）、HEAD 换了或变得解析不出来、**索引内容标识换了**（条目数
   一点没变、只是暂存的内容或模式被外部工具换过，这种改动只有树 ID 看得见）、确认之后才开始的
   合并/变基等流程、确认时还没有的 `index.lock`、有效配置里的提交者身份换了人——任何一处对不上就
   不发命令，弹窗把对不上的地方逐个列出来，删除刚写的提交信息文件，**表单里的标题、描述、作者与
   合作者一个字都不动**，然后重读仓库现状，让你对着新的现状重新点一次“创建提交”、重新确认一遍。
   这一道能保证的边界也写在确认框里，不含糊成“事务”：它覆盖“你点下确定”到“程序创建那个进程”之间；
   再往后到 Git 自己读索引那一小段，归 Git 自己的 `index.lock` 管，本程序既不持那把锁也不等它；
   而 `prepare-commit-msg`、`pre-commit` 这类 hooks 本来就可以在你的授权下改动暂存内容，那种改动
   发生在复核之后。因此这是“确认的那一份与执行的那一份对得上”的复核，不是把外部并发写入或 hooks
   一并锁死的隔离保证。
7. **拒绝在执行任何命令之前**。以下情形一律不弹命令窗口、不改动仓库，并把原因写进“任务状态”：
   没有暂存内容（同时说明不会代为暂存、不会用 `git commit -a`）；还有未解决的冲突条目（点名条目）；
   仓库里有没走完的特殊流程；提交者身份凑不出来；作者身份残缺或含控制字符；时间换算不出（或落在
   Git 收不下的区间）；提交信息文件路径含双引号/控制字符（无法安全进 cmd）；那一组事实没能问齐
   （超时、Git 没回答、回答的形状不对，都按“这份事实没读回来”拒绝，绝不退回用早前那一份继续），
   或问回来的与界面上显示的对不上（那种确认框会写成“一半旧的一半新的”拼出来的承诺，索性不给）。
   特殊流程的判定依据是 Git 自己留在**绝对 Git 目录**里的痕迹（`MERGE_HEAD`、`REVERT_HEAD`、
   `CHERRY_PICK_HEAD`、`BISECT_LOG`、`rebase-merge\`、`rebase-apply\`），只读地判断存在与否；那种
   状态下的提交与平常不是一件事（合并提交会带第二个父、变基中途的提交会推进待办清单），本程序当前
   不接手，也**绝不替你终止那种流程**（不 `--abort`、不 `--quit`、不 reset）。`index.lock` 存在时
   只在范围说明里提醒一次：锁由 Git 自己管，程序既不删也不等。
8. **命令形态与底线**。实际执行的是

   ```
   git commit --cleanup=verbatim -F <临时信息文件>
   ```

   - 正文一律走 UTF-8 临时文件，绝不拼进命令行（多行、引号、`%`、中文都不必再考虑 shell 展开）；
   - 不带 `-a`、不带任何路径参数：提交范围就是索引里那一份，未暂存的改动留在工作区；
   - `--cleanup=verbatim` 是实测后写死的：Git 对 `-F` 的默认清理是 `whitespace`（会收拢连续空行、
     去行尾空格），而 `commit.cleanup` 是用户自己的配置。把形态写进命令，才能保证“不润色用户的
     文字”不因配置或版本而变——实测正文里的 `# 开头的行` 在 `-F` 下不会被当注释删掉，但空行与
     行尾空格会被 `whitespace`/`default` 收拾；
   - **不加 `--no-verify`**：hooks 与签名设置照常生效，需要口令或签名交互时由命令窗口里的 Git
     自己提问，程序不猜也不代答；
   - 信息文件的所有权随操作交给“在途操作”记录，只在拿到终态（Git 已退出，或根本没启动）之后删除；
     Git 可能还活着的结果未知场合宁留残档也不删，避免打断一次合法的提交。
9. **成功与失败各自收尾**。成功（退出码 0）后：清空标题、描述与合作者，**作者那一栏留着继续用**，
   两个时间回到此刻，底部说明交代清了什么、留了什么；紧随其后的自动重读把两个列表与 HEAD 更新到位。
   清空只针对**你确认并提交掉的那一份内容**：命令窗口里跑 Git 的那段时间你又在表单上打了新字，
   那几个栏位与“你改过时间”的记号都会保留下来，不会被一次成功的提交顺手抹掉。失败时表单一个字都
   不动（hook 拒绝、被 Git 判为冲突、路径问题等都是一样），命令窗口一直保留，用户可以直接改好再点
   一次。只有确认创建成功才清空——“窗口打开了”从来不是成功。退出码与 Git 的原始报错都写进
   “任务状态”，结论与重读后的仓库现状并排显示在同一行。

## 10. 最近提交（只读 `git log`）与提交详情（`git show`）

界面中部第三栏“最近提交”展示从当前 HEAD 可达的历史。

1. **只读、挂在同一次刷新里**。后台工作区读取在 `git status` 成功后紧接着发一条只读 `git log`
   （仅当 HEAD 可解析；尚无提交的仓库不发，那条命令在那种仓库里必然非 0 退出）：
   `-C <工作区根> --no-optional-locks --no-replace-objects -c log.showSignature=false
   log --no-decorate --format=%H%x00%an%x00%at%x00%s%x00%p -z -n 100`。
   `-z` 加 `%x00` 让字段与记录全部以 NUL 分隔，解析只按“每条五个字段”分组，绝不按空格/制表符拆
   列——中文、制表符、`%`、全角空格与几百字的长标题都原样回来，空标题（`--allow-empty-message` 的
   提交）也合法；`%H` 是完整对象 ID（SHA-1 40 位 / SHA-256 64 位，不硬编码长度），`%at` 是作者
   时间的 Unix 秒，界面按本机时区换算显示（含那一天实际生效的夏令时）；`%p` 数父提交识别合并提交。
   这一段与 `git status` 的成败**分开记录**：历史读取失败时两个文件列表照常落地，历史列单独显示
   归类原因，不会伪装成“没有提交”。同样要求**每条记录都以 NUL 收尾**：末尾缺那个 NUL（最后一条只
   回来半截标题或半截父提交列表）就整段作废，按“读取不完整”说明，而不是少列一条提交。
   （`--no-decorate` 必须排在 `log` 子命令之后；实测排在前面对 git 本体是未知选项。）
2. **最多 100 条，并明确说明**。不按 `--all` 无差别混合所有分支，也不一次读完大型仓库的全部历史；
   恰好返回满额时摘要注明“已达上限 100 条，更早的历史未读取”。本版本不做搜索与图形分支树。
3. **detached HEAD 照常可读**。读的是“从 HEAD 可达”，与是否挂在分支上无关。
4. **刷新保留选中**。历史列表与更改列表同一套就地更新：按完整对象 ID 记忆，刷新后仍存在的提交
   保持选中；创建提交/撤回之后随同一次刷新更新，被撤回的提交自然失去选中。
5. **双击某条提交：命令窗口里跑原生 `git show`**。先把双击的行号与刚读回的模型核对（行数一致、
   该行对象 ID 与模型一致），再用条目里保存的**完整对象 ID**构造
   `show --format=fuller --no-ext-diff --no-textconv --ignore-submodules=none --submodule=short <完整 ID>`：
   元数据（作者/提交者、两个时间与偏移）、正文与差异全部留在命令窗口里，结束后窗口保留、应用独立
   收到退出码。ID 不套在 `--` 之后（实测 `git show -- <id>` 会把 ID 当成路径、输出为空），安全的
   前提是执行前再校验一次“仅小写十六进制、24–64 位”；校验不过就弹说明、不开窗口。历史列是只读
   列表：不提供任何 checkout/reset/revert 入口，查看详情失败也绝不会把当前分支切到那条提交。

## 11. 撤回最近提交（带预期旧值的 `git update-ref`）

底部 `撤回最近提交` 按钮把**当前分支的最新一次提交**挪回它的第一父提交，语义上对应普通场景下的
`git reset --soft HEAD^`——但它不是 revert（不生成反向提交），更不是 hard reset（不丢弃任何改动）。
实际执行的是**带预期旧值的原子引用更新**，目标写的是**完整分支引用名**（`refs/heads/…`）而不是
可变的 `HEAD`：确认之后即使 `HEAD` 换指到别的分支，被移动的也只还是你确认的那一个引用。只移动
分支引用：索引与工作区一个字节都不动，原提交的改动相对新 HEAD 表现为“已暂存的更改”。按钮只针对
最新提交，与历史列表选中了哪条无关。

1. **点击时重新读取，不吃列表旧账**。按下按钮后先在后台发起一轮只读预检（`symbolic-ref --quiet HEAD`、
   `rev-parse --verify --quiet HEAD`、`rev-list --parents -n 1 <原完整ID>`、
   `cat-file commit <原完整ID>`、`rev-parse --is-shallow-repository`、
   `rev-parse --verify --quiet <第一父完整ID>^{commit}`、`log -1 --format=%s <原完整ID>`、
   `for-each-ref refs/remotes`（含 `--contains <原完整ID>`）与一次 `git status --porcelain=v2 -z`，
   全部隐藏窗口、带 `--no-optional-locks` 与 `--no-replace-objects`，不弹命令窗口、不访问远端），
   加上 Git 目录里的流程痕迹探测（与提交同一来源），全部读回来后才摆出确认框；对象类查询绑的都是
   预检那一刻拿到的**完整对象 ID**，不再写 `HEAD`；界面原先显示的 HEAD 或暂存条目数与刚读回的不
   一致时，确认框第一句就说明以刚读回的为准。
   （父对象可读性用 `rev-parse --verify --quiet <ID>^{commit}` 而不是 `cat-file -t --quiet`：实测
   本机 Git 2.53 的 `git cat-file` 没有 `--quiet` 选项，那样问会直接以用法错误 129 失败。判读层
   同时把“rc0 但答的不是那个 ID”归入父指针不一致，拒绝文案覆盖“读不到或并不是一个能解出的提交对象”。）
2. **明确拒绝、不给强制通道的状态**：仓库（或当前分支）还没有任何提交；游离 HEAD（没有分支引用可挪）；
   分支引用名不合格（不是 `refs/heads/` 下的完整名字）；父关系两处证据对不上；要挪去的父提交对象本地
   读不到或并不是一个能解出的提交对象；merge / rebase / cherry-pick / revert / bisect 进行中；有未
   解决冲突条目；工作区/索引现状或发布状态没能读回来；分不清「真正的第一个提交」与「浅仓库历史边界」
   （两边都说没有父，可 `--is-shallow-repository` 没给出答案）时也不会去删除分支引用。这些是“结果
   无法保证”或 Git 自己就先不接受的状态——“强制继续”不等于绕过 Git 拒绝执行的条件，因此那种场合只
   说明原因、不打开确认框、也不终止任何流程、不联网补全历史。
3. **浅仓库边界绝不当成“第一个提交”**。“这条提交有没有父”由两份互不相通的证据共同说话：
   `rev-list --parents` 给出的是 Git 的**历史视图**，浅仓库的历史边界会把有父的提交报成没有父；
   `cat-file commit` 读出的是**提交对象自己**记录的 `parent` 行，浅克隆仍保留完整对象，因此看得到被
   历史视图隐藏的父。两处不一致 → 判为浅边界，明确拒绝并说明需要你自己 `git fetch` / `--unshallow`
   补全历史（本程序不自动联网、不自动 unshallow）；两处都说没有父，**且**
   `rev-parse --is-shallow-repository` 明确回答 `false` 时，才认定它是真正的根提交。浅仓库里只要那个
   要挪去的父提交对象本地读得到，撤回照样允许，但会作为需要你明确确认的风险，并说明更早的历史不在本地。
4. **发布状态三态，绝不含混**。“这条提交是否已被远端包含”只拿本地已有的远端跟踪引用说话（不联网
   fetch，界面上也这么说）：命中 → **已知已发布**（列出命中的引用）；查询成功但没有任何引用包含它 →
   **本地信息未发现已发布**（会补一句：引用可能过期，这不能证明它从未被推送）；查询失败或本地根本没有
   `refs/remotes` → **无法判断**。已知已发布与无法判断都属于要用户明确确认的风险；领先/落后数量从不
   被用来断言是否发布。
5. **需要确认的风险走“强制撤回（仅本地）”**。除上面两类发布疑境外，合并提交（以第一父为目标并说明
   其余父提交的去向）与浅仓库也需确认。那种场合弹的是带专用按钮的风险框（TaskDialog；万一打不开则
   退回是/否并在正文点明对应关系）：`强制撤回（仅本地）` 与 `取消`。这个“强制”只是确认越过本程序的
   风险提示——执行的命令与普通撤回一字不差，绝不追加 `--hard`、绝不自动 force push、远端是否更新
   完全由用户之后自己决定。普通撤回（本地未发现已发布、干净或带改动的单父提交）则摆出同样的事实后以
   “确定撤回/取消”确认。
6. **已有改动一起保留，不承诺分成两堆**。索引与工作区不动，因此撤回后“已暂存的更改”里是原提交的
   改动与用户本来就暂存的改动**合在一起**的那一份（Git 不记录哪一行属于哪次提交，没法自动分开）；
   未暂存侧原样还在。这种撤回只移动分支引用、不碰索引，不会产生文本合并冲突——确认框把这两件事如实
   说清，不吓唬也不隐瞒。
7. **仓库的第一个提交**没有 `HEAD^`，软撤回表达不了“回到尚无提交”。受控路径是
   `git update-ref -d -m <说明> <完整分支引用> <原完整ID>`：Git 只在引用确实还指向这个 ID 时才删除它
   （值不匹配即以非 0 拒绝），删除的只有那一个分支引用，索引与工作区照旧一字不动，撤回后全部原提交
   内容表现为已暂存的新增。**不创建空提交冒充撤回**；形态不支持时直接说明阻止原因，绝不退回破坏性
   命令。分支引用被删除后它自己的 reflog 是否还在由 Git 决定，因此这条路径**不承诺**任何 reflog
   线索，可靠的找回依据只有原提交的完整对象 ID。
8. **普通撤回的命令形态**是 `git update-ref --create-reflog -m <说明> <完整分支引用> <第一父完整ID>
   <原完整ID>`。实测 `--create-reflog` 在 `core.logAllRefUpdates=false` 的仓库里照样留下该分支的
   reflog（`git reflog show <分支>`）；根提交的删除路径不承诺这条记录。
9. **点头之后、执行之前再核对一次 HEAD/分支**（两条毫秒级只读查询）。确认框是模态的，期间外部终端
   照样可能动了仓库：分支引用名或 HEAD 对不上就取消本次执行并刷新，绝不对着已经变了的目标执行旧方案。
   命令里带的预期旧值再由 Git 原子核对一次——“确认之后分支被别人推进”会让它直接拒绝。执行走命令窗口
   执行器：显示真实命令与 Git 输出，结束后窗口保留，应用独立拿到退出码并自动重读仓库；不以“窗口已
   打开”当作撤回成功。完整的符号引用事务需要 `git update-ref --stdin`，而命令窗口没有标准输入通道，
   因此“确认后复核与启动 Git 之间的极短窗口”本程序锁不住，确认框里如实写明这一点，不自称挡住了
   任意外部写入者。
10. **恢复线索随结果保留**。确认框、操作状态与撤回成功的结论里都带着**原提交完整对象 ID**，并写明
    找回方式 `git update-ref <完整分支引用> <原完整ID>`（根提交撤回后在“尚无提交”状态下同样可用，
    实测；这条找回命令不再带预期旧值，由用户确认时机）；本程序不自动恢复、不删除 reflog。

## 12. fetch（`git fetch --recurse-submodules=no --no-prune --no-prune-tags --no-tags <远端>`）

顶部 `fetch` 按钮向一个明确的远端抓取，**只更新那个远端在 `refs/remotes/<远端>/` 之下的远端跟踪
引用**：它不移动 HEAD、不改任何本地分支与本地标签、不动索引与工作区，也不顺带 `pull`。会被改动的
是这批跟踪引用、`.git/FETCH_HEAD` 与对象库——`fetch` 不是磁盘只读操作，确认框与状态栏都按这个口径
说，不写成「什么都没动」。

> **联网边界**：用户点击 `fetch` 按钮时访问**用户自己配置的远端**（含网络远端），这是产品功能、
> 属于用户操作，认证沿用用户已有的凭据助手/SSH agent/交互提示；而**自动化测试绝不碰网络**——它们
> 只在 `RemoteRig` 夹具自建的临时根内本地 bare 仓库上跑同样的生产代码路径（见 `testing.md` 的隔离
> 规则与守卫）。两者共用同一套方案层与执行器，差别只在「测试环境根本不放行网络形态的远端」。

1. **抓取目标只认两样东西**，此外一概不猜。按下按钮后先发起一轮只读预检（`symbolic-ref HEAD`、
   `branch.<分支名>.remote` 的有效配置、`git remote` 的既有远端清单，外加 `git config --null
   --get-regexp` 两条「影响抓取范围的配置」查询，全部隐藏窗口、带 `--no-optional-locks`，不弹命令
   窗口、不接触任何远端）：当前分支**明确配置**了远端且它确实在清单里 → 目标直接确定，摆出确认框；
   否则（分支没配远端、配置指向已不存在的远端、游离 HEAD）把既有远端连同各自 fetch URL 一个个摆进
   **远端选择界面**，选谁由用户点头。只有一个普通远端时也照实列为候选，默认选中它，但“点不点”仍在
   用户手里。无论目标是配置给的还是用户选的，**都过同一道范围核对**才给确认框。
2. **一个远端也没有就明说**：拒绝执行、不猜 `origin`、不自动创建远端、不改动任何配置；查询失败或
   `git remote` 回答不合约定时同样不在这上面猜目标。
3. **范围写死在命令里，而不只是「参数里没有 `--prune`」**（本机 Git 2.53 实测 + Git 官方文档）：
   `git fetch --recurse-submodules=no --no-prune --no-prune-tags --no-tags <远端>`。每个中和项各挡
   一件事：
   - `--recurse-submodules=no`：`submodule.recurse` / `fetch.recurseSubmodules` 不会把这一步扩大到
     子模块；
   - `--no-prune`：挡掉 `fetch.prune`（全局）与 `remote.<远端>.prune`（远端级）——这两条按文档
     「等同于在命令行上给了 `--prune`」，会**删除**过期的远端跟踪引用；实测命令行上的 `--no-prune`
     覆盖它们（把两条配置都设成 `true` 后 `git fetch --dry-run -v` 报出 `[deleted]`，加上
     `--no-prune` 就不再报）；
   - `--no-prune-tags`：挡掉 `fetch.pruneTags` / `remote.<远端>.pruneTags`——文档写明它等同于额外
     声明 `refs/tags/*:refs/tags/*`，动的是**本地标签**；实测该映射确实会被加进来，因此这一项不能省；
   - `--no-tags`：关掉 Git 默认的**标签自动跟随**（抓下来的对象所指的标签会被写进 `refs/tags/`），
     并按文档覆盖 `remote.<远端>.tagOpt`；
   - 命令里没有 `--all`／`--multiple`，且始终点名单个远端，所以 `fetch.all=true` 与 `remotes.<组>`
     那种远端组展开都不参与（文档：显式指定远端即覆盖 `fetch.all`；实测 `git fetch <组名>` 会把组名
     当仓库名而失败，只有 `--all`/`--multiple`/`git remote update` 才展开）。
4. **命令行绕不过的那一句只能验证**：`remote.<远端>.fetch` 决定「哪些本地引用会被写」。本程序逐条
   核对它的目标端，全部落在 `refs/remotes/<远端>/` 之下才肯执行；指向 `refs/heads/`、`refs/tags/`、
   别的远端命名空间，或镜像仓库那种 `+refs/*:refs/*`，以及没有目标端／目标端为空的写法，一律
   **在执行前拒绝并点名具体那一句配置**——不改写用户配置，也不换一套 refspec 去「凑」出承诺（那样
   会连带替换掉用户自己的分支过滤与上游映射）。合法形态原样放行：单分支过滤
   `+refs/heads/topic*:refs/remotes/origin/topic*` 这类映射，以及以 `^` 开头的负 refspec（文档写明
   负 refspec 只排除、不含目标端，是缩小而不是扩大）。只配了 `remote.<远端>.mirror=true` 而映射照常
   时**放行**：文档写明 mirror 只改变 push 的形态，不影响 fetch；确认框把这一点说出来。多个
   `remote.<远端>.url` 也只作披露——文档写明 fetch 用的是第一个地址。至于 `.git/branches/<名>` 那种
   Git 正在淘汰的档案形态，它的映射确实会把远端分支写进本地 `refs/heads/`，但 `git remote` 根本不列它，
   而本程序的候选只来自 `git remote`，因此不可能被选中。
5. **读不懂就不承诺**：`--get-regexp` 的回答缺结尾 NUL、被截断、认不出键名，或 prune/pruneTags/all
   的取值不符合 Git 的布尔语法（`true/yes/on/1`、`false/no/off/0`，省略取值即为真），一律拒绝执行
   并说明原因。实测本机 Git 2.53：`remote.origin.prune = maybe` 这种写法连 `git remote -v` 都会先
   失败，本程序的预检因此读不回事实——那种场合 Git 自己也不接受这次抓取。展示出来的配置原文一律
   限长并先做凭据掩码（URL 里的账号口令不会被抄到屏幕上）。
6. **真实执行留在命令窗口**：走与 `status` 同一个外部命令窗口执行器，需要口令或交互时由命令窗口里
   的 Git 自己提问，**沿用用户已有的认证方式**（凭据助手、SSH agent、交互式提示都在原生 `git.exe`
   那一侧，本程序不代管、也不写入任何凭据或配置）。结束后窗口保留，应用独立按 `result.txt` 取回
   Git 退出码——不以“窗口已打开”当作抓取成功。
7. **失败如实收场、不自动重试**：无远端、映射不合格、远端不可达、认证不过、用户在窗口里取消、命令
   非 0 退出，都按真实退出码给出结论并恢复按钮；绝不反复自动重试，也**不会因此改用 `--prune`、换成
   别的远端或别的地址、替你设置上游、或删除改写任何远端配置**。
8. **确认框说的是这一刻读回的配置，不是事务**：范围核对覆盖「点确定之前」；点头之后到 Git 真正读
   配置之间，外部程序仍可改动这份配置（包括那句 `remote.<name>.fetch` 映射），本程序不持有 Git 的锁，
   也没有事务级隔离——确认框把这句边界原样写出来，不自称锁住了任意外部写入者。
9. **抓取成功后重读**：结论里说明“只按确认框上那份范围更新了远端跟踪引用（`FETCH_HEAD` 与对象库
   随之变化）”，随后自动刷新重读仓库摘要与上游；下一次点 `撤回最近提交` 的发布状态判断用的就是这批
   新读回的引用——同一条本地提交，fetch 前判“本地信息未发现已发布”，fetch 到确实包含它的远端引用后
   改判“已知已发布”（三态判据完全共用）。
10. **与 `pull` 第一步同一个实现**：目标解析、命令行参数、范围验证与确认正文全部出自
    `src/git/fetch_scope.*` 这一份策略，`fetch` 按钮与 `pull` 的获取阶段都从它取，不可能各说一套范围。

## 13. pull（先 `git fetch`，再 `git merge` / `git rebase`）

顶部 `pull` 按钮把「把远端的更新拿到本地」拆成**两个可见阶段**，中间夹三轮只读预检。为什么不是一条
`git pull`：那样网络操作与整合被捆在一起，「预检看到的」和「实际整合的」可能不是同一份提交，也就
没法在动手前把关系与风险讲清楚。

```
点 pull → 预检①（只读）→ 确认框「本地分支 ← 远端分支」
        → 命令窗口：git fetch --recurse-submodules=no --no-prune --no-prune-tags --no-tags <远端>   ← 阶段一「获取」
        → 预检②（只读，含关系与冲突预演）→ 需要时选策略 → 带风险清单的确认框
        → 预检③（只读，执行前复核）→ 命令窗口：git -c … merge|rebase … <完整ID>   ← 阶段二「整合」
        → 按退出码结案并自动刷新
```

1. **前提由 Git 的回答决定，猜不出来就拒绝**。预检①问的是 `symbolic-ref --quiet HEAD`、
   `rev-parse --verify --quiet HEAD`、
   `for-each-ref --format=%(upstream:remotename)%(09)%(upstream)%(09)%(upstream:remoteref)`、
   四条策略配置查询（`branch.<分支>.rebase`、`pull.rebase`、`pull.ff`、`merge.ff`）、一条合并等效性
   配置清单（`git config --null --get-regexp`，覆盖 `merge.<名>.driver` 与 `pull.twohead`/`pull.octopus`）、
   两条影响抓取范围的配置查询、`git status --porcelain=v2 -z`，外加按 Git 目录里的档案判断的流程
   痕迹——全部隐藏窗口、带 `--no-optional-locks`，不弹命令窗口、不接触任何远端。以下情形给出**具体
   原因**并拒绝：不在分支上（游离 HEAD）、这个分支还没有任何提交、**没有明确上游**
   （`branch.<分支>.remote` / `.merge` 没配或只有半截）、有 merge/rebase/cherry-pick/revert/bisect
   还没走完、还有未解决的冲突条目、上游那个远端的 fetch 映射会把引用写到允许命名空间之外、任何一条
   查询没读回可采信的回答。拒绝时不产生命令，也**不猜 `origin/main`、不代跑 `git branch
   --set-upstream-to`、不写任何配置文件**——那种状态本程序说不准，Git 自己也会先拒绝，加参数绕不过去。
2. **获取是网络操作，就让它留在命令窗口里**。确认后执行的目标解析、参数生成、范围验证与确认正文都
   与 `fetch` 按钮**同出一份实现**（`src/git/fetch_scope.*`），两边的参数数组与命令展示逐字相同，
   各有测试钉住；这一步同样只保证「HEAD、本地分支、索引与工作区不在范围内」，`FETCH_HEAD`、对象库
   与允许命名空间里的跟踪引用会随抓取变化，确认框就这么写。需要口令时由命令窗口里的 Git 自己提问。
   这一步**不藏在界面的“刷新”里**：刷新永远是本地只读查询。获取失败（非 0、被拒、认证不过）就停在
   这一步——不自动重试、不因此改用 `--prune`、不换远端或别的地址、不替你设置上游、不改配置，也不去
   做任何整合。
3. **关系判据用完整对象 ID，四种关系各说各话**。预检②先用
   `rev-list --left-right --count <HEAD 完整ID>…<跟踪引用完整ID>` 问出「本地独有 / 远端独有」几个
   提交，据此分为**已一致 / 可快进 / 本地领先 / 已分叉**；再问 `merge-base`、
   `diff --name-only -z <基准> <远端ID>`（这次会带进哪些路径），分叉时还会问一句
   `rev-list --count --merges <基准>..<HEAD>`（本地独有提交里有几个合并提交——普通变基会把它们
   压平，确认框要点名这个数）。已一致与本地领先都是 `nothingToIntegrate`：一条命令也不给（本地领先
   属于 push 的范围，不是 pull 能解决的方向问题）。可快进的场合内容不可能冲突，**冲突预演根本不发起**；
   分叉时才做预演。
4. **内容冲突预演不改工作区与索引，但不是「完全不写仓库」**：
   `git merge-tree --write-tree --name-only <HEAD> <远端>`——它把结果 tree 写进对象库（不可达，`gc`
   自行回收），引用、索引与工作区分毫不动；绝不在用户工作区里先真合一次再 `reset` 回去模拟 dry-run，
   也绝不自动 stash。退出码 0/1 分别是「预演无冲突 / 有冲突」，冲突文件名从输出里按约定取出；这个
   Git 不认该子命令时（退出码 129/128）降级为**「没能预演，保守提醒」**并计入风险，不装作「没有冲突」。
   预演用的三方合并机械与真实合并并非在所有配置下都等效：仓库里存在 `merge.<名>.driver`（外部合并
   程序）或遗留的 `pull.twohead`/`pull.octopus` 配置、或那份清单没能完整读回时，预演结论一律**如实
   降档为「强提示而非保证」**并计入风险，让「没有冲突」不再被当成免检通行证。
5. **整合策略按 Git 原生解析读配置，选择、确认、预演与命令必须说同一件事**。`branch.<分支>.rebase`
   只要**存在**就单独说了算（哪怕它的取值是 Git 不认的——原生同样是当场 fatal 而不回落
   `pull.rebase`），不存在才轮到 `pull.rebase`；布尔取值大小写不敏感，`merges`/`interactive` 及
   缩写 `m`/`i` 必须严格小写；空值与裸键按原生布尔语义就是「假」（合并），与「没设」是两回事，判读
   层带着「存在与否」走。可执行的形态有三种：合并、普通变基、**保留合并结构的变基**——`merges`/`m`
   会真的翻译成 `git rebase --rebase-merges`，落地后合并提交仍是两父（集成测试用父子图核对，不是
   只看参数）。`interactive`/`i` 原生要开交互式编辑器、最终形态由用户当场改定的 todo 清单决定——
   本程序承诺不了「确认的形态=得到的形态」，只有真会执行它的场合（分叉且未被 ff-only 抢先）明确拒绝
   并交代人工办法，绝不悄悄换成普通变基或合并（可快进与无事可做时原生本来就不开编辑器，照常放行）；
   Git 自己都会当场拒绝的取值（`bogus`、`MERGES`、已并入 merges 的 `preserve`……）同样明确拒绝、
   点名那条配置，不降级、不猜。快进意愿按原生次序生效：`pull.ff` 存在即覆盖 `merge.ff`；配置给的
   `pull.ff=only` **优先于任何策略**——分叉时发出 `merge --ff-only` 让 Git 给出与原生一致的拒绝
   （仓库零改动），可快进时就是快进；用户当场选过策略（等价命令行 `--rebase`/`--no-rebase`）时原生
   把 `only` 降回默认，本程序照此建模并说明；`merge.ff` 只在合并路线被读到——它既不压制「问用户」，
   也不参与变基。反过来，**可快进 + 变基意图一律快进**：即便配置写着「绝不快进」，原生在这种组合也
   强制快进、不产生多余的合并提交。`merge.ff` 的无效取值原生 merge 明确忽略——照默认走，不跟着掉档；
   `pull.ff` 的无效取值则同 `pull.rebase` 一样如实拒绝。双方分叉而配置没定策略时，把「合并」「变基」
   两个候选摆出来由用户当场选（合并排第一，与本程序的默认倾向一致；原生 git pull 在这种情况下同样
   拒绝并要求当场定），选完还会再给一次带风险清单的确认——本程序从不写配置文件。因为实际执行的是
   `git merge`（它看不见 `pull.ff`），配置里的快进意愿被**翻译成命令行上显式的 `--ff-only` /
   `--no-ff`**：预检声称的形态与命令真正做的形态因此是同一件事。**变基这一路不做合并式预演**：
   重放是逐提交的，冲突可能出现在中间某一步，拿合并预演的结论去声称「变基不会冲突」是假话——确认框里
   明说这一点；普通变基还会按 `rev-list --count --merges` 的实数点名「本地这几个合并提交会被压平」
   并给出 `merges` 出路。
6. **命令形态把范围写死**（按配置/选择定下的策略各给一条示例）：

   ```
   git -c submodule.recurse=false merge  --no-autostash --no-edit        <远端提交完整ID>   （合并）
   git -c submodule.recurse=false merge  --no-autostash --no-ff --no-edit <远端提交完整ID>   （配置要求不快进）
   git -c submodule.recurse=false merge  --no-autostash --ff-only        <远端提交完整ID>   （可快进；或 ff-only 配置下由 Git 拒绝）
   git -c submodule.recurse=false rebase --no-autostash                  <远端提交完整ID>   （变基）
   git -c submodule.recurse=false rebase --no-autostash --rebase-merges  <远端提交完整ID>   （配置 merges：保留合并结构）
   ```

   `-c …` 与 `--no-autostash` 只对这一个子进程生效：不写配置，`autoStash` 类配置也不会把「替你
   stash」这件事悄悄做掉，子模块不会被递归改动。目标用**完整对象 ID**而不是引用名——钉住「刚刚抓
   回来的那一份提交」，不让执行时再去看那个引用又停在哪儿。没有 `--no-verify`：pre-merge /
   commit-msg 等 hooks 与签名照常生效。
7. **风险清单与「不保证」**。`requiresForce` 的风险条目逐条给原因并点名受影响文件：预演报出的冲突
   文件、未提交改动与带入路径的重叠、未跟踪文件与远端带来的同名路径撞车、变基会重写本地这几个提交
   （ID 变化、已推送过就会与协作者分叉，本程序不自动 force push）、普通变基遇到本地合并提交时按
   实数点名「会被压平」并给出 `merges` 出路、预演不可用、自定义 merge driver／遗留策略命中（或那份
   清单没读全）时预演结论降档为强提示、配置与当前关系相矛盾（如 `pull.ff=only` 而双方已分叉——照
   配置发出的那条会被 Git 原生拒绝）。风险确认框的按钮是「按这份预检继续整合」与「取消」（TaskDialog，
   失败时退回是/否并注明等价），「继续」只越过本程序的风险提示，不追加任何更激烈的参数。确认文字末尾
   写明预检**不是保证**：点头之后远端可能又变、hooks 可能拒绝、外部程序可能改同一个仓库。
8. **点头之后还要再核对一次现状才动手**。预检③把预检①那套查询原样重发一遍，`DescribePullChange`
   逐处比对：分支引用、HEAD、那条远端跟踪引用的位置、四条策略配置的「存在与否 + 取值」（确认框是按
   那一刻的配置承诺的形态）、合并等效性清单、工作区/索引的**逐条**现状（按「哪一侧、哪个路径、什么
   状态字元」排序比对，不只数个数）、流程痕迹有无变化。任何一处对不上就放弃执行、给出「从什么变成
   什么」的原因并刷新——预检之后的远端又动了也一样：不把旧预检当保证，也不靠盲目重复 fetch 把这件事
   盖过去。
9. **失败与冲突保留现场**。整合非 0 退出时，界面读回现场并明确说明：还有没有 Git 流程在进行
   （`MERGE_HEAD`、`rebase-merge\` 等档案）、`git diff --name-only -z --diff-filter=U` 读回的未合并
   文件清单、分支与 HEAD 现在在哪；同时列出这些文件在“未暂存的更改”里以待解决状态出现。本程序
   **从不** `merge --abort` / `rebase --abort` / `reset` / `--continue`，也不替你选任何一方的内容——
   处理现场是用户的决定。
10. **取消时的边界**。取消获取：命令窗口不打开、远端不接触、仓库不动。取消整合（获取已经跑过）：
    本地分支、索引与工作区都不动，但**那次可见的 fetch 已经把远端跟踪引用更新到远端的位置，这一处
    改动保留**——本程序不把它退回去（那要改写引用），确认后的状态栏与取消说明都写清楚这一点。

## 14. 推送（`git push`，只推当前分支这一条引用）

点 `推送` 后的路径是：后台只读预检 → 确认框（有风险时要求明确点「仍要推送」）→ 执行前复核 →
命令窗口里真实的 `git push` → 终态后自动重读仓库 → 另向**发布目标**发只读 `git ls-remote` 核实。
全程 GUI 不冻结，命令窗口保留输出，凭据由 Git 自己的认证方式处理。

1. **界面上必须看见三样东西**：源分支（`refs/heads/<分支>`，现在在哪一份提交）、目标远端（以及它
   **实际**的发布 URL，逐条展开）、目标分支（远端那一侧的完整引用名）。三者都取 Git 自己的回答：
   分支名来自 `symbolic-ref`，远端名与远端分支来自 `for-each-ref` 的
   `%(upstream:remotename)/%(upstream)/%(upstream:remoteref)`，本程序不改写、不缩写、不「就近取一个
   同名分支」。确认框上写的「要推送的那一份」是**完整提交 ID**，命令里钉住的也是它。
2. **命令形态把范围与内容都钉死**（本机 Git 2.53 实测，测试里逐条钉住）：

   ```
   git [-c remote.<远端>.mirror=false] [-c remote.<远端>.tagopt=] -c push.followTags=false \
       push --recurse-submodules=no <远端> <完整提交ID>:refs/heads/<远端分支>
   ```

   完整显式的 refspec 是关键，而且**源侧写的不是分支名、是你确认那一刻的完整提交 ID**——点头之后
   哪怕外部把这条分支又推进了（执行前复核会先作废旧方案），命令能送出去的也只是被钉住的那一份。
   `push.default`（实测设成 `nothing` 也照推）、`remote.<远端>.push` 的额外 refspec、
   `push.followTags`、`remote.<远端>.tagOpt=--tags` 在这种形态下都不会被附上，所以既不会多推分支，
   也不会顺带推标签。两句 `-c` 只为这一个子进程生效：`remote.<远端>.mirror=true` 实测会让「带
   refspec 的 push」以 128 失败（`fatal: --mirror can't be combined with refspecs`），存在时才补上
   中和它；`tagopt` 同理。命令里**没有** `--force` / `--force-with-lease` / `--mirror` / `--all` /
   `--tags` / `--no-verify`，也没有 `--set-upstream`：非快进就让 Git 拒绝，pre-push hook、签名与
   认证提示照常生效（源侧改为对象 ID 之后，钩子是否仍被唤起、钩子输入里是不是同一份提交、本地跟踪
   引用是否照旧前移，都由夹具用例在真实 Git 上逐条钉住；推送成败仍以发布目标的核实为准，不以跟踪
   引用前移与否为依据）。
3. **发布目标与抓取目标可能不是同一个地方**，这一点必须解析出来而不是猜。推送远端按 Git 自己的优先序
   裁定（`branch.<分支>.pushRemote` > `remote.pushDefault` > `branch.<分支>.remote`），裁定出的名字
   **显式**写进命令，于是那条优先序不再参与第二次。生效配置一次问回（`git config --list --null`；
   实测本机 Git 2.53 它输出的记录有三种合法形态——`键<换行>值`、显式空值 `键<换行>`、省略取值的布尔
   裸键 `键`——本程序把它们与「根本没设」严格分开判读，多行值原样保留，含 `include` 叠加与各层优先序
   都由 Git 自己算好，多值键的顺序原样保留），随后用 `git remote get-url --push --all <远端>` 让
   Git 把**每一个**实际发布地址逐条展开（`pushurl` 优先于 `url`，`url.*.insteadOf`／落回 `url` 场合
   的 `pushInsteadOf` 改写已叠在里面）。这条查询问不成——非 0、地址为空、条数与配置清单对不上、地址
   里有控制字符——一律拒绝发起推送，**绝不退回配置里未经解析的原样地址**继续发布。下列情况一律进
   风险清单、要求明确点头，并在确认文字里逐个列出：独立 `pushurl`、**多个** `pushurl`（实测
   `git push <远端>` 会推给每一个，这不是本程序扩大范围；那条命令的退出码是各目标合计的，逐目标
   收到没有以推送后的核实为准）、`insteadOf`／`pushInsteadOf` 改写过、推送远端与上游所在远端不同。
4. **前提不成立就拒绝，且不产生任何命令**：游离 HEAD（没有分支可推，不替它挑一个）、分支还没有提交、
   没有上游（`PushPlan` 的契约是「推当前分支到它的上游」，所以这里照旧 blocked：不猜 `origin/<分支>`、
   这条命令里不带 `--set-upstream`、不创建远端分支设置、不写任何配置文件，说明里给出该自己跑的那句命令；
   界面在这种场合改走下面第 10 条的「首次推送」，那是**另一条裁决链**，不是把这里的契约放宽）、
   上游配置只有远端没有分支记录、上游给出的远端引用不是 `refs/` 开头、
   裁定出的远端根本不在仓库的远端清单里（同时把既有远端列出来）、问不出一个可用的发布 URL（含上一
   条的任何一种解析失败）。仓库里的 merge/rebase 流程**不**阻止推送：推送只送已有的提交，不碰索引与
   工作区，那种现场只作为一句如实的说明出现。
5. **本地对远端的了解只到上一次 fetch 为止**。确认文字里的「领先 N 个、落后 M 个」依据的是
   `refs/remotes/<远端>/<分支>`，并且明确标出这是抓取的那一侧；落后 ≥1 时预先说明这次会被 Git 以
   non-fast-forward 拒绝（撤回已发布提交后正是这种场合），本程序不会为了让它“成功”而改用 `--force`。
   看起来已一致（不领先也不落后）时同样列为风险：仍然把命令发出去是为了向远端问个准话，而不是拿旧
   结论宣称成功。上游跟踪引用在本地还不存在时，说明「这次会在对端新建这条分支」并要求明确点头。
6. **点头之后、执行之前再核对一次**。`DescribePushChange` 逐处比对：当前分支引用、要推送的那一份
   提交、上游三件套、发布远端名、展开后的发布 URL 清单、会被中和的那些设置的有无可变。工作区/索引的
   改动**不在**比对范围——推送本来就不碰它们，点头之后你又改了一个没暂存的文件不该让一次合法的推送
   作废。任何一处对不上就放弃执行并刷新。核对通过到 Git 自己启动并读配置之间仍有一段谁都锁不住的
   窗口（本程序不持有、也不该持有 Git 的锁，配置层没法原子钉死）：送哪一份已经被命令钉死、不在那个
   窗口里；去哪里若在那一刻被外部改动，推送后的逐目标核实会把不一致如实报出来。这句边界原样写在
   确认文字里，不冒充事务。
7. **命令窗口里看得见真实过程**：实际执行的命令行（源侧就是那串完整提交 ID）、Git 的原生输出、需要
   口令时由 Git 自己提问（沿用你已有的凭据助手/SSH agent/交互提示），结束后窗口保留，本程序独立取
   退出码并刷新。命令与展示里出现的都是远端**名字**而不是 URL；凡是要显示 URL 的地方（`pushurl`、
   `get-url --push --all` 的回答、核实目标）一律先把内嵌的 `user:password@` 掩成 `***@`；Git 错误
   转述与诊断文本里**每一处**内嵌凭据的地址也过同一道掩码，凭据不进界面、不进状态栏。
8. **成功与否以发布目标的实况为准**。命令窗口报结束后，界面按**确认框上那一批已展开地址**逐个发只读
   `git ls-remote -- <发布 URL> <远端引用>`（后台线程、GUI 不冻结），把「刚推出去的那一份完整 ID」
   与对端那条引用的位置对照，结论分四种：已核实 / 与预期不符 / 部分核实（有目标没问到）/ 未能核实。
   `Git 报告成功` 但核不上时明确写“不把它算成推送成功”；命令报成功而某个目标没问到时，逐目标写
   “已推送但未核实”——既不替你断言送到，也不据此判失败；命令失败而核到对端已经到了那份提交时写
   “以实况为准”。已展开的地址再交回 Git 时仍可能命中 `url.*.insteadOf` 被**再次改写**（实测空值的
   `-c url.<base>.insteadOf=` 并不能取消既有规则，本程序不假装能关掉它）——那种场合核实问到的地方
   若与推送的不同，结论落到“与预期不符/没能核实”，不会硬说成功。**本地远端跟踪引用看起来一致不算
   证据**：实测推送到独立 `pushurl` 成功后，Git 照样把本地的 `refs/remotes/origin/*` 挪到了新位置，
   而抓取的那个仓库根本没收。这一步本身要联网，认证失败或超时只说明“这一处没能核实”，不据此断言
   推送失败，也不自动重试。
9. **失败保留现场**：非快进被拒、目标地址不存在、hook 拒绝、认证失败时，本地分支与远端都停在原位，
   本程序不重试、不改用更激烈的参数、不 reset、不改配置，命令窗口里留着 Git 的完整输出。

### 14.1 首次推送（这条分支还没有上游）

`git/first_push_plan` 是**独立的一条裁决链**：目标不再由仓库配置裁定，而是由用户当场选出来。
它的存在不放宽第 14 节任何一条承诺——同一条 push 命令、同一批 URL 解析与凭据掩码、同一个
命令窗口执行器、同一次执行前复核与逐目标核实。

1. **什么时候提起**：`CanOfferFirstPush` 只在几件事同时成立时为真——在分支上且分支引用形态合格、
   HEAD 已经解析出完整提交 ID、上游那条查询**问过且 Git 明确回答没有配置**（问不成不在列）、
   生效配置读回来了、仓库里至少有一个带 url 或 pushurl 的远端。任何一个不成立，界面展示的还是
   第 4 条那句拒绝，一个字都不改。
2. **候选从哪来**：远端名取自 `git config --list --null`（Git 叠好 include 与优先序的答案），
   每个候选的发布地址逐个用 `git remote get-url --push --all <远端>` 让 Git 自己展开——与普通推送
   **同一份解析函数**（`ResolvePushUrls`），条数对不上、地址含控制字符、非 0 退出都算这个候选
   「问不成」，带着原因留在清单里但不可选中，绝不拿未经解析的配置原文顶替。
3. **目标分支名是用户输入的资料**：输入框只做纯形态提示（空、首尾空格、空格、引号/冒号/控制字符），
   权威裁定是后台那条 `git check-ref-format refs/heads/<名>`（实测本机 Git 2.56：合格退出码 0、
   不合格 1、空串 1，三种都没有输出）。不合格就明确拒绝，不改写、不加前缀凑一个、不换一个名字。
   这个命令**不认 `--`**（实测带 `-oops` 连 `--` 都挡不住，先以 129 用法错误死在它自己的参数解析上），
   所以本程序只交 `refs/` 开头的完整引用形态。
4. **对端现状分三种答案**：Git 判这个引用名可用之后，才按每个已展开的发布地址发一次只读
   `git ls-remote -- <URL> refs/heads/<名>`——这一步**会访问远端**（只读，两边都不改）。
   退出码 0 且回答里没有那一行 = 对端还没有这条分支；非 0、启动不成、超时 = **问不到**
   （认证、权限、网络都归这一类）。两者的措辞与字段都分得开，绝不把「问不到」写成「没有」。
   各发布地址答的位置不一致时不合成一个位置。只有对端那份位置问得出、各目标一致、且确实与这次要推的
   不是同一份时，才追加一条 `rev-list --left-right --count <对端那份>...<这次要推的那份>`
   （形态与 pull 的关系查询同一份实现）：左=只有对端有的提交数，大于 0 就是会被 Git 拒绝的非快进；
   那个对象本地读不到时这条查询死在 Git 自己的解析上（实测 128 + fatal），结论就是「判断不了」，
   既不当 0 也不当「会被拒」。
5. **推送与设置上游是两步，各自有结果**。第 1 步是那条钉死完整提交 ID 的 push（与第 14 节
   第 1—3 条同一份构造）；第 2 步是两条各自在命令窗口里跑的 `git config`：
   `branch.<本地分支名>.remote = <用户选的远端>`、`branch.<本地分支名>.merge = <目标引用>`，
   一条只管一把键、一条一个退出码，键名/取值/适用分支/配置文件落点
   （`git rev-parse --git-path config` 当场问回；实测主工作区答 `.git/config`，
   开着 `extensions.worktreeConfig` 时普通 `git config` 的写入点仍是它）全部写进确认内容。
   **不用 `git push -u`**：那样「远端收到没有」与「本地配置写成没有」只剩一个退出码，
   本程序就没办法把两个结果分开报告；也不会为了用 `-u` 把命令的源侧退回成会变的分支名。
   第 2 步只在第 1 步报告成功之后才发；某一条没写成就停下、说清写到第几条、不自动重发、
   不自动回退已写入的那条。用户选「只推送」时一条配置都不写。
6. **点头之后同样再核对一次**（`DescribeFirstPushChange`，查询集原样重发）：分支、要推的那份提交、
   「上游还是没有」、选定远端还在不在清单里、展开后的发布 URL、引用名的 Git 裁定、对端那条引用的
   位置、会被中和的那些设置的有无。其中「上游已经被设好」单独措辞并让用户改走普通推送——
   那种场合目标已经由仓库配置说清楚了，不该拿临场挑的目标去执行。
7. **仍然不 force**：对端已有那条引用时列成风险要求明确点头，但命令里一个 `--force` 都没有；
   「首次推送」不是覆盖现有远端分支的理由，非快进由 Git 自己拒绝。
8. **任何一步取消都不留痕迹**：不打开命令窗口、不接触远端（除已经问过的那次只读询问）、
   不写任何配置。

> **联网边界**与 fetch/pull 同一口径：用户点 `推送` 时访问的是**用户自己配置的远端**，认证沿用其
> 已有的凭据助手/SSH agent/交互提示，本程序不代管凭据也不写入任何配置；自动化测试只在临时根内的
> 本地 bare 仓库上跑同一条生产代码路径（夹具环境写死 `GIT_ALLOW_PROTOCOL=file`，任何网络形态的
> URL 在发起连接前就被 Git 拒绝），绝不接触网络。
>
> **本版本的边界**：没有上游的分支只多出一个「首次推送」入口——目标远端与目标分支都由用户当场选，
> 上游写入必须用户明确同意，且只在推送成功后执行。除此之外程序不猜 `origin/main`、不做分支管理
> （改名、删除、重命名远端、给已有上游的分支改上游）、不强制推送、不推标签、不一次推多个分支；
> `pull` 仍然拒绝没有上游的分支，抓取与整合两步都不写配置。

## 15. 子模块导航（`进入子模块` / `返回父仓库`：只换绑定的仓库，不写任何东西）

列表里状态列写着「子模块」的那一条对应父仓库的一条 gitlink。导航做的事只有两件：
把界面绑定的仓库换成那个子模块自己的工作区，以及回到刚才那个父仓库；换过去之前把父仓库
界面上那份未提交的表单草稿连同来路一起收进代管，回到同一个仓库时原样交还。
实现分三层：`git/submodule_navigation`（查询形态、判读与措辞）、`app/submodule_journey`
（来路栈与草稿代管的纯状态机）、`platform/windows/submodule_probe`（只读探测的编排）、
`ui/submodule_flow`（阶段、作废与界面接缝）。

1. **三条只读查询的形态**（真实 Git 上已钉住）：父索引那条记录用
   `git -C <父根> --no-optional-locks ls-files -s -z -- :(literal)<相对路径>`
   （`-z` 不可省：不带它时 Git 把含空格/非 ASCII 的路径按 C 引号转写，那种回答不是原样路径，
   拿它比对会把合法子模块说成“路径对不上”；`:(literal)` 与暂存链路是同一份 pathspec 构造）；
   父提交记的那一份用 `rev-parse --verify --quiet HEAD:<相对路径>`（仓库还没有提交时以
   退出码 1 + 空输出答“没有”，实测不是 129 用法错误）；子模块现在的 HEAD 沿用
   `BuildPullHeadObjectArguments` 那一条，与 pull/push 预检完全同形态，不另写一套。
2. **进入之前必须三件都对**：目录存在且是目录；Git 认它是**当前这个**父仓库登记的子模块
   （识别结果 `kind` 是子模块且 `--show-superproject-working-tree` 答的根与界面绑定的父仓库
   折叠后相同）；父索引里那条记录确实是 `160000`。任何一条不过就明确拒绝并点名的确是哪一条：
   目录不见了、同名的是文件、独立仓库或另一份克隆、被移动过的子模块、裸仓库或 `.git` 内部、
   识别问不成（含 `safe.directory` 拦截）、索引里那条已经不是 gitlink。
   判读层不信“看起来像”：空输出是“明确没有这条记录”，查询失败是“不知道”，两者措辞不同。
3. **还没有初始化的子模块进不去**。那种目录里没有 `.git`，Git 从它往上找到的工作区根就是
   父仓库本身——这一条由识别的 `root` 与父根相同来识别，措辞是“还没有初始化”而不是含糊的
   “这不是仓库”。初始化/更新会联网并改动工作区，绝不在点导航时隐式触发；程序只把
   `git submodule update --init -- <路径>` 说给使用者，由他自己决定。clone 出来没初始化的
   仓库（gitlink 在索引里、目录空或不存在）因此同样被拒绝。
4. **返回的准入只看身份**：栈顶记下的那个子模块工作区根必须与界面当前绑定的根折叠相同
   才允许返回；用户中途自己在“本地仓库”那一栏填了别的路径时一句拒绝，代管内容原样留着——
   把父仓库那份草稿交到一个不相干的仓库上，比不返回更糟。嵌套子模块是多层栈，逐层退。
5. **表单草稿代管**：离开哪个仓库就按那个仓库的工作区根存一份（含标题、描述、作者、合作者
   与两个时间及“同步修改”勾选）；空的代管记录不存，免得回头拿一条空记录去问要不要覆盖。
   同一条父→子连点两次不压两层来路。交还前若界面上又有用户写的内容，先用风险确认框问一句
   （按钮上写清按下去是哪一份留下），两份都不会被悄悄覆盖；交还的作者栏按“用户自己写的字”
   记号落地，随后到达的“这个仓库的默认作者”不得盖掉它。这条链路上没有任何“自动清空”。
6. **回到父仓库后核三份位置**（全部只读，不联网）：`索引 / 父提交 / 子模块 HEAD` 合成六种
   结论——一致（显示干净）、指针已暂存、指针未暂存、问不出子模块位置、那条记录已不是 gitlink、
   问不全。每种各有措辞：未暂存时说“选中它点加入暂存区”，已暂存时说“下一步是在父仓库创建提交”，
   干净时补一句**父仓库显示干净不证明子模块那次提交已推到任何远端**；问不全时不说“该暂存”
   也不说“干净”。子模块内部有没有已跟踪改动/未跟踪文件，看的是父仓库列表里那一条自己的
   `S<c><m><u>` 状态，判读不混用别处的快照。
7. **导航不写任何东西**：不改父仓库索引、不产生提交、不访问远端、不递归进子模块暂存或提交，
   也不改任何配置。父仓库对子模块永远只有一条 gitlink——这条既有边界不因导航而放宽。
8. **并发与作废**：任何在途的被编排操作（预检、执行前复核、命令窗口里那条命令、推送后的核实、
   上游写入）都拦住导航（`app::DescribeNavigationRefusal`）；导航自己在途时也拦住写操作按钮。
   探测与识别都在后台线程，GUI 不冻结；识别回来的根与等待中的那个不一致时按“被人抢了切换”
   收场，代管内容与表单都不动。

> 实测口径：上面第 1 条与第 3 条里 Git 怎么答（`-s -z -- :(literal)` 被接受、unborn 时
> `HEAD:<路径>` 是退出码 1 + 空输出、普通目录被识别成“根就是父仓库”）由
> `submodule_navigation_queries_fixture_are_accepted_by_real_git` 与
> `submodule_entry_probe_fixture_refuses_paths_that_are_not_gitlinks` 两条只读夹具用例在
> 本机 Git 2.56 上钉住；需要真实提交图的那几条（登记的 gitlink、子模块内部提交后的三份位置、
> 未初始化的 clone、导航不动任何仓库）在 `git-mutating` 组，由维护者本人运行。
