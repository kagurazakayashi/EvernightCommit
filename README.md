# EvernightCommit（Git 提交工具，Windows 原生 C++）

项目名 **EvernightCommit**；窗口标题沿用需求文档规定的“Git 提交工具”。
面向 Windows 的 Git 提交图形界面工具，原生 Win32 + Common Controls，不依赖任何跨平台 GUI 框架。

**当前实现范围：Git 可执行文件的发现、选择与验证（步骤 2），仓库路径选择、仓库识别与当前分支摘要（步骤 3），
统一的 Windows 外部命令窗口执行器并接入 `status` 按钮（步骤 5），工作区状态解析——“未暂存的更改”
与“已暂存的更改”两个列表已按只读 `git status` 填充（步骤 6），手动刷新与操作结束后的自动刷新（步骤 7），
以及“加入暂存区 →”按钮：把选中的未暂存条目交给命令窗口里真实的 `git add`（见 3.6 节），
和“← 移出暂存区”按钮：把选中的已暂存条目从索引撤回（有提交时是 `git restore --staged`，
尚无提交时是同样只写索引的 `git reset -q --`，见 3.7 节），
以及提交表单的数据与校验：标题/描述的必填与排版、作者 `姓名 <邮箱>` 取自本仓库的有效 Git 配置（只读，
不回写任何配置）、合作者的增删改与 `Co-authored-by` trailer 去重（见 3.8 节），
以及作者时间与提交者时间（本机时区、显示该时刻实际 UTC 偏移）和 **`创建提交` 按钮**：
点击后先只读重读仓库现状再给出确认框，然后在命令窗口里执行真实的 `git commit`（见 3.9 节），
以及 **`撤回最近提交` 按钮**：点击后先只读预检分支 / HEAD / 父提交 / 远端跟踪引用与工作区状态，
再在命令窗口里执行真实的 `git update-ref <完整分支引用> <第一父完整ID> <原完整ID>`
（仓库的第一个提交走带旧值核对的 `git update-ref -d`），
只移动那一个分支引用、索引与工作区分毫不动；浅仓库的历史边界会被识别出来并明确拒绝（见 3.11 节），
以及 **`fetch` 按钮**：先只读问出抓取目标（当前分支配置的远端，或让你在既有远端清单里明确选择），
再在命令窗口里执行真实的 `git fetch --recurse-submodules=no <远端>`——只更新远端跟踪引用，
HEAD、本地分支、索引与工作区都不受影响（见 3.12 节）。**
以及 **`pull` 按钮**：分「获取」与「整合」两个可见阶段，两条命令都在命令窗口里执行，
中间夹三轮只读预检——先问出本地分支与它明确的上游，判出可快进 / 已分叉 / 本地领先，
用不改动工作区与索引的 `git merge-tree --write-tree` 预演内容冲突；整合策略尊重已有的
`pull.rebase` / `branch.<分支>.rebase` / `pull.ff` / `merge.ff` 配置（配置没定而双方分叉时
由用户当场选，默认偏向合并），点头之后再核对一次现状，然后才在命令窗口里执行
`git -c submodule.recurse=false merge --no-autostash …` 或 `… rebase --no-autostash <完整ID>`（见 3.13 节）。**
以及 **`推送` 按钮**：先只读问清「在哪个分支、要推哪一份提交、上游是谁、这次实际会推给哪个远端的
哪个地址」，把**源分支 / 目标远端 / 目标分支**与发布 URL 一起摆出来确认，然后在命令窗口里执行
带完整显式 refspec 的 `git push`——只推这一条引用，不带 `--force` / `--mirror` / `--all` / `--tags`，
也不推标签、不动子模块；命令窗口那头上报终态之后，还会向**发布目标**逐条发只读 `ls-remote`
核对那条引用到底停在哪，成功与否以那份实况参与结论（见 3.14 节）。**
程序启动即按 PATH 自动定位 `git.exe` 并在后台验证；“Git 程序”行可下拉选择候选、手动输入或浏览选择。
“本地仓库”行初值为程序启动时的工作目录（绝对路径），可键入或浏览选择，识别在后台只读执行，
并区分普通工作区、链接工作树、子模块、裸仓库、`.git` 内部、尚无提交、游离 HEAD 与非仓库目录。
仓库识别成功后，程序会在后台再读一次工作区状态，把改动分成“索引相对 HEAD”与“工作区相对索引”两侧显示；
读取全程只读，不写入对象库、不访问远端，也不会替你暂存或提交任何文件。
`status` 按钮会在**新的命令窗口**里执行真实的 `git status`：窗口显示实际命令与 Git 原生输出，
允许 Git 在终端里自己提问；本程序通过结果文件取得 Git 的退出码，不靠窗口是否关闭来判断成败。
草图里的依赖 Git 的写操作（暂存、移出暂存、创建提交、撤回提交、`fetch`、`pull`、`推送`）已全部接入，
各自有单独的接通开关（见 4 节 `AppState`），不会伪造数据或成功提示；
后台只读查询接口（`git --version`、仓库识别、工作区读取、有效身份读取、撤回/pull/push 预检、
推送后的远端核实）继续保留、不经命令窗口。

## 1. 环境与工具链

按官方资料确认的最低要求，以及本机实测版本：

| 组件 | 最低要求 | 本机实测 |
| --- | --- | --- |
| 编译器 | MSVC 工具集 14.28（Visual Studio 2019 16.11）起提供 `/std:c++20` | 14.51.36231（cl 19.51） |
| Windows SDK | Windows 10 SDK（`GetDpiForWindow`、`AdjustWindowRectExForDpi` 需 10.0.14393+；本工程按 `_WIN32_WINNT=0x0A00` 编译） | 10.0.26100.0 |
| CMake | 3.28（`CMakePresets` schema 8；C++20 支持自 3.12 的 `cxx_std_20` 起即有） | 4.4.2 / VS 自带 4.3.1 |
| 生成器 | Visual Studio 生成器，或 Ninja（需自带 `cl`/`rc` 的开发者环境） | VS 2026 + Ninja 1.13 |
| 目标平台 | Windows x64（仅支持 x64，非 Windows 会在配置阶段直接报错） | — |

> 注意：MSYS2 自带的 `cmake` 不提供 Visual Studio 生成器，且其 `link.exe` 会遮蔽 MSVC 链接器。
> 请使用 Visual Studio 安装目录下的 CMake，或独立的 CMake 发行版。

### 运行库部署要求

默认动态链接 VC 运行库（Debug `/MDd`、Release `/MD`）。因此：

- 开发机上（已装 Visual Studio）直接运行 `EvernightCommit.exe` 即可；
- 在未安装运行库的机器上分发时，需要随程序部署 **Microsoft Visual C++ Redistributable (x64)**，
  本机对应安装包为 `VC\Redist\MSVC\<版本>\vc_redist.x64.exe`；
- 若希望免部署单文件，可改用静态运行库：配置时加上
  `-DCMAKE_MSVC_RUNTIME_LIBRARY=MultiThreaded$<$<CONFIG:Debug>:Debug>`。

### 系统区域、代码页与用户名

本程序的数据链路不使用系统 ANSI 代码页（原因与做法见 3.3 第 2 条），因此不要求用户为了运行它
去改用户名、把仓库搬到 ASCII 路径，或开启/关闭 Windows 的“Beta: 使用 Unicode UTF-8 提供全球语言支持”。

验收矩阵与**实际验证状态**（不要把这一格当作已全绿）：

| 环境形态 | 本机是否已实测 | 说明 |
| --- | --- | --- |
| 系统 ANSI 代码页 = UTF-8（开启 Beta UTF-8 的 Windows 11） | 已实测通过 | 开发机即此形态；中文临时目录、中文仓库路径、含 `%`/`&`/中文/emoji 的文件名、中文窗口标题均可用 |
| 简体中文传统代码页（ACP/OEM 936） | **未实测，待人工验证** | 判定链路已经不看系统代码页，但需要在真的 936 机器上确认显示与交互；Git 输出为 UTF-8，控制台码页由命令窗口显式设为 UTF-8 |
| 西文代码页（1252/437） | **未实测，待人工验证** | 同上；这一形态下旧实现会因“ANSI 装不下中文”直接拒绝操作，现在不再有该判定 |
| 中文用户名导致 `%TEMP%` 含非 ASCII | 已实测通过（自动化用例把本进程临时目录指向中文目录） | 操作目录与说明书、标记、结果文件全部走 Unicode API |
| 仓库路径含中文、空格、`&` | 已实测通过 | 见 3.3 与 2.1 的命令窗口用例清单 |
| 窗口标题为中文 | 已实测通过 | 标题由命令窗口辅助进程用 `SetConsoleTitleW` 设置，不再按码页编码 |

在上述未实测的机器上如发现命令窗口打不开、窗口里中文显示成乱码或“关闭窗口”按钮找不到窗口，
请在反馈时附上状态栏原文与操作目录里 `spec.txt` 的内容（路径见状态栏提示），以便定位是哪一个环节。

## 2. 构建与运行

在项目根目录执行（PowerShell 或命令提示符）：

```powershell
# 使用 Visual Studio 生成器（无需开发者命令提示符）
cmake --preset vs2026-x64
cmake --build --preset vs2026-debug
ctest --preset vs2026-debug
.\build\vs2026-x64\bin\Debug\EvernightCommit.exe
```

只有 Visual Studio 2022 时改用 `vs2022-x64` / `vs2022-debug` / `vs2022-release` 预设即可。

使用 Ninja（必须先进入 “Developer Command Prompt for VS”，使 `cl.exe`、`rc.exe` 在 PATH 中）：

```bat
cmake --preset ninja-x64
cmake --build --preset ninja-debug
ctest --preset ninja-debug
```

其他常用开关：

- `-DBUILD_TESTING=OFF`：不生成测试目标；
- `-DGC_WARNINGS_AS_ERRORS=ON`：把 `/W4` 警告视为错误（CI 用）。

产物位置：`build/<预设名>/bin/<配置>/EvernightCommit.exe`。构建目录与 IDE 本地文件均已在
`.gitignore` 中排除。

### 2.1 自动化测试夹具与隔离规则

测试入口不变：`ctest --preset <预设名>`（或 `build/ninja-x64/bin/Debug/gc_tests.exe` 直接看逐用例输出）。
`-DBUILD_TESTING=OFF` 时测试目标与夹具完全不参与构建；测试运行期间不下载任何依赖。

纯逻辑测试用桩输出即可；涉及真实 Git 的用例由 `tests/support/git_fixture.*` 提供临时仓库夹具，
每条用例独立拥有：

- **临时根目录**：在系统临时目录下以 `CreateDirectoryW` 原子冲突重试创建唯一目录，
  只有亲手创建成功的实例才认领所有权；析构（含用例异常栈展开）递归清理，先清只读位、
  短重试应对杀软/索引器占用，析构不抛异常，删不净时打印残留路径。
  设置环境变量 `GC_TEST_KEEP_TEMP=1` 可保留现场（默认一律清理），保留时打印目录位置。
- **配置隔离**：子进程环境块剔除 `GIT_*`、`HOME`、`USERPROFILE`、语言变量后注入
  `GIT_CONFIG_GLOBAL`（指向临时空文件）、`GIT_CONFIG_NOSYSTEM=1`、空 `GIT_TEMPLATE_DIR`，
  用户的 `.gitconfig`、系统配置、模板与 hooks、凭据助手对测试仓库不可见；测试绝不写用户配置。
- **身份与时间确定**：固定测试身份 `Evernight Test <test@example.invalid>`，
  提交时间取固定基准 + 序号（与本机时钟无关），默认分支显式写死 `main`。
- **禁止网络**：`GIT_ALLOW_PROTOCOL=file` 只放行本地 file 传输，网络 URL 在发起连接前即被 Git 拒绝。
  夹具的 `AddRemote` / 克隆来源另有**测试远端守卫**：一切带协议的 URL（含 `file://`——它能指向
  UNC 网络共享，不能当作一定不联网）、scp 形态 `user@host:path`、UNC 路径与临时根之外的绝对路径
  一律拒绝，只放行临时根内的盘符绝对路径。
- **路径守卫**：所有 Git 调用显式绑定工作目录，且必须位于本次临时根内（折叠 `..` 后判定），
  越界直接拒绝；夹具永远不会在开发仓库或用户真实仓库执行 `init`/`add`/`commit`。
- **不碰 Git 的子进程用例**：`subprocess_capture_fixture_tests.cpp` 只驱动 `cmd.exe` 跑本用例
  自己写的批处理（全部 ASCII，数据文件按字节原样写在用例目录里），用来制造“输出恰好/超过保留上限”
  “两条流同时灌满”“子孙进程占着管道”“超时被终止”这些收尾形态；里面没有任何 Git 写操作。
- **前置条件失败与断言失败分开**：Git 不可用、临时目录创建失败、夹具命令意外非 0 退出等
  以“前置失败”中止用例并输出命令行、退出码与 stderr 诊断，但同样计入失败、返回非 0，
  绝不静默跳过集成测试。

允许例外（对应 AGENTS.md 权限边界）：夹具仅在自己创建并认领所有权的临时目录中执行
`git init`、`git add`、`git commit` 等真实 Git 操作；产生的提交是真实本地对象，
测试远端只允许是同一临时根内的本地 bare 仓库。`GitFixture` 因此提供多工作区辅助
（`SetActiveRepository` 切换活动工作区、`CloneRepository` 本地克隆、`AddRemote`/`Push` 经
测试远端守卫、`RevParseVerified` 读回引用实际指向），以及 `RemoteRig`——自动搭好
「一个 bare 远端 origin.git + 两个克隆自它的 A 与 B」的三方形态，
供 fetch/pull/push 各步骤用 `Run`/`RunCheckedInRepo` 执行生产方案合成的命令，
构造「B 推送→A 抓取」「无远端」「无效本地目标」「分叉」等场景。
集成测试覆盖：空仓库、初始提交、第二次提交父子链、
未暂存/已暂存/未跟踪状态、中文路径内容回读、配置隔离、协议封禁，用真实仓库驱动的
仓库识别边界（普通工作区、子目录上溯、尚无提交、非仓库、裸仓库、`.git` 内部、游离 HEAD、
链接工作树、子模块），用真实仓库驱动的工作区读取（修改/删除/新增/重命名双路径、暂存一次后再编辑的
两侧同现、未跟踪目录展开为单个文件、中文与含空格及 `&`、`^`、`%` 的文件名、内容冲突与“改/删”冲突、
本地子模块的“提交指针已移动”与“内部改动 + 内部未跟踪”两种状态、无提交仓库、非仓库目录的失败归类），
用真实临时仓库驱动“加入暂存区”的生产方案（多选只暂存选中项、删除与未跟踪、工作区重命名的两条目、
部分暂存后再次添加、`[ ] # ! % -` 与中文空格路径不越界命中、1200 条一次完成、未合并条目被记为已解决、
子模块只记指针、路径消失时全有或全无、旧 Git 的参数形态结果一致，并逐字节确认工作区文件未被改写）、
用真实临时仓库驱动“← 移出暂存区”的生产方案（有提交时索引逐条退回 HEAD、无提交时改用只写索引的
`git reset -q --` 且磁盘文件原样留下、部分暂存只撤索引那一份而工作区保持最新、重命名旧新路径成对撤回、
子模块指针退回而不进入子模块、`[ ]` 等字面路径不过度命中、600 条一次完成、路径消失时 restore 全有或全无、
旧 Git 的参数形态结果一致，同样逐字节确认工作区没有被改写）、
用真实临时仓库驱动“作者默认值”的生产查询路径（仓库本体配置优先于用户层、只有用户层时回落到它、
姓名与邮箱分属两层时逐 key 取值、`include` 递回包含、设成空值等同缺失、两项都没设、
配置档语法坏了报 128 而不是“没设过”、头尾空白按 Git 用作身份时的方式修剪，
并逐字节确认这次读取没改 `.git/config`、没动 HEAD、没产生 `index.lock`）、
以及用真实临时仓库驱动“创建提交”的生产方案（把 commit_plan 产出的参数与环境覆盖原样交给
真实 `git.exe`，再用 `git cat-file commit HEAD` 读回提交对象核对：作者身份与那一刻的
秒数加偏移 `1700000000 +0530`、提交者仍是配置身份而时间是另一个瞬间与偏移 `-0700`、正文里的中文/行尾空格/连续空行/
`#` 开头的行一字未改、`Co-authored-by` 只有一条且在最末、只有已暂存条目进入树而未暂存的改动
原样留在工作区、父提交只有一个，并核对提交落地后的 `HEAD^{tree}` 逐字符等于确认框上那个
「索引内容标识」（`git write-tree` 给的树对象 ID）——确认的那一份就是执行的那一份；
另外覆盖 `pre-commit` hook 拒绝时 HEAD 不前进且索引分毫未动、
真实冲突索引里 `write-tree` 问不出内容标识因而预检当场失败且不产生任何参数（`MERGE_HEAD` 同时被探到）、
`index.lock` 探测只读不删、身份预检问回的每一项都与真实 Git 一致且除了那棵树以外不改仓库、
索引内容标识只跟着索引走（只改工作区不动它，暂存后条目数不变而内容换了就一定换）、
确认之后被人换分支/换掉暂存内容/起合并时复核都作废旧方案、
UTF-8 信息文件的字节形态与用完即删）、
以及用真实命令窗口驱动的执行器（`status` 成功退出码 0、
无效参数的非 0 退出码来自 Git 而非命令窗口自身、中文空格与 `&` 目录、含 `& ^ % ! ( )` 的参数原样送达、
受控环境覆盖确实进入子进程、含双引号的注入在启动前被拒、Git 程序不存在报“启动失败”、
提前关窗得到“结果未知”而不卡在“执行中”、运行中被关窗落成“窗口被提前关闭”、
Git 进程无法创建时报“Git 未能启动”且不带任何退出码、
命令完成但保留窗口仍开着时照样结案并允许下一项操作、`Shutdown` 不等 Git 也不杀 Git，
以及中文临时目录、中文窗口标题、超出传统代码页的文件名与辅助入口的伪造请求拒绝；
操作目录生命周期的部分则覆盖：每次操作的目录名互不相同且用完即回收、
被推到“超过 60 分钟”阈值仍在进行的操作不会被下一次清扫误删（用只读的
`git hash-object --stdin` 造长任务，不靠提交拖时间）、磁盘上的 `start.txt` 与 `result.txt`
确实带着本次操作的口令、结果由临时名改名发布不留半截）。
另有 `tests/command_window_directory_tests.cpp` 一组隔离用例，在测试自己拥有的临时根里
检查时间阈值的参考值（60 分钟 = 3600 秒）、时钟不可信时一律不回收、
只有亲手新建成功才认领目录（已存在的目录连里面的旧结果都不复用、不覆盖）、
以及租约/开始标记被持有时整目录保留、名单之外的内容与删不动的目录原样留下、
目录联接不被越界清理。
命令窗口用例会真的弹出控制台，用例结束时由执行器关闭；若用例中途强杀进程，可能在 `%TEMP%` 留下
`GcOp<进程ID>x<随机段>` 目录。下次启动只回收“最后写入时间超过 60 分钟”**且**“名单内的文件
没有一个还被人持有”的目录，而且只删自己写出的那几个文件名：别的实例正在用的目录、
以及来历不明的内容都不会被动（详见 3.3 第 3 条）。

### 3.1 Git 前置条件与路径选择

运行本程序需要一个 Windows 版 Git（推荐 [Git for Windows](https://git-scm.com/download/win)）；
程序本身不携带也不安装 Git。`Git 程序` 的确定流程：

1. **自动发现**：启动时按当前进程的 Windows PATH 逐目录查找 `git.exe`（效果对应 `where git`
   的搜索意图），不扫描磁盘、不读注册表；多个候选按 PATH 顺序去重（大小写不敏感）后进入下拉列表。
   发现结果自动选中第一个候选并立即验证。
2. **手动选择**：直接在组合框键入路径（裸名 `git` 也会按 PATH 解析），或用 `浏览…` 选择 `git.exe`。
   有效路径统一规范化为绝对路径；后续所有 Git 调用都使用该确定的程序路径，不再依赖 shell 再次搜索。
3. **后台验证**：对工作线程直接以参数数组执行 `<git.exe> --version`（`CreateProcessW` +
   `CREATE_NO_WINDOW`，不弹命令窗口、不经 cmd 拼接），限时 3 秒，捕获退出码、输出与启动错误；
   确认路径是文件且程序确实报告 Git 版本后保存版本号供后续步骤使用。
4. **失败与恢复**：找不到 Git、文件不存在、无法启动、超时、输出不是 Git 版本，或程序正常退出但
   **它的输出没能完整读回**（读管道失败、超过保留上限、没读到结尾）时，“任务状态”显示
   具体原因；确认不了版本就不会开始使用它。改正路径后自动重新验证并恢复，无需重启程序。
   连续输入有 0.5 秒防抖；旧验证结果按序号丢弃，不会覆盖新选择。
   注意“输出没读全”与“这不是 git.exe”是两种说法：版本行可能在没读到的那一段里，
   程序不会据此断定你选错了程序。

### 3.2 仓库路径选择与识别

“本地仓库”的确定流程（对应开发计划步骤 3）：

1. **初值与输入**：初值是程序启动时的工作目录，取绝对路径后填入输入框；不修改进程的工作目录。
   支持直接键入（0.5 秒防抖）与 `浏览…` 选择目录；带空格、中文的路径按 UTF-16 原样处理。
2. **只问 Git，不看 `.git`**：识别一律以 Git 的回答为准，不用“目录里有没有 `.git`”推断，
   因为链接工作树与子模块的 `.git` 是文件，裸仓库根本没有 `.git` 子目录。
   查询全部是只读的 `rev-parse` / `symbolic-ref` / `for-each-ref`，以参数数组在隐藏窗口子进程中执行，
   每条查询都显式 `-C <仓库目录>` 并同时把子进程工作目录绑定为该目录，
   因此切换仓库不会影响正在运行的其他查询，也不依赖 shell 二次搜索。
3. **形态区分**：普通工作区、链接工作树（`--git-common-dir` 与 `--absolute-git-dir` 不同）、
   子模块仓库（`--show-superproject-working-tree` 有值）、裸仓库、`.git` 目录内部、非仓库目录。
   分支维度另外区分“尚无提交”（HEAD 不可解析但有分支名）与“游离 HEAD”（给出短提交 ID）。
   裸仓库与 `.git` 内部**没有可用工作区**：识别本身算成功，但不会进入面向工作区的提交流程，
   “任务状态”会说明原因；链接工作树与子模块则照常可用，只是额外说明来历。
   “来历”（链接工作树/子模块）与“分支状态”（游离/尚无提交）可能同时成立，标签会把两者一起讲清楚。
   上游为空时显示“未设置上游”，不会让仓库整体加载失败。
4. **错误恢复与连续切换**：识别在工作线程执行，GUI 线程不冻结；每次提交带递增序号，
   较慢完成的旧结果作废。路径不存在、不是目录、被 Git 的 `safe.directory` 安全检查拦截、
   权限不足、超时或输出不合预期，都会在“任务状态”里给出具体原因，改正后自动恢复。
5. **边界**：绝不在用户选中的目录执行 `git init`，不修改仓库或全局配置，
   不自动修复 `safe.directory` 与目录所有权，不执行 `fetch`，也不把真实仓库路径写进测试。
   识别用到的 Git 查询都是本地只读操作，不访问远端。

依赖 Git 的按钮要同时满足三个条件才会启用：功能已接通（草图里的写操作已全部接通，
每个按钮各有单独的接通开关，见 4 节 `AppState`）、
Git 程序验证可用、仓库已识别为可用工作区。`status` 另外要求“同一时刻只有一个操作在跑”（见 3.3）。

### 3.3 外部命令窗口执行器

用户主动点击的 Git 操作（第一个入口是 `status`）不在本进程里静默执行，而是**新开一个命令窗口**：

1. **窗口里看到的就是真实命令**。执行器用 `CreateProcessW` 启动**本程序自己的命令窗口辅助入口**
   （显式 `lpApplicationName`、可写的命令行缓冲、工作目录设为所选仓库、Unicode 环境块）。
   辅助进程先 `AllocConsole` 开一个新控制台窗口，用 `SetConsoleTitleW` 写上标题，
   把控制台输入/输出码页显式设为 UTF-8，原样回显即将执行的 Git 命令行，
   再用 `CreateProcessW` 直接启动 `git.exe`（输入输出都接到同一个控制台，
   所以凭据提示、GPG 口令提示都在这个窗口里原生交互）。Git 退出后辅助进程把窗口交给
   `cmd.exe /d /v:off /e:on /k`：`/d` 跳过注册表 AutoRun，`/v:off` 与 `/e:on` 显式固定
   保留窗口的交互形态（`!` 保持字面量、命令扩展行为不受注册表开关摆布；
   本次操作的参数本来就不经过这个 cmd，这些旗标只约束用户之后在窗口里手输的内容），
   `/k` 让窗口留在交互提示符，用户可继续翻看输出。
2. **一条链路上没有码页转换**。系统 ANSI 代码页、控制台输入/输出代码页、脚本文件编码与
   Git 自己的 UTF-8 输出是四件不同的事，本执行器只碰最后一件：
   * 路径、参数、窗口标题全部以 UTF-16 形态经 Unicode API 传递
     （`CreateProcessW`、`SetConsoleTitleW`、`CreateFileW`），不经过批处理字节流；
   * 一次操作的语义写进操作目录里的 `spec.txt`（**严格 UTF-8**：编码由我们自己校验，
     孤立代理项等非法码元直接失败，绝不写成问号、`U+FFFD` 或“最佳匹配”顶替原值）；
   * 命令窗口的控制台码页被显式设为 UTF-8，与 Git 输出的 UTF-8 对齐。
   因此**中文用户名下的临时目录、中文/空格/`&` 的仓库路径、含 `%`、`!`、中文的文件名、
   中文窗口标题，以及超出传统代码页的字符（西里尔、emoji）都能正常工作**，
   不需要用户改用户名、搬仓库，也不需要开启或关闭“Beta: Unicode UTF-8”来绕过。
   旧实现要把路径与参数按系统 ANSI 代码页编码后写进批处理，因此这三类情形会被整次操作拒绝；
   现在那段编码（`ansi_text`）已经删除，系统代码页不再参与判定。
3. **成败判定与窗口无关**。每个操作有自己的独占临时目录（`%TEMP%\GcOp<进程ID>x<随机段>`，
   父目录可以是非 ASCII 路径；随机段每次新生成，只有亲手把目录新建成功的那一次才算认领它，
   撞名就换一个猜不到的名字重来，绝不采纳已经存在的目录，也不复用其中已有的任何文件）。
   里面有五个文件：`spec.txt`（操作说明书，由本程序写入）、`start.txt`（辅助进程确实已开始执行，
   内容带着本次操作的随机口令）、`result.tmp` 与 `result.txt`（Git 的退出码，同样带着本次口令；
   先写 `result.tmp` 再改名为 `result.txt`，所以观察端要么还没有结果，要么读到的是完整一条）、
   `lease.txt`（执行器一直握到操作结束的租约）。结果行的最后一列是辅助进程创建 Git 进程时
   `CreateProcessW` 的直接事实（`started` / `notstarted`）：「Git 未能启动」据此判定，
   不再从任何退出码数值反推——Git 自己返回 9009 也只算它的一次普通回答。
   观察线程轮询这些文件与进程状态，
   把“进程启动 / 进程退出 / 标记文件 / 结果文件”四路事实合成唯一终态：
   `启动失败`、`已启动`、`执行中`、`执行完成`（含 Git 退出码）、`Git 未能启动`（无退出码可言）、
   `结果未知（窗口被提前关闭）`、`结果未知（辅助进程未能开始执行）`、`结果未知（超过观察期限）`。
   判定器给出终态的那一刻就结案并释放操作槽位，**不等保留的命令窗口关闭**：
   Git 跑完后窗口按设计一直开着，界面照样能立刻发起下一项操作。
   **绝不匹配 Git 输出里的某句话来判断成功**，也不把命令窗口自身的退出码当作 Git 的退出码；
   标记与结果里写的口令必须是**本次操作**的那一份，格式不对、只写了一半、或属于另一次操作的
   记录一律当“没有这条痕迹”，所以陈旧残骸不可能被认作这一次的成功。
   用完由本程序删除：正常结束时观察线程落账之后就收尾，启动前失败的那几次也不会把目录留下。
   应用退出时还有操作在跑，本程序**不会**去删它（那个命令窗口还要往里写结果），
   界面把它记成“结果未知”，绝不停在“执行中”。下一次启动会回收这类残留，但条件是两条都满足：
   最后写入时间超过 60 分钟，**并且**目录里本程序自己写出的那几个文件没有一个还被别的进程持有
   （执行器的租约、辅助进程握着的开始标记都是“还在用”的可查证据）。
   因此超过一小时的长操作、正在等你输入口令的操作、以及另一个实例正在用的目录都不会被误删；
   查不出结论的（权限不足、目录被做成链接、里面有来历不明的文件）保留不动，只留下诊断记录，
   回收也从不递归删除目录内容。
4. **GUI 不等待、不冻结**。`Start` 在界面线程只做“规划 + 写说明书 + 创建进程”，
   每个进行中的操作由独立观察线程等待，结束后向主窗口 `PostMessage`（消息只携带操作 ID，
   结果由执行器保管），界面线程不打开管道、不 `WaitForSingleObject`。
   关闭窗口时若还有操作在跑会先征求确认；无论用户怎么选，本程序都**不会终止正在运行的 Git**，
   已结束的窗口还开着也不会阻止应用退出。
5. **注入防护**。程序路径与每个参数都用引号包起来，并且要求路径与参数**不含双引号与控制字符**、
   引号区域之外不出现 `& | < > ^`、参数数量与命令行长度不超过上限——这类输入在启动进程之前就被拒绝，
   而不是“加个双引号当安全脚本”。现在没有任何 shell 参与 Git 的调用，
   所以 `%`、`!`、括号、`&` 都只是参数里的普通字符，实测原样送达 Git；
   上面那道引号区域校验仍然保留，为的是让“同一份输入在执行边界上只有一种合法形态”
   成为可测试的不变量，也防止日后又有人把这些值拼进某条 shell 命令。
   多行提交信息等正文走临时文件传给 `git commit -F`，不进命令行。
   **辅助入口不是通用命令执行器**：命令行上只有“操作目录 + 本次操作的随机口令”两项数据，
   要执行什么只来自该独占目录里的说明书；辅助进程会核对目录名的形态、说明书所在目录与
   说明书声明的目录名是否一致、口令是否与启动时传来的一致，然后用与界面同一套校验
   重新复核说明书内容，任一项不合格就不执行（也不写任何结果文件）。
   如实说明边界：这套绑定防的是“用别的目录来驱动这个入口”，
   能以当前用户身份在临时目录里造文件、造进程的第三方本来就拥有同样的执行能力，
   它不是同身份攻击者之间的隔离手段。
6. **集中环境策略**。后台预检与命令窗口执行共用同一份策略（`git/git_environment.h`）：
   继承环境里能改写命令语义的「重定向」变量一律不带走——仓库定位（`GIT_DIR`、`GIT_WORK_TREE`、
   `GIT_NAMESPACE`）、索引与对象库（`GIT_INDEX_FILE`、`GIT_OBJECT_DIRECTORY`、
   `GIT_ALTERNATE_OBJECT_DIRECTORIES`）、配置注入与重定向（`GIT_CONFIG_PARAMETERS`、
   `GIT_CONFIG_COUNT` 与逐条 `GIT_CONFIG_KEY_<n>`/`GIT_CONFIG_VALUE_<n>`、`GIT_CONFIG_GLOBAL`、
   `GIT_CONFIG_SYSTEM`、废弃别名 `GIT_CONFIG`）、身份与时间（`GIT_AUTHOR_NAME/EMAIL/DATE`、
   `GIT_COMMITTER_NAME/EMAIL/DATE`）都被移除，实际仓库、索引与身份因此始终由「界面选中的目录」
   和表单决定，从终端或其他 Git 工具里启动本程序不会把操作搬到别的仓库上。移除确实在继承环境里
   存在的重定向变量时，操作结论会按变量名告知用户（只列名字，绝不显示值）。
   其余变量照常保留：用户的真实 Git 配置、凭据助手、`PATH`、`HOME`/`USERPROFILE`、
   SSH 相关（`GIT_SSH`、`GIT_SSH_COMMAND`、`SSH_AUTH_SOCK`）一概不动，正常认证与工具链不受影响。
   命令窗口在此之上再落交互契约：设 `GIT_TERMINAL_PROMPT=1` 并删除 `GIT_ASKPASS` / `SSH_ASKPASS`，
   以免提问被搬成 GUI 弹窗而偏离“在命令窗口里原生交互”；
   并设 `GIT_PAGER=cat`——新建控制台是交互式 TTY，Git 默认把 `status`/`log` 之类输出交给 `less`，
   辅助进程会停在等用户按键的那一屏上，退出码迟迟拿不到、临时目录也被窗口占用，
   而命令窗口本来就保留全部输出供滚动查看，分页没有价值。
   「创建提交」表单的作者身份与两个时间作为操作覆盖排在策略之后，只进那一次子进程的环境块，
   不回写任何配置，也不改动本进程环境。

界面侧的“刷新”“路径选择”“仓库识别”等只读动作仍走隐藏窗口子进程（`subprocess`，
`CREATE_NO_WINDOW`、分别捕获 stdout/stderr），**不弹命令窗口**；两种模式刻意分开：
命令窗口模式不截获任何管道，以免破坏 Git 的终端输入；后台捕获模式不弹窗、不交互，
环境按同一份集中策略装配并额外设 `GIT_TERMINAL_PROMPT=0`——只读探测绝不停留在看不见的问题上
（凭据助手照常保留，那是看得见的交互）。环境块装配不起来时（进程环境读不出或为空、
覆盖名不合法）查询明确失败并给出原因，绝不退回“裸继承环境”去猜。

### 3.4 工作区状态解析（未暂存 / 已暂存两个列表）

仓库识别成功且该形态有可用工作区时，主窗口在后台再发只读查询填充列表
（`git status` 填两块文件列表，HEAD 可解析时紧接着一条 `git log` 填“最近提交”，见 3.10；
都是隐藏窗口子进程，不弹命令窗口）。对应开发计划步骤 6。

1. **取的是 Git 的机器可读输出，不是给人看的文本**。参数固定为
   `--porcelain=v2 -z --untracked-files=all --ignore-submodules=none`（外加 `-C <工作区根>`、
   `--no-optional-locks`、`--no-replace-objects`），全部以参数数组提交：
   * `--porcelain=v2`：每条记录用两栏 `XY` 分别描述“索引相对 HEAD”和“工作区相对索引”，
     因此**同一文件可以同时出现在左右两块列表**（暂存一次修改后又继续编辑，两侧状态互不覆盖）；
   * `-z`：记录以 NUL 分隔，且**路径原样输出、不做任何引号转义**——含空格、中文、`&`、`^`、`%`
     的文件名可原样还原，也不依赖 `core.quotepath` 与本机 ANSI 代码页。重命名/复制记录的目标路径与
     来源路径之间同样是 NUL，解析按记录类型成对消费，绝不按行或按空格拆文件名；
     同时要求这份输出**每条记录都以 NUL 收尾**：非空输出末尾少了那个 NUL，说明最后一条是残缺的
     （半个文件名），整份按“读取不完整”拒绝；完全空的输出才是合法的“干净工作区”答复；
   * `--untracked-files=all`：未跟踪目录展开成一条条可单独选择的文件，而不是只列一个目录；
   * `--ignore-submodules=none`：覆盖用户自己的 `submodule.*.ignore` / `diff.ignoreSubmodules` 配置，
     子模块状态一律如实回报。
   不请求 `--ignored`：被 Git 忽略的文件不进列表，程序也不会用任何强制加入手段。
2. **索引状态与工作区状态分开建模**。解析结果是两个独立列表；每条记录同时保留 Git 原始 `XY`
   状态码、仓库相对路径、重命名的来源路径与相似度字段。界面上的“状态/相对路径”文字**只用于显示**，
   构造暂存或提交命令时一律取这些原始字段，不从单元格文本反解。
3. **未合并项是冲突，不是删除**。`u` 记录（如 `UU`、`UD`）作为**一条**带“冲突”标识的条目落在
   未暂存那一侧：它需要在工作区里被解决，而解决它的动作正是暂存；程序不会把它拆成
   “一次删除 + 一次新增”冒充两侧都有的普通变化，也不会在读取摘要里把它当成干净状态。
4. **子模块区分“提交指针”与“内部状态”**。`<sub>` 栏位为 `S<c><m><u>`，分别是提交指针已移动、
   内部已跟踪文件有改动、内部有未跟踪文件。父仓库对子模块只有**一条 gitlink 记录**：
   在父仓库暂存子模块只会记录它指向哪个提交，子模块内部的文件属于那个仓库自己的改动，
   必须进入子模块工作区另行暂存与提交。因此父仓库列表里不会出现 `子模块内/某文件` 这种条目，
   程序也不会递归提交或把内部修改伪装成可在父仓库一次暂存的内容；
   读到子模块变化时，底部状态条会直接说明这条范围限制（鼠标停在列表上也有完整说明）。
5. **读取在后台执行，切换仓库不会串数据**。读取在工作线程跑，GUI 线程不冻结；
   每次提交带递增序号，较慢完成的旧结果按序号作废。开始新一轮仓库识别时**立刻清空**上一份列表，
   识别失败、目录不是仓库、裸仓库与 `.git` 内部这些没有可用工作区的形态同样清空，
   界面上不会出现“看着像当前仓库、其实是上个仓库”的条目（刷新链路的处理见第 3.5 节）。
6. **成功、干净、失败各有说法**。读取成功但两侧都没有条目时显示“没有未暂存的更改 / 没有已暂存的更改”，
   读取过程中显示“正在读取”，失败时显示归类原因（超时、启动失败、被 `safe.directory` 拦截、
   权限不足、`index.lock` 已存在、输出没读全等，判定见第 3.5 节第 9 条）。**输出不符合约定或没读全时
   整份丢弃并报告失败**，绝不交出解析出来的一半——
   一份缺文件的列表会让人在看不见的改动上做提交决定。所有读取都是只读的，
   失败信息里也据此说明“没有对仓库做任何改动”。
7. **本节没有做的事**：“加入暂存区”见 3.6 节，“移出暂存区”见 3.7 节；提交历史（`git log`）见 3.10 节。

### 3.5 刷新与任务状态协调

界面上有两类完全不同、但都叫“看仓库怎么样了”的动作，本项目的分工如下。

- **内部刷新（只读，不弹窗口）**：“刷新”按钮与操作结束后的自动重读都走这条路径，
  在本程序的后台线程里执行只读 Git 查询（仓库识别 + `git status`），只更新界面，
  **不会**打开 `cmd.exe` 窗口（详见 3.3 的窗口规则）。
- **命令窗口操作（用户主动执行）**：`status`、加入/移出暂存区、`创建提交`、`撤回最近提交`、
  `fetch`、`pull`（获取与整合两条）、`推送`，都在命令窗口里跑真实命令并保留输出。

一次刷新的覆盖范围：

1. **一次刷新同时更新顶部摘要与两个列表**。分支、上游、仓库形态都可能被外部终端改掉
   （切分支、在别处提交、`git pull`），只重读 `git status` 会得到“半新半旧”的界面，
   因此刷新先重新识别仓库、识别成功后接着读取工作区，两步都在后台。
   “最近提交”（`git log`）挂在同一次工作区读取里：`git status` 成功后紧接着追问一条只读 log
   （仅当 HEAD 可解析），不另建触发机制（见 3.10）。
2. **短时间内的多次刷新合并成一轮**。连点“刷新”、几个操作接连结束、切换仓库这几路触发共用一个
   防抖定时器（0.3 秒）；若请求到达时已经有一次读取在途，就只登记“读完再补一次”，
   合并槽是一个布尔标记而不是队列，**不会无限排队**，也不会让列表反复闪。
3. **过期结果一律丢弃**。每次请求都捕获仓库身份（Git 程序路径 + 工作区根）与身份版本号：
   切换仓库、改用另一个 `git.exe`、或识别失败/变成没有工作区的形态时版本号递进，
   迟到的旧结果被判定为过期后**不落地**，当前列表保持原样，等属于新身份的那一次读取来填。
   刷新（身份未变）时摘要与列表留在原位，等新结果就地替换，不整屏清空。
4. **操作结束后无论成败都重读一次**。失败的操作同样可能已经改动仓库（提交到一半、`push` 被拒、
   合并留下冲突）。成功与否只认 Git 的退出码：**命令窗口开起来不算成功**，
   只有拿到退出码且为 0 才报“成功”；状态栏会同时给出“刚才的操作怎么样”与“仓库现在怎么样”，
   详细输出仍留在命令窗口里。
5. **保留你的选择与视图**。列表按“条目身份”记忆多选（更改列表按仓库相对路径、提交历史按完整对象 ID），
   就地增删改行而不是整列清空——
   报表视图不响应 `LVM_SCROLL`，清空重建后没有任何消息能把视口放回去，所以“不清空”是保住
   滚动位置的唯一办法。某文件被暂存后从左栏移到右栏，选择跟着它走；已经被提交或被外部删除的条目
   自然不再被选中，也不会把选中状态挪到别的文件上。**刷新不会重置提交表单**：
   标题、描述、作者、合作者与两个时间都保持你输入的内容，时间也不会被改回“现在”。
6. **同一工作区同时只允许一个由本程序发起的操作**。操作在跑时 `status`、暂存/取消暂存、
   创建提交、撤回提交、`fetch`、`pull`、`推送` 都禁用（互相抢仓库锁没有意义），
   而“刷新”这类只读动作按条件继续可用。
   **已结束但保留下来的命令窗口不会锁住界面**：结果一到账就释放槽位；
   万一完成通知丢失（执行器已不再认识该操作），轮询会把它判为“结果未知”、释放槽位并安排一次刷新，
   而不是永远显示“执行中”。
7. **失败要能被再次刷新恢复**。读取失败、`git status` 因 `index.lock` 已存在而报错、
   命令窗口被提前关闭（拿不到退出码）、通知丢失，都会给出明确状态并允许再点刷新。
   本程序**绝不删除 Git 的锁文件**，也不代为 `reset`/`checkout`：锁是 Git 自己的并发保护，
   只能由持有它的那个进程结束后自然消失。
8. **外部改动靠手动刷新恢复**。用户完全可以在别的终端里改仓库（本项目不做文件监听，
   也不引入复杂的监视机制）：只要点一下“刷新”，界面就会回到 Git 回答的真实状态。
9. **后台读取的输出：先完整读回，才拿来判断**。上面这些只读查询（仓库识别、`git status`、`git log`、
   作者默认身份、`fetch`/`pull`/`推送` 前的预检与核对）都在隐藏窗口里读 Git 的标准输出与标准错误，
   本程序对它们的要求是“要么完整、要么不算答案”：

   * 标准输出与标准错误**分别**读取，各自记录收尾形态：正常读到结尾、超过保留上限被截断、
     读取本身失败、子进程结束后管道迟迟不关（它的子孙还占着写端）而主动放弃，是四种不同的结果，
     界面上说的就是哪一种，不写成“没有输出”；
   * 每一路保留上限为 16 MiB（够装二十万条上下的变化记录）。超过之后只留开头一段并明确判为
     “读取不完整”，**不会把少了若干条当成一份完整快照**；同时仍把管道排空，不把子进程卡在写不上；
   * 子进程退出后先把管道里已缓冲的输出排空再收工，等到结尾才算完整；放弃读取也有期限，
     不会让界面永远停在“正在读取”；
   * 字节必须是**有效的 UTF-8** 才会被解码使用。遇到不合法的字节（例如某个仓库里的文件名
     本来就不是 UTF-8 编码），这一次读取按“输出不完整”失败处理，**不会**用替代字符拼出一个
     看起来能用、其实与磁盘上不同的路径去暂存或提交；
   * NUL 分隔的机器输出还必须满足“每条记录都以 NUL 收尾”。末尾缺那个 NUL 就是半条记录
     （半个文件名、半条配置值、少字段的提交记录），整份拒绝；完全空的输出仍然是合法的
     “干净答复”（干净工作区、没有匹配的条目），不会被误判成失败；
   * 因此某一次读取不完整时，界面显示“Git 输出读取不完整（原因…）”并提示重新读取，
     而不是一个空列表或“0 项”。**推送与 `pull` 的确认框在配置或冲突清单读不全时直接拒绝发起**：
     半条 URL 也像一条 URL，本程序不在看不清实际发布地点的前提下推送。

### 3.6 加入暂存区（`git add`）

把“未暂存的更改”里**选中的**条目交给命令窗口里真实的 `git add`，执行结束后自动重读两侧列表。
反方向的“← 移出暂存区”见 3.7 节。

1. **没有选中就是“什么都不做”**。点击时如果一行都没选，只在“任务状态”里给一句说明，
   绝不把“没有选择”理解成“暂存全部”：程序构造的参数里不会出现 `.`、`-A`、`-u`、`--all`，
   也不会用 `git add -p`/`-i` 这类要人按键的形态。
2. **只处理选中的变化**。修改、删除（记下删除本身就是暂存的一部分，无需 `-A`）、类型变化、
   未跟踪新文件、子模块 gitlink 与未合并条目都按各自条目处理；没选中的条目原地保留，
   同一路径已暂存的那一份改动也不会被顺带动到（可重复点：索引内容更新为工作区当前内容）。
3. **路径按字面语义交给 Git**。实测本机 Git 2.56：`--pathspec-file-nul` 的 NUL 分隔只关闭
   “引号/C 转义”这一层，**pathspec 的 glob 魔法仍然生效**——清单里直接写 `brk[x].txt`
   会连带命中同目录的 `brkx.txt`。因此每条路径都带 `:(literal)` 前缀，实测加前缀后只命中自己；
   `#` 开头不是注释、`!` 开头不是取反、`%` 原样保留、前导 `-` 不会被当成选项，
   中文与含空格、`&` 的文件名同样按原样送达。
4. **多选很多文件不受命令行长度限制**。所选路径写进 `%TEMP%` 下一个 NUL 分隔的 UTF-8 清单文件
   （文件名含进程号与进程内序号，用 `CREATE_NEW` 独占创建，绝不覆盖别人的同名文件），
   命令里只出现 `--pathspec-from-file=<路径>` 与 `--pathspec-file-nul`；实测 1200 条路径一次完成。
   清单在 Git 退出（拿到退出码）之后删除；若命令窗口被提前关闭而 Git 可能还在读它，宁可留一个
   临时文件也不删。
   旧版本 Git（`git --version` 解析不出 2.25 及以上）退回“字面 pathspec 直接进参数数组”的形态，
   范围与清单形态完全一致；条目数或长度超出参数形态的承受能力时**直接拒绝执行**并说明原因，
   不静默退化成 `git add .`，也不自作主张分批。
5. **重命名按一次变化处理**。索引侧的重命名条目会同时给出旧路径与新路径，两条一起交给同一条命令；
   工作区里改名的真实形态是“.D 旧路径”+“?? 新路径”两条未暂存条目，要暂存这次改名请把两条都选中
   （实测选中两条后 Git 记成 `R100`，只选新文件则旧路径的删除仍留在未暂存侧）。
6. **未合并（冲突）条目必须先由用户确认**。`git add` 会把该文件**工作区里的当前内容**写进索引并记为
   已解决——实测连 `<<<<<<<` 标记也会一起进索引。程序不判断冲突是否真的解决完，只在执行前把这句话
   原样讲出来，由用户选择继续或取消；取消不会打开命令窗口，也不会改动仓库分毫。
7. **子模块只记录提交指针**。父仓库对子模块只有一条 gitlink：指针已移动时这一次 `git add` 记录新的
   提交 ID；指针未移动、只有内部改动时这一次实际上是空操作（实测退出码仍为 0，内部脏文件一个都不进
   父索引）。程序把范围限制说在前面，绝不递归进入子模块暂存或提交，也不改子模块任何东西。
8. **失败保留 Git 的原始回答**。选中的某条路径在点击之后才消失（外部删档/移动）时，Git 报
   `fatal: pathspec ... did not match any files`（退出码 128），实测此时**整条命令没有任何内容进索引**，
   是全有或全无，不会出现“一半暂存成功”；程序只转述这条错误与退出码，绝不改成更大范围的 `add` 重试，
   也绝不删除 `index.lock` 之类的锁文件（锁文件原因见 3.5）。
9. **并发与后续动作**。点击瞬间按行号核对条目身份并拷成选择快照，之后的刷新不会改变本次范围；
   工作区根与协调器身份不一致时拒绝执行（避免把上一个仓库的路径用到新仓库上）；
   同一时刻只允许一个命令窗口操作，按钮在操作进行期间禁用；命令窗口里的 Git 结束后照常自动重读一次，
   窗口本身保留供查看输出（详见 3.3、3.5）。

### 3.7 移出暂存区（`git restore --staged` / `git reset -q --`）

把“已暂存的更改”里**选中的**条目从索引撤回，工作区一个字节都不动，执行结束后自动重读两侧列表。
范围控制、字面 pathspec、清单文件与旧版本退回这些机制与 3.6 完全同一套代码，只是命令方向相反。

1. **只写索引**。有最近一次提交时命令是 `git restore --staged -- <所选路径>`：实测已暂存的修改退回
   HEAD 的内容而磁盘上仍是最新字节（条目回到“未暂存的更改”）、已暂存的删除把路径放回索引而磁盘上
   依然没有那个文件（不会“顺手把文件捡回来”）、已暂存的新增从索引移除而文件原样留在磁盘上变成未跟踪。
   绝不使用 `git restore`（不带 `--staged`，那会改写工作区）、`git reset --hard`、`git checkout --`
   或 `git clean` 这类会丢弃改动的命令，也没有任何“命令失败就换破坏性后备”的路径。
2. **没有 HEAD、或者 Git 太旧没有 `restore` 时，换一条同样只写索引的命令**。仓库还没有任何提交时
   `git restore --staged` 会当场失败（实测 `fatal: could not resolve 'HEAD'`，退出码 128，索引分毫未动）；
   而 `git restore` 这个子命令本身是 2.23 才有的，更旧的 Git 只会回
   `git: 'restore' is not a git command`。两种场合都改用 `git reset -q -- <所选路径>`：
   实测效果与前者一致——所选路径的索引条目退回最近一次提交的版本（没有提交时即从索引移除）、
   磁盘文件原样保留并回到未跟踪，未选中的索引内容不受影响。
   **带路径的 `git reset` 只动索引**；只有不带路径的那种形态才会改动 HEAD，
   本程序绝不构造（没有选中时直接不执行，并说明这一点）。
   HEAD 是否可解析取仓库识别时 Git 自己的回答（`headResolved`），`restore` 是否存在取
   `git --version` 的回报值（解析不出来就当作不支持，宁可用保守的那条命令，不猜）。
3. **重命名必须成对撤回**。索引侧的重命名条目会同时交出旧路径与新路径两条 pathspec：实测只撤新路径会
   留下“旧路径仍是暂存的删除”这种半成品状态，界面上就变成一半已撤、一半还暂存着。
4. **内容只存在于索引里的条目先要用户点头**。X 为新增/重命名/复制（HEAD 里没有这个路径）而 Y 为删除
   （磁盘上已经没有那个文件）时，索引是那份内容唯一的容身之处，取消暂存等于把它删掉。程序把这句话
   讲明白并允许取消；取消不碰仓库，也不会为了让命令“看起来成功”而去写文件或改用别的命令。
   集成用例专门断言：这份内容消失是因为它本来就不在磁盘上，而不是被哪条命令删掉的。
5. **冲突条目一律拒绝**。实测 `git restore --staged` 作用在未合并路径上会成功执行，并把三份 stage 记录
   收拢成 HEAD 的那一份、留下 MERGE_HEAD 与工作区里的冲突标记——这等于悄悄改写了冲突现场。
   取消暂存不是解决冲突，因此选中条目里出现任何未合并状态都整份拒绝（连合法的那条也不单独执行），
   并说明该走的正路（在工作区改好后“加入暂存区”，或明确地中止合并）。
   反过来，冲突仓库里取消暂存另一个已暂存的文件时，实测 `UU` 记录、MERGE_HEAD 与冲突标记全部原样保留。
6. **子模块只退回提交指针**。取消暂存只把父仓库索引里的 gitlink 退回最近一次提交记录的值；实测命令不会
   进入子模块工作区，内部未提交的文件与未跟踪文件都不动，而因为子模块检出的提交没变，父仓库随后仍会
   把这条指针改动显示在未暂存一侧。这段范围限制写在确认框里，由用户先看到再决定。
7. **成败只认 Git 的退出码**。操作在保留的 `cmd` 窗口里执行，程序按 3.3 的结果文件取退出码：
   `git restore --staged` 遇到点击之后才消失的路径会**先校验再动手**，实测整条命令失败且没有半个路径被
   撤回；失败后不重试、不换命令，只转述 Git 的原始错误并立即重读两侧列表。带路径的 `git reset`
   对匹配不到的路径是静默跳过（实测退出码 0），所以界面同样以刷新后的真实状态为准，而不是“命令跑完了”。
8. **范围绝不扩大**。没有选中什么都不做；多选只处理选中行；清单形态下路径不进命令行，
   旧 Git 退回参数形态时超出承受能力就直接拒绝执行，不改成不带路径的全量取消，也不分批。
   文件名里的 `[ ] # ! %`、前导 `-`、空格与中文都按字面 pathspec 送达（同 3.6 的实测结论）。

### 3.8 提交表单：提交信息、作者与合作者

本步骤只做“表单数据 + 校验 + 消息合成”，`创建提交` 按钮仍然禁用：没有任何 Git 写操作被接进表单，
也不会把表单文字拼进命令行（多行正文将来走临时文件传给 `git commit -F`）。

1. **不润色用户的文字**。标题单行、必填、不能全为空白；描述可空、可多行。不检查任何前缀风格
   （`feat:`/`fix:` 之类一概不管），不翻译、不改写、不修剪描述中间的行——只做三件确定性的事：
   行尾统一成 LF（多行编辑控件插入的是 CRLF）、去掉首尾空行、按“标题 / 空行 / 描述 / 空行 / trailer 段”排版。
2. **身份格式“姓名 <邮箱>”**。校验规则刻意比 Git 严：实测 `git commit --author=...` 对坏形态几乎不检查，
   只会静默把身份拆成另一个样子写进提交（本表在本机 Git 2.56 实测）：

   | 输入 | Git 实际记下 | 本程序 |
   |---|---|---|
   | `Name <a@b> extra` | 姓名 `Name`，邮箱 `a@b`（尾端文字丢掉） | 拒绝 |
   | `Na<me <a@b>` | 姓名 `Na`，邮箱 `me a@b`（拆错） | 拒绝 |
   | `A <a@b> <c@d>` | 姓名 `A`，邮箱 `a@b`（第二组丢掉） | 拒绝 |
   | `Name <a@b`（缺 `>`） | 照样接受 | 拒绝 |
   | `  <a@b>`（缺姓名） | 拒绝（退出码 128） | 拒绝 |

   另一方面刻意不苛刻：邮箱只要求“有 `@` 且不在首尾、不含空白”，因此 `a@b`、`user+tag@host`、
   非 ASCII 信箱、`& % " $ ; |` 等 shell 特殊字符一律接受——它们的风险在“怎么交给 Git”，不在格式本身。
   换行、CR、Tab、NUL、C1 与 U+2028/U+2029 一律拒绝：一条身份里塞进换行，就能在提交信息里凭空多出一行 trailer。
3. **作者初值向 Git 问，不自己读配置文件**。仓库本体的 `.git/config`、用户层（含 XDG 与
   `GIT_CONFIG_GLOBAL`）、系统层、`include`/`includeIf` 的优先序是 Git 的规矩，本程序只发
   `git -C <工作区根> --no-optional-locks config --null --get user.name`（`user.email` 同理，
   实测 2.56 一次问两个 key 不成立：第二个参数被当成值样板），照它的答复合成 `姓名 <邮箱>`。
   实测语义：退出码 0 输出“值+NUL”（头尾空白原样保留，用作身份时 Git 自己会修剪，界面同样修剪）、
   退出码 1 是“没设过”而不是失败、配置档语法坏了是 128 并带 `fatal: bad config line N`、
   同一 key 多值时取最后一个、**在非仓库目录里也照样回答用户层身份**（所以只在已识别出的工作区根上发起查询）。
   回答必须是“值 + 结尾那个 NUL”才作数：值读到一半就断（缺结尾 NUL）或那一路输出根本没读全，
   按“查不到”报告，不会把半条值当成一个完整身份（见第 3.5 节第 9 条）。
   用户在界面里改作者只影响本次提交，程序绝不写回任何配置；提交者身份仍由有效配置决定，
   界面按同一次查询报告它现在“可用 / 缺失 / 还不知道”。
4. **合作者是一条条独立的条目**，通过模态输入框添加（Enter 确定、Esc 取消），双击列表某一行修改，
   `删除` 按选中行（可多选）。格式不对或与已有条目是同一位时，输入框**不关闭**，把原因写在框里；
   同一位的判定是“姓名与邮箱都折叠空白后、按 ASCII 大小写不敏感相同”（`ZS@Example.Invalid` 与
   `zs@example.invalid` 算同一位）。列表内部模型与行号一一对应，收进去的是修剪过头尾空白的写法。
5. **trailer 去重只看描述的最后一段**。判定顺序：描述按空行分段，最后一篇每行都是 `键: 值`（或空白开头的续行、
   且最后一行不是续行）才算 trailer 段；段内 `Co-authored-by` 的条目与表单里的合作者按上面的同一位规则比较，
   重复的**在原位置换成表单写法**，不在表单里的 `Co-authored-by` 与其它键（`Signed-off-by` 等）原样保留、
   顺序不变，表单里剩下的依顺序追加在段末。全形冒号“说明：”这类中文散文行不会被当成 trailer 键，
   正文中间的引用也就不会被删——程序不做任何全局字符串替换。
6. **表单内容属于哪一个仓库要讲清楚**。作者初值是后台查回来的，所以“程序填的”和“你打的”分开记：
   你没动过作者栏时，默认值可以落地；你动过之后默认值绝不覆盖（只把配置里的身份报给你看）；
   把作者栏清空就是主动退回“用配置里的身份”。切换仓库时如果表单里已有你输入的内容，先弹框问
   “保留 / 放弃 / 取消”，只有明确选“否”才丢弃（关闭对话框等同取消，不会吃掉你打的字）；
   选保留后那段旧默认作者转成你的内容，不会被新仓库的配置悄悄盖掉。刷新则完全不动标题、描述、合作者与时间。
7. **说明分两条通道**。表单自己的话（校验结论、合作者增删、作者值的来路）显示在底部说明栏，
   “任务状态”那一行继续留给仓库状态与命令窗口操作的结论——两边都是要看的，谁也不该把谁抹掉。
8. **纯函数承担全部格式处理**。`git/commit_identity`（解析/校验/同一位判定/去重）、
   `git/commit_message`（校验结论与消息合成）、`git/author_config`（查询参数构造与回答归类）、
   `app/commit_form_session`（谁写的、换仓库要不要问）都不依赖 Win32，可用纯字符串与桩输出完整测试；
   界面只做“搬运 + 显示”，不从单元格文本反解任何参数。

### 3.9 日期时间与创建提交（`git commit`）

本步骤把两个时间控件接成真正交给 Git 的值，并把 `创建提交` 按钮接到命令窗口里的真实 `git commit`。
规则仍然分两层：`git/commit_date` 与 `git/commit_plan` 是纯逻辑（可脱离窗口完整测试），
时区换算、信息文件写出与 Git 目录痕迹探测在 `platform/windows`，界面只做搬运与显示。

1. **两个时间各自独立，值都带明确时区**。作者时间进 `GIT_AUTHOR_DATE`，提交者时间进
   `GIT_COMMITTER_DATE`；日期与时分秒都能用键盘直接改，控件年份限 1970–2099。
   本机 Git 2.53 与自建临时仓库实测：

   | 交给 Git 的写法 | 实测结果 |
   |---|---|
   | `1759219200 +0800`（10 位秒数 + 偏移） | 接受，`%ad` 原样显示该偏移 |
   | `0 +0800`、`10000000 +0800`（不足 9 位） | `fatal: invalid date format`，退出码 128 |
   | `@0 +0800`、`@1 +0000`（带 `@` 的内部形态） | 接受，秒数没有位数门槛 |
   | `-1 +0800`、`-100000000 +0800`（负数） | 一律拒绝 |
   | `4294967295 +0800`、`253402300799 +0800` | 一律拒绝（贴近 32 位秒数边界） |
   | `1969-07-20T20:17:00+00:00`（ISO 带 `T`） | 拒绝 |

   因此一律采用 `@<UTC 秒> <±hhmm>`：秒数取该墙上时间真正的 UTC 瞬间，偏移取**那一刻**在本机
   实际生效的偏移（`TzSpecificLocalTimeToSystemTime` 按那一天的夏令时规则判定），
   界面右侧的说明显示的就是它。带明确偏移是为了不让 Git 按“读这个环境变量的进程所在时区”补默认值
   ——那种默认值会把用户挑的时刻挪掉几个小时。
   夏令时“跳过的那一小时”与“重复的那一小时”由系统给出确定映射，本程序照实回报系统给的那个偏移，
   所以显示的偏移与交给 Git 的值永远是一对，不存在“界面说 A、Git 记 B”。

2. **默认值取“提交那一刻”，不是程序启动那一刻**。没人动过时间控件时，点 `创建提交` 会先把两块控件
   改成此刻（改完让你亲眼看到要用的时间），再进入核对；你手动改过之后就一律用你改的值，
   刷新列表、切换分支结论、命令窗口回来都不重置它。改错了要退回此刻，点 `恢复当前时间`
   ——它同时清掉“你改过时间”的记号，这是那条明确的退路。切换仓库时选“放弃表单内容”，时间也回到此刻。

3. **`时间同步修改` 默认勾选，且联动看得见**。勾着时提交者那两块控件置灰，改作者时间即同步过去，
   交给 Git 的两个值取同一个时刻；取消勾选后两侧各改各的（例如让提交时刻晚于作者时刻）。
   勾选状态改变时底部说明栏会写清现在适用哪条规则。

4. **身份分工不变，且只覆盖本次子进程**。作者来自表单（拆成 `GIT_AUTHOR_NAME` 与 `GIT_AUTHOR_EMAIL`），
   提交者仍由这个仓库的有效 Git 配置决定，本程序一概不覆盖 `GIT_COMMITTER_NAME` / `GIT_COMMITTER_EMAIL`，
   也不写任何配置文件、不改你自己的环境变量（覆盖只进那一次 `CreateProcessW` 的环境块）。
   配置凑不出提交者身份时直接拒绝并说明原因（缺失与“还没读到”是两句话），不替用户写配置。

5. **点击之后先重读，再给确认框；确认框绑的是刚问回来的那一份现状**。顺序是：表单校验（标题/作者/合作者）→
   时间换算 → 后台只读重读仓库摘要与 `git status`（复用第 3.5 节的刷新链路，不弹窗口、不阻塞界面）→
   紧接着再问一组“这次提交该绑定的事实”：工作区根与绝对 Git 目录、完整分支引用（`refs/heads/…`）、
   HEAD 的完整对象 ID、**索引内容标识**、有效配置里的提交者身份，以及 Git 目录里的流程痕迹。
   这一组同样在工作线程里问，不弹窗口。
   索引内容标识取 `git write-tree` 给出的树对象 ID：它是 Git 自己对“索引里现在是这样一堆内容”的签名，
   路径、模式、内容任何一处变化都必然换出一个不同的 ID，而未暂存的工作区改动动不了它。
   这一步唯一的可观察副作用按实写在确认框里：`write-tree` 会把算出的树对象写进仓库的对象库
   （没有任何引用指向它，之后由 Git 自己的垃圾回收清理），并可能顺手刷新索引里过期的文件状态信息
   （条目与内容一字不动）；不产生提交、不移动分支或标签、不改工作区文件、不写配置。
   确认框里能看到：实际要执行的命令与工作目录、上面这一组事实（含完整的树对象 ID）、
   本次提交的暂存条目（超过 15 项折成“另有 N 项”）、未暂存条目数（明确说它不会进入本次提交）、
   提交信息前 20 行与字节数、两个身份、两个时间与偏移。
   点下按钮那一刻界面显示的 HEAD 与暂存条目数会被留下做对比：与刚读回的**不一致时，
   提示写在确认文字最前面**（“HEAD 从 X 变成 Y”“已暂存的条目从 M 项变成 N 项”），
   并列出现状已就地更新，绝不假装旧列表还成立。切换仓库、识别失败或这一轮根本没能发起读取时，
   这次待确认的提交直接作废。

6. **点了“确定”还要再核一遍，核不过就作废**。发出命令之前，程序把第 5 条那一组只读查询**原样重发一遍**，
   逐处与确认框上写的那一份比对：工作区根或 Git 目录换了、完整分支引用换了（哪怕 HEAD 一个字符没动，
   例如同一份提交上切到另一条分支）、HEAD 换了或变得解析不出来、**索引内容标识换了**（条目数一点没变、
   只是暂存的内容或模式被外部工具换过，这种改动只有树 ID 看得见）、确认之后才开始的合并/变基等流程、
   确认时还没有的 `index.lock`、有效配置里的提交者身份换了人——任何一处对不上就不发命令，
   弹窗把对不上的地方逐个列出来，删除刚写的提交信息文件，**表单里的标题、描述、作者与合作者一个字都不动**，
   然后重读仓库现状，让你对着新的现状重新点一次“创建提交”、重新确认一遍。
   这一道能保证的边界也写在确认框里，不含糊成“事务”：它覆盖“你点下确定”到“程序创建那个进程”之间；
   再往后到 Git 自己读索引那一小段，归 Git 自己的 `index.lock` 管，本程序既不持那把锁也不等它；
   而 `prepare-commit-msg`、`pre-commit` 这类 hooks 本来就可以在你的授权下改动暂存内容，
   那种改动发生在复核之后。因此这是“确认的那一份与执行的那一份对得上”的复核，
   不是把外部并发写入或 hooks 一并锁死的隔离保证。

7. **拒绝在执行任何命令之前**。以下情形一律不弹命令窗口、不改动仓库，并把原因写进“任务状态”：
   没有暂存内容（同时说明不会代为暂存、不会用 `git commit -a`）；还有未解决的冲突条目（点名条目）；
   仓库里有没走完的特殊流程；提交者身份凑不出来；作者身份残缺或含控制字符；
   时间换算不出（或落在 Git 收不下的区间）；提交信息文件路径含双引号/控制字符（无法安全进 cmd）；
   第 5 条那一组事实没能问齐（超时、Git 没回答、回答的形状不对，都按“这份事实没读回来”拒绝，
   绝不退回用早前那一份继续），或问回来的与界面上显示的对不上（那种确认框会写成“一半旧的一半新的”
   拼出来的承诺，索性不给）。
   特殊流程的判定依据是 Git 自己留在**绝对 Git 目录**里的痕迹（`MERGE_HEAD`、`REVERT_HEAD`、
   `CHERRY_PICK_HEAD`、`BISECT_LOG`、`rebase-merge\`、`rebase-apply\`），只读地判断存在与否；
   那种状态下的提交与平常不是一件事（合并提交会带第二个父、变基中途的提交会推进待办清单），
   本程序当前不接手，也**绝不替你终止那种流程**（不 `--abort`、不 `--quit`、不 reset）。
   `index.lock` 存在时只在范围说明里提醒一次：锁由 Git 自己管，程序既不删也不等。

8. **命令形态与底线**。实际执行的是

   ```
   git commit --cleanup=verbatim -F <临时信息文件>
   ```

   * 正文一律走 UTF-8 临时文件，绝不拼进命令行（多行、引号、`%`、中文都不必再考虑 shell 展开）；
   * 不带 `-a`、不带任何路径参数：提交范围就是索引里那一份，未暂存的改动留在工作区；
   * `--cleanup=verbatim` 是实测后写死的：Git 对 `-F` 的默认清理是 `whitespace`（会收拢连续空行、
     去行尾空格），而 `commit.cleanup` 是用户自己的配置。把形态写进命令，才能保证 3.8 节承诺的
     “不润色用户的文字”不因配置或版本而变——实测正文里的 `# 开头的行` 在 `-F` 下不会被当注释删掉，
     但空行与行尾空格会被 `whitespace`/`default` 收拾；
   * **不加 `--no-verify`**：hooks 与签名设置照常生效，需要口令或签名交互时由命令窗口里的 Git 自己提问，
     程序不猜也不代答；
   * 信息文件的所有权随操作交给“在途操作”记录，只在拿到终态（Git 已退出，或根本没启动）之后删除；
     Git 可能还活着的结果未知场合宁留残档也不删，避免打断一次合法的提交。

9. **成功与失败各自收尾**。成功（退出码 0）后：清空标题、描述与合作者，**作者那一栏留着继续用**，
   两个时间回到此刻，底部说明交代清了什么、留了什么；紧随其后的自动重读把两个列表与 HEAD 更新到位。
   清空只针对**你确认并提交掉的那一份内容**：命令窗口里跑 Git 的那段时间你又在表单上打了新字，
   那几个栏位与“你改过时间”的记号都会保留下来，不会被一次成功的提交顺手抹掉。
   失败时表单一个字都不动（hook 拒绝、被 Git 判为冲突、路径问题等都是一样），
   命令窗口一直保留，用户可以直接改好再点一次。只有确认创建成功才清空——“窗口打开了”从来不是成功。
   退出码与 Git 的原始报错都写进“任务状态”，结论与重读后的仓库现状并排显示在同一行。

10. **测试**。`tests/commit_plan_tests.cpp` 用纯数据逐条断言拒绝条件、命令形态、环境覆盖清单
   （只有作者身份与两个时间四项）与确认文字的边界，另有两组分别核那层身份本身：
   `InterpretCommitIdentity` 对每一组查询回答怎么判读（`--quiet` 的“明确没有”算答复而不是失败、
   形状不对的对象 ID、超时/没跑起来/输出没读全、问错了工作区），
   以及 `DescribeCommitIdentityChange` 在确认之后能认出哪些变化（内容换了而条目数没换、
   同一 HEAD 上换分支、HEAD/仓库搬迁、流程后起、`index.lock` 后起、复核读不回时那句作废说明）；
   `tests/commit_date_tests.cpp` 用独立参考值核对历法换算与 `@<秒> <±hhmm>` 的每个拒绝分支；
   `tests/local_time_tests.cpp` 把偏移与 `GetDynamicTimeZoneInformation` 的 `Bias`、瞬间与系统精确
   UTC 时钟分别比对，并与系统的正向映射来回对照（不写死本机时区，换时区仍成立）；
   `tests/commit_plan_fixture_tests.cpp` 在真实临时仓库里把生产方案产出的参数与环境块直接交给
   `git.exe`，然后 `git cat-file commit HEAD` 读回提交对象核对：作者身份与 `1700000000 +0530`、
   提交者身份仍是配置身份而时间是另一个瞬间 `1700003600 -0700`、正文里的中文/行尾空格/连续空行/
   `#` 开头的行/缩进一字未改、合作者 trailer 只有一条在最末、只有已暂存的两条进入树而
   未暂存那条与未跟踪文件原样留在工作区、父提交只有一个，
   以及最关键的一条：提交落地后 `HEAD^{tree}` 逐字符等于确认框上那个索引内容标识——
   你点头时看到的那份索引内容，就是 Git 真正写进仓库的那一份。另有真实用例覆盖：
   `pre-commit` hook 以非 0 退出时 HEAD 不前进、索引分毫未动；真实冲突索引里 `write-tree` 问不出
   内容标识，预检当场失败且不产生任何参数与环境覆盖（`MERGE_HEAD` 同时被流程痕迹探测抓到）；
   `index.lock` 能被探测到而探测本身不删仓库里的任何文件；
   身份预检问回的每一项都与真实 Git 一致（工作区根/Git 目录/完整分支引用/尚无提交的 HEAD/
   配置里的提交者身份/流程痕迹），且除了那棵树以外不改变仓库状态；
   索引内容标识只跟着索引走——只改工作区不动它，暂存后条目数不变而内容换了就一定换，
   并且 Git 自己承认它是一个树对象；确认之后被人换分支（HEAD 没动）、被外部换掉暂存内容
   （条目数没动）、或起了合并时，复核都作废旧方案（顺带钉住真实 Git 的一条事实：索引与 HEAD
   不一致时它根本不让合并开始）；
   UTF-8 信息文件的字节形态（中文三字节、emoji 四字节）、结尾换行只补一个、两次写出互不覆盖、用完即删。

### 3.10 最近提交（只读 `git log`）与提交详情（`git show`）

界面中部第三栏“最近提交”展示从当前 HEAD 可达的历史。对应开发计划步骤 13。

1. **只读、挂在同一次刷新里**。后台工作区读取在 `git status` 成功后紧接着发一条只读
   `git log`（仅当 HEAD 可解析；尚无提交的仓库不发，那条命令在那种仓库里必然非 0 退出）：
   `-C <工作区根> --no-optional-locks --no-replace-objects -c log.showSignature=false
   log --no-decorate --format=%H%x00%an%x00%at%x00%s%x00%p -z -n 100`。
   `-z` 加 `%x00` 让字段与记录全部以 NUL 分隔，解析只按“每条五个字段”分组，
   绝不按空格/制表符拆列——中文、制表符、`%`、全角空格与几百字的长标题都原样回来，
   空标题（`--allow-empty-message` 的提交）也合法；`%H` 是完整对象 ID
   （SHA-1 40 位 / SHA-256 64 位，不硬编码长度），`%at` 是作者时间的 Unix 秒，
   界面按本机时区换算显示（含那一天实际生效的夏令时）；`%p` 数父提交识别合并提交。
   这一段与 `git status` 的成败**分开记录**：历史读取失败时两个文件列表照常落地，
   历史列单独显示归类原因，不会伪装成“没有提交”。同样要求**每条记录都以 NUL 收尾**：
   末尾缺那个 NUL（最后一条只回来半截标题或半截父提交列表）就整段作废，
   按“读取不完整”说明，而不是少列一条提交（完整度判定见第 3.5 节第 9 条）。
2. **最多 100 条，并明确说明**。不按 `--all` 无差别混合所有分支，也不一次读完大型仓库的全部历史；
   恰好返回满额时摘要注明“已达上限 100 条，更早的历史未读取”。本版本不做搜索与图形分支树。
3. **detached HEAD 照常可读**。读的是“从 HEAD 可达”，与是否挂在分支上无关。
4. **刷新保留选中**。历史列表与更改列表同一套就地更新：按完整对象 ID 记忆，
   刷新后仍存在的提交保持选中；创建提交/撤回之后随同一次刷新更新，被撤回的提交自然失去选中。
5. **双击某条提交：命令窗口里跑原生 `git show`**。先把双击的行号与刚读回的模型核对
   （行数一致、该行对象 ID 与模型一致），再用条目里保存的**完整对象 ID**构造
   `show --format=fuller --no-ext-diff --no-textconv --ignore-submodules=none --submodule=short <完整 ID>`：
   元数据（作者/提交者、两个时间与偏移）、正文与差异全部留在命令窗口里，结束后窗口保留、
   应用独立收到退出码。ID 不套在 `--` 之后（实测 `git show -- <id>` 会把 ID 当成路径、输出为空），
   安全的前提是执行前再校验一次“仅小写十六进制、24–64 位”；校验不过就弹说明、不开窗口。
   历史列是只读列表：本步骤不提供任何 checkout/reset/revert 入口，
   查看详情失败也绝不会把当前分支切到那条提交。
6. **测试**。`tests/commit_history_tests.cpp` 用桩输出断言参数约定、五字段分组、中文/制表符/
   空标题原样保留、合并提交识别、64 位 ID 合法、非法输出必须整体作废，以及
   `git show` 方案的参数与拒绝分支；`tests/commit_history_fixture_tests.cpp` 在真实临时仓库里
   核对顺序与字段、合并提交、刷新后新提交出现、detached HEAD 可读、超过 100 条按上限截断并注明，
   并把构造好的 `git show` 参数原样交给真实 `git.exe` 执行，核对输出含完整对象 ID 与正文。

### 3.11 撤回最近提交（带预期旧值的 `git update-ref`）

底部 `撤回最近提交` 按钮把**当前分支的最新一次提交**挪回它的第一父提交，语义上对应普通场景下的
`git reset --soft HEAD^`——但它不是 revert（不生成反向提交），更不是 hard reset（不丢弃任何改动）。
实际执行的是**带预期旧值的原子引用更新**，目标写的是**完整分支引用名**（`refs/heads/…`）而不是可变的
`HEAD`：确认之后即使 `HEAD` 换指到别的分支，被移动的也只还是你确认的那一个引用。
只移动分支引用：索引与工作区一个字节都不动，原提交的改动相对新 HEAD 表现为“已暂存的更改”。
按钮只针对最新提交，与历史列表选中了哪条无关。对应开发计划步骤 14。

1. **点击时重新读取，不吃列表旧账**。按下按钮后先在后台发起一轮只读预检
   （`symbolic-ref --quiet HEAD`、`rev-parse --verify --quiet HEAD`、
   `rev-list --parents -n 1 <原完整ID>`、`cat-file commit <原完整ID>`、
   `rev-parse --is-shallow-repository`、`cat-file -t --quiet <第一父完整ID>`、
   `log -1 --format=%s <原完整ID>`、`for-each-ref refs/remotes`（含 `--contains <原完整ID>`）与一次
   `git status --porcelain=v2 -z`，全部隐藏窗口、带 `--no-optional-locks` 与 `--no-replace-objects`，
   不弹命令窗口、不访问远端），加上 Git 目录里的流程痕迹探测（与提交同一来源），全部读回来后才摆出确认框；
   对象类查询绑的都是预检那一刻拿到的**完整对象 ID**，不再写 `HEAD`；
   界面原先显示的 HEAD 或暂存条目数与刚读回的不一致时，确认框第一句就说明以刚读回的为准。
2. **明确拒绝、不给强制通道的状态**：仓库（或当前分支）还没有任何提交；游离 HEAD（没有分支引用可挪）；
   分支引用名不合格（不是 `refs/heads/` 下的完整名字）；父关系两处证据对不上；要挪去的父提交对象
   本地读不到；merge / rebase / cherry-pick / revert / bisect 进行中；有未解决冲突条目；
   工作区/索引现状或发布状态没能读回来；分不清「真正的第一个提交」与「浅仓库历史边界」
   （两边都说没有父，可 `--is-shallow-repository` 没给出答案）时也不会去删除分支引用。
   这些是“结果无法保证”或 Git 自己就先不接受的状态
   ——“强制继续”不等于绕过 Git 拒绝执行的条件，因此那种场合只说明原因、不打开确认框、
   也不终止任何流程、不联网补全历史。
3. **浅仓库边界绝不当成“第一个提交”**。“这条提交有没有父”由两份互不相通的证据共同说话：
   `rev-list --parents` 给出的是 Git 的**历史视图**，浅仓库的历史边界会把有父的提交报成没有父；
   `cat-file commit` 读出的是**提交对象自己**记录的 `parent` 行，浅克隆仍保留完整对象，因此看得到被
   历史视图隐藏的父。两处不一致 → 判为浅边界，明确拒绝并说明需要你自己 `git fetch` / `--unshallow`
   补全历史（本程序不自动联网、不自动 unshallow）；两处都说没有父，**且**
   `rev-parse --is-shallow-repository` 明确回答 `false` 时，才认定它是真正的根提交。
   浅仓库里只要那个要挪去的父提交对象本地读得到，撤回照样允许，但会作为需要你明确确认的风险，
   并说明更早的历史不在本地。
4. **发布状态三态，绝不含混**。“这条提交是否已被远端包含”只拿本地已有的远端跟踪引用说话
   （不联网 fetch，界面上也这么说）：命中 → **已知已发布**（列出命中的引用）；
   查询成功但没有任何引用包含它 → **本地信息未发现已发布**（会补一句：引用可能过期，
   这不能证明它从未被推送）；查询失败或本地根本没有 `refs/remotes` → **无法判断**。
   已知已发布与无法判断都属于要用户明确确认的风险；领先/落后数量从不被用来断言是否发布。
5. **需要确认的风险走“强制撤回（仅本地）”**。除上面两类发布疑境外，合并提交（以第一父为目标并
   说明其余父提交的去向）与浅仓库也需确认。那种场合弹的是带专用按钮的风险框（TaskDialog；万一打不开则
   退回是/否并在正文点明对应关系）：`强制撤回（仅本地）` 与 `取消`。这个“强制”只是确认越过
   本程序的风险提示——执行的命令与普通撤回一字不差，绝不追加 `--hard`、绝不自动 force push、
   远端是否更新完全由用户之后自己决定。普通撤回（本地未发现已发布、干净或带改动的单父提交）
   则摆出同样的事实后以“确定撤回/取消”确认。
6. **已有改动一起保留，不承诺分成两堆**。索引与工作区不动，因此撤回后“已暂存的更改”里
   是原提交的改动与用户本来就暂存的改动**合在一起**的那一份（Git 不记录哪一行属于哪次提交，
   没法自动分开）；未暂存侧原样还在。这种撤回只移动分支引用、不碰索引，不会产生文本合并冲突
   ——确认框把这两件事如实说清，不吓唬也不隐瞒。
7. **仓库的第一个提交**没有 `HEAD^`，软撤回表达不了“回到尚无提交”。受控路径是
   `git update-ref -d <完整分支引用> <原完整ID>`：Git 只在引用确实还指向这个 ID 时才删除它（值不匹配
   即以非 0 拒绝），删除的只有那一个分支引用，索引与工作区照旧一字不动，撤回后全部原提交内容
   表现为已暂存的新增。**不创建空提交冒充撤回**；形态不支持时直接说明阻止原因，绝不退回破坏性命令。
   分支引用被删除后它自己的 reflog 是否还在由 Git 决定，因此这条路径**不承诺**任何 reflog 线索，
   可靠的找回依据只有原提交的完整对象 ID。
8. **点头之后、执行之前再核对一次 HEAD/分支**（两条毫秒级只读查询）。确认框是模态的，期间外部
   终端照样可能动了仓库：分支引用名或 HEAD 对不上就取消本次执行并刷新，绝不对着已经变了的目标执行旧方案。
   命令里带的预期旧值再由 Git 原子核对一次——“确认之后分支被别人推进”会让它直接拒绝。
   执行走命令窗口执行器：显示真实命令（`git update-ref …` 或 `git update-ref -d …`）与
   Git 输出，结束后窗口保留，应用独立拿到退出码并自动重读仓库；不以“窗口已打开”当作撤回成功。
   完整的符号引用事务需要 `git update-ref --stdin`，而命令窗口没有标准输入通道，因此“确认后复核与
   启动 Git 之间的极短窗口”本程序锁不住，确认框里如实写明这一点，不自称挡住了任意外部写入者。
9. **恢复线索随结果保留**。确认框、操作状态与撤回成功的结论里都带着**原提交完整对象 ID**，
   并写明找回方式 `git update-ref <完整分支引用> <原完整ID>`（根提交撤回后在“尚无提交”状态下同样可用，
   实测）；普通撤回带 `--create-reflog`，实测在 `core.logAllRefUpdates=false` 的仓库里照样留下了
   该分支的 reflog（`git reflog show <分支>`），根提交的删除路径则不承诺这条记录。
   本程序不自动恢复、不删除 reflog。
10. **测试**。`tests/undo_commit_plan_tests.cpp` 用桩回答断言查询参数形态、`--quiet` 的
    “明确没有”与“查询失败”的分别、短 ID 前缀比较不虚报变化、两份父证据与浅仓库状态的组合判定
    （真正根提交 / 浅边界 / 父对象读不到 / 不一致各自归类）、三态发布判据、每种拒绝条件，
    以及根提交/普通/合并/已发布各形态的命令构造与确认文字底线；
    `tests/undo_probe_fixture_tests.cpp` 在真实临时仓库里驱动生产预检与方案，把方案合成的命令
    原样交给真实 `git.exe` 执行：核对撤回前后 `git ls-files -s` 逐条不差、工作区文件字节不变、
    原提交改动与既有暂存一起留在索引、中文路径正常、`update-ref` 旧值不匹配时 Git 拒绝、
    按恢复线索可用 `update-ref <引用> <完整ID>` 整条找回；另覆盖 `depth=1` 与 `depth=2` 的真实浅克隆、
    合并提交取第一父、确认之后分支被别处推进或切换、两个分支指向同一提交时只动确认的那个引用，
    以及关闭 reflog 后 `--create-reflog` 仍留下记录；并自建**本地 bare 远端 fixture**
    （`git push` 上去制造“已知已发布”，未推送的新提交回落普通确认）——该 bare fixture 形态
    供后续 fetch/pull/push 步骤复用。

### 3.12 fetch（`git fetch --recurse-submodules=no <远端>`）

顶部 `fetch` 按钮向一个明确的远端抓取，**只更新远端跟踪引用**（`refs/remotes/…`）：
它不移动 HEAD、不改任何本地分支、不动索引与工作区，也不顺带 `pull`。对应开发计划步骤 15。

> **联网边界**：用户点击 `fetch` 按钮时访问**用户自己配置的远端**（含网络远端），
> 这是产品功能、属于用户操作，认证沿用用户已有的凭据助手/SSH agent/交互提示；
> 而**自动化测试绝不碰网络**——它们只在 `RemoteRig` 夹具自建的临时根内本地 bare 仓库上
> 跑同样的生产代码路径（见 2.1 的隔离规则与守卫）。两者共用同一套方案层与执行器，
> 差别只在「测试环境根本不放行网络形态的远端」。

1. **抓取目标只认两样东西**，此外一概不猜。按下按钮后先发起一轮只读预检
   （`symbolic-ref HEAD`、`branch.<分支名>.remote` 的有效配置、`git remote` 的既有远端清单，
   全部隐藏窗口、带 `--no-optional-locks`，不弹命令窗口、不接触任何远端）：
   当前分支**明确配置**了远端且它确实在清单里 → 目标直接确定，摆出确认框；
   否则（分支没配远端、配置指向已不存在的远端、游离 HEAD）把既有远端连同各自 fetch URL
   一个个摆进**远端选择界面**，选谁由用户点头。只有一个普通远端时也照实列为候选，
   默认选中它，但“点不点”仍在用户手里。
2. **一个远端也没有就明说**：拒绝执行、不猜 `origin`、不自动创建远端、不改动任何配置；
   查询失败或 `git remote` 回答不合约定时同样不在这上面猜目标。
3. **范围写死在命令里**：`git fetch --recurse-submodules=no <远端>`——`--recurse-submodules=no`
   显式关闭子模块递归，仓库配置里的 `submodule.recurse` 不会悄悄扩大这一步的范围；
   命令里没有 `--prune`（不隐式清理过期跟踪引用）、没有 `--all`（不一次抓所有远端）、
   没有 `pull`/`merge`。确认框把这几点逐条讲清，并写明目标来历（分支配置 / 刚选定）。
4. **真实执行留在命令窗口**：走与 `status` 同一个外部命令窗口执行器，需要口令或交互时由命令窗口里
   的 Git 自己提问，**沿用用户已有的认证方式**（凭据助手、SSH agent、交互式提示都在原生 `git.exe`
   那一侧，本程序不代管、也不写入任何凭据或配置）。结束后窗口保留，应用独立按 `result.txt`
   取回 Git 退出码——不以“窗口已打开”当作抓取成功。
5. **失败如实收场、不自动重试**：无远端、远端不可达、认证不过、用户在窗口里取消、命令非 0 退出，
   都按真实退出码给出结论并恢复按钮，绝不反复自动重试，也绝不删除或改写远端配置
   （“无效本地目标”那条用例专门核对：fetch 失败后 `remote.<name>.url` 原样还在）。
6. **抓取成功后重读**：结论里说明“只更新了远端跟踪引用”，随后自动刷新重读仓库摘要与上游；
   下一次点 `撤回最近提交` 的发布状态判断用的就是这批新读回的引用——同一条本地提交，
   fetch 前判“本地信息未发现已发布”，fetch 到确实包含它的远端引用后改判“已知已发布”
   （见 3.11 第 3 点，三态判据完全共用）。
7. **测试**。`tests/fetch_plan_tests.cpp` 用桩回答断言三条查询的参数形态、`git remote -v`
   的解析（fetch/push 行、纯名字行、中文与含空格 URL、只有 push 行退用其 URL）、
   `--quiet`/`config` 的“明确没有”与“查询失败”的分别，以及目标判定的四条规矩
   （配置命中即确定 / 没配置或配置对不上或游离 HEAD 一律列候选 / 一个也没有则拒绝且不猜 origin /
   查询失败不猜）、命令里绝不含 `--prune`/`--all`/`pull`、递归选项写死。
   `tests/fetch_fixture_tests.cpp` 在真实临时仓库里驱动生产预检与方案，把方案合成的命令原样交给
   真实 `git.exe`：B 推送新提交后 A 抓取——核对 `refs/remotes/origin/main` 确实前进，
   而 A 的 HEAD、`refs/heads/main`、`ls-files -s` 逐条不差、工作区 `status` 仍干净；
   抓取后同一条本地提交的发布状态从“未发现已发布”变“已知已发布”并回落强制确认；
   无远端仓库判 blocked 且 `git remote` 仍为空；指向根内不存在目录的“无效本地目标”以 Git 真实
   失败收场且 `remote.<name>.url` 不被删除；测试远端守卫拒绝 `http/https/ssh/git/file://`、
   scp 形态、UNC 与根外路径。三方形态（bare 远端 + A/B 两工作区）由 `RemoteRig` 夹具自动搭好。

### 3.13 pull（先 `git fetch`，再 `git merge` / `git rebase`）

顶部 `pull` 按钮把「把远端的更新拿到本地」拆成**两个可见阶段**，中间夹三轮只读预检。
对应开发计划步骤 16。为什么不是一条 `git pull`：那样网络操作与整合被捆在一起，
「预检看到的」和「实际整合的」可能不是同一份提交，也就没法在动手前把关系与风险讲清楚。

```
点 pull → 预检①（只读）→ 确认框「本地分支 ← 远端分支」
        → 命令窗口：git fetch --recurse-submodules=no <远端>     ← 阶段一「获取」
        → 预检②（只读，含关系与冲突预演）→ 需要时选策略 → 带风险清单的确认框
        → 预检③（只读，执行前复核）→ 命令窗口：git -c … merge|rebase … <完整ID>   ← 阶段二「整合」
        → 按退出码结案并自动刷新
```

1. **前提由 Git 的回答决定，猜不出来就拒绝**。预检①问的是
   `symbolic-ref --quiet HEAD`、`rev-parse --verify --quiet HEAD`、
   `for-each-ref --format=%(upstream:remotename)%(09)%(upstream)%(09)%(upstream:remoteref)`、
   四条策略配置（`branch.<分支>.rebase`、`pull.rebase`、`pull.ff`、`merge.ff`）、
   `git status --porcelain=v2 -z`，外加按 Git 目录里的档案判断的流程痕迹——全部隐藏窗口、
   带 `--no-optional-locks`，不弹命令窗口、不接触任何远端。以下情形给出**具体原因**并拒绝：
   不在分支上（游离 HEAD）、这个分支还没有任何提交、**没有明确上游**
   （`branch.<分支>.remote` / `.merge` 没配或只有半截）、有 merge/rebase/cherry-pick/revert/bisect
   还没走完、还有未解决的冲突条目、任何一条查询没读回可采信的回答。
   拒绝时不产生命令，也**不猜 `origin/main`、不代跑 `git branch --set-upstream-to`、
   不写任何配置文件**——那种状态本程序说不准，Git 自己也会先拒绝，加参数绕不过去。
2. **获取是网络操作，就让它留在命令窗口里**。确认后执行的是
   `git fetch --recurse-submodules=no <远端>`，与 `fetch` 按钮同一范围口径
   （不 `--all`、不 `--prune`、不递归子模块、不合并）；需要口令时由命令窗口里的 Git 自己提问。
   这一步**不藏在界面的“刷新”里**：刷新永远是本地只读查询。获取失败（非 0、被拒、认证不过）
   就停在这一步——不自动重试、不改配置，也不去做任何整合。
3. **关系判据用完整对象 ID，四种关系各说各话**。预检②先用
   `rev-list --left-right --count <HEAD 完整ID>…<跟踪引用完整ID>` 问出「本地独有 / 远端独有」几个提交，
   据此分为**已一致 / 可快进 / 本地领先 / 已分叉**；再问 `merge-base`、
   `diff --name-only -z <基准> <远端ID>`（这次会带进哪些路径）。已一致与本地领先都是
   `nothingToIntegrate`：一条命令也不给（本地领先属于 push 的范围，不是 pull 能解决的方向问题）。
   可快进的场合内容不可能冲突，**冲突预演根本不发起**；分叉时才做预演。
4. **内容冲突用不改动工作区/索引的能力预演**：`git merge-tree --write-tree --name-only <HEAD> <远端>`
   ——它只把结果 tree 写进对象库（不可达，`gc` 自行回收），引用、索引与工作区分毫不动；
   绝不在用户工作区里先真合一次再 `reset` 回去模拟 dry-run，也绝不自动 stash。
   退出码 0/1 分别是「预演无冲突 / 有冲突」，冲突文件名从输出里按约定取出；
   这个 Git 不认该子命令时（退出码 129/128）降级为**「没能预演，保守提醒」**并计入风险，
   不装作「没有冲突」。
5. **整合策略尊重已有配置，且预检与实际策略必须一致**。优先序照 Git 自己的规矩：
   `branch.<分支>.rebase` 覆盖 `pull.rebase`（`true`/`false`/`merges`），
   `pull.ff` 覆盖 `merge.ff`（`only`/`false`/默认）。确认框里写明这个结论是**哪条配置给的**。
   双方分叉而配置没定策略时，把「合并」「变基」两个候选摆出来由用户当场选（合并排第一，
   与本程序的默认倾向一致），选完还会再给一次带风险清单的确认——本程序从不写配置文件。
   因为实际执行的是 `git merge`（它看不见 `pull.ff`），配置里的快进意愿被**翻译成命令行上显式的
   `--ff-only` / `--no-ff`**：预检声称的形态与命令真正做的形态因此是同一件事。
   **变基这一路不做合并式预演**：重放是逐提交的，冲突可能出现在中间某一步，
   拿合并预演的结论去声称「变基不会冲突」是假话——确认框里明说这一点。
6. **命令形态把范围写死**（示例为已分叉选合并）：
   ```
   git -c submodule.recurse=false merge  --no-autostash --no-edit <远端提交完整ID>
   git -c submodule.recurse=false rebase --no-autostash            <远端提交完整ID>
   git -c submodule.recurse=false merge  --no-autostash --ff-only  <远端提交完整ID>   （可快进）
   ```
   `-c …` 与 `--no-autostash` 只对这一个子进程生效：不写配置，`autoStash` 类配置也不会
   把「替你 stash」这件事悄悄做掉，子模块不会被递归改动。目标用**完整对象 ID**而不是引用名——
   钉住「刚刚抓回来的那一份提交」，不让执行时再去看那个引用又停在哪儿。
   没有 `--no-verify`：pre-merge / commit-msg 等 hooks 与签名照常生效。
7. **风险清单与「不保证」**。`requiresForce` 的风险条目逐条给原因并点名受影响文件：
   预演报出的冲突文件、未提交改动与带入路径的重叠、未跟踪文件与远端带来的同名路径撞车、
   变基会重写本地这几个提交（ID 变化、已推送过就会与协作者分叉，本程序不自动 force push）、
   预演不可用、配置与当前关系相矛盾（如 `pull.ff=only` 而双方已分叉）。
   风险确认框的按钮是「按这份预检继续整合」与「取消」（TaskDialog，失败时退回是/否并注明等价），
   「继续」只越过本程序的风险提示，不追加任何更激烈的参数。确认文字末尾写明预检**不是保证**：
   点头之后远端可能又变、hooks 可能拒绝、外部程序可能改同一个仓库。
8. **点头之后还要再核对一次现状才动手**。预检③把预检①那套查询原样重发一遍，
   `DescribePullChange` 逐处比对：分支引用、HEAD、那条远端跟踪引用的位置、
   工作区/索引的**逐条**现状（按「哪一侧、哪个路径、什么状态字元」排序比对，不只数个数）、
   流程痕迹有无变化。任何一处对不上就放弃执行、给出「从什么变成什么」的原因并刷新——
   预检之后的远端又动了也一样：不把旧预检当保证，也不靠盲目重复 fetch 把这件事盖过去。
9. **失败与冲突保留现场**。整合非 0 退出时，界面读回现场并明确说明：
   还有没有 Git 流程在进行（`MERGE_HEAD`、`rebase-merge\` 等档案）、
   `git diff --name-only -z --diff-filter=U` 读回的未合并文件清单、分支与 HEAD 现在在哪；
   同时列出这些文件在“未暂存的更改”里以待解决状态出现。本程序**从不** `merge --abort` /
   `rebase --abort` / `reset` / `--continue`，也不替你选任何一方的内容——处理现场是用户的决定。
10. **取消时的边界**。取消获取：命令窗口不打开、远端不接触、仓库不动。
    取消整合（获取已经跑过）：本地分支、索引与工作区都不动，但**那次可见的 fetch 已经把
    远端跟踪引用更新到远端的位置，这一处改动保留**——本程序不把它退回去（那要改写引用），
    确认后的状态栏与取消说明都写清楚这一点。
11. **测试**。`tests/pull_plan_tests.cpp` 用桩回答断言查询参数形态、
    `--quiet`/`config` 的「明确没有」≠「查询失败」、上游三栏解析（含缺栏）、
    `rev-list` 四种关系、`merge-tree` 三种结局（0/1/129）、`-z` 清单里含空格与中文的路径原样可比、
    五种前提拒绝、命令形态与配置优先序、预演结论不得跨策略借用、风险清单点名文件、
    执行前复核的逐处比对。`tests/pull_probe_fixture_tests.cpp` 用 `RemoteRig`
    （bare 远端 + A/B 两个本地工作区，全程同根内本地路径、不放行任何网络形态）驱动
    **生产预检编排与生产方案层**，并把方案合成的命令原样交给真实 `git.exe` 执行，逐项断言：
    无上游拒绝且不写配置、已一致/本地领先不给命令、可快进只前移分支引用且命令钉在抓回来的完整 ID、
    无冲突分叉先问策略选合并后真的产生两个父的合并提交、文本冲突被预演点名而预检本身
    `HEAD/refs/heads/main/ls-files -s/status/MERGE_HEAD` 一字不动（真跑确实留下冲突现场，
    未合并清单读回同一份文件名；`merge --abort` 只是用例自己的收尾）、
    未提交改动重叠与未跟踪撞名都被点名且 Git 真的拒绝、本地那份内容一字未动、
    `pull.rebase=true` 时不问策略直接变基且历史是线性的（HEAD 只有一个父、父提交正是远端那份）、
    取消整合后只剩「跟踪引用前移」这一处遗留、外部改动让执行前复核报出原因。
    每个用例都核对夹具那份「用户层」配置档案跑完仍然是空的——整条链路从不写配置。

> **联网边界**与 3.12 同一口径：用户点 `pull` 时访问的是**用户自己配置的远端**，认证沿用其已有的
> 凭据助手/SSH agent/交互提示，本程序不代管凭据也不写入任何配置；自动化测试只在临时根内的
> 本地 bare 仓库上跑同一条生产代码路径，绝不接触网络。

### 3.14 推送（git push，只推当前分支这一条引用）

对应开发计划步骤 17。点 `推送` 后的路径是：后台只读预检 → 确认框（有风险时要求明确点「仍要推送」）
→ 执行前复核 → 命令窗口里真实的 `git push` → 终态后自动重读仓库 → 另向**发布目标**发只读
`git ls-remote` 核实。全程 GUI 不冻结，命令窗口保留输出，凭据由 Git 自己的认证方式处理。

1. **界面上必须看见三样东西**：源分支（`refs/heads/<分支>`，现在在哪一份提交）、目标远端
   （以及它**实际**的发布 URL）、目标分支（远端那一侧的完整引用名）。三者都取 Git 自己的回答：
   分支名来自 `symbolic-ref`，远端名与远端分支来自 `for-each-ref` 的
   `%(upstream:remotename)/%(upstream)/%(upstream:remoteref)`，本程序不改写、不缩写、不「就近取一个同名分支」。
2. **命令形态把范围钉死**（本机 Git 2.53 实测，测试里逐条钉住）：

   ```
   git [-c remote.<远端>.mirror=false] [-c remote.<远端>.tagopt=] -c push.followTags=false \
       push --recurse-submodules=no <远端> refs/heads/<分支>:refs/heads/<远端分支>
   ```

   完整两侧的显式 refspec 是关键：`push.default`（实测设成 `nothing` 也照推）、
   `remote.<远端>.push` 的额外 refspec、`push.followTags`、`remote.<远端>.tagOpt=--tags`
   在这种形态下都不会被附上，所以既不会多推分支，也不会顺带推标签。两句 `-c` 只为这一个子进程生效：
   `remote.<远端>.mirror=true` 实测会让「带 refspec 的 push」以 128 失败
   （`fatal: --mirror can't be combined with refspecs`），存在时才补上中和它；`tagopt` 同理。
   命令里**没有** `--force` / `--force-with-lease` / `--mirror` / `--all` / `--tags` / `--no-verify`，
   也没有 `--set-upstream`：非快进就让 Git 拒绝，pre-push hook、签名与认证提示照常生效。
3. **发布目标与抓取目标可能不是同一个地方**，这一点必须解析出来而不是猜。推送远端按 Git 自己的
   优先序裁定（`branch.<分支>.pushRemote` > `remote.pushDefault` > `branch.<分支>.remote`），
   裁定出的名字**显式**写进命令，于是那条优先序不再参与第二次。生效配置一次问回
   （`git config --list --null`，含 `include` 叠加与多值键顺序），随后用
   `git remote get-url --push <远端>` 让 Git 自己算出实际地址（`pushurl` 优先于 `url`，
   `url.*.insteadOf` / `pushInsteadOf` 的改写已经叠在里面）。下列情况一律进风险清单、要求明确点头，
   并在确认文字里逐个列出：独立 `pushurl`、**多个** `pushurl`（实测 `git push <远端>` 会推给每一个，
   这不是本程序扩大范围）、`insteadOf` 改写过、推送远端与上游所在远端不同。
   多个 `pushurl` 时 `get-url` 只回答第一个的改写结果，界面就说“按配置原样列出全部、
   推送后逐个目标去问实际位置”，不假装核得出来。
4. **前提不成立就拒绝，且不产生任何命令**：游离 HEAD（没有分支可推，不替它挑一个）、
   分支还没有提交、没有上游（不猜 `origin/<分支>`、不代设 upstream、不创建远端分支设置、
   不写任何配置文件，说明里给出该自己跑的那句命令）、上游配置只有远端没有分支记录、
   上游给出的远端引用不是 `refs/` 开头、裁定出的远端根本不在仓库的远端清单里（同时把既有远端列出来）、
   问不出一个可用的发布 URL。仓库里的 merge/rebase 流程**不**阻止推送：推送只送已有的提交，
   不碰索引与工作区，那种现场只作为一句如实的说明出现。
5. **本地对远端的了解只到上一次 fetch 为止**。确认文字里的「领先 N 个、落后 M 个」依据的是
   `refs/remotes/<远端>/<分支>`，并且明确标出这是抓取的那一侧；落后 ≥1 时预先说明
   这次会被 Git 以 non-fast-forward 拒绝（撤回已发布提交后正是这种场合），
   本程序不会为了让它“成功”而改用 `--force`。看起来已一致（不领先也不落后）时同样列为风险：
   仍然把命令发出去是为了向远端问个准话，而不是拿旧结论宣称成功。
   上游跟踪引用在本地还不存在时，说明「这次会在对端新建这条分支」并要求明确点头。
6. **点头之后、执行之前再核对一次**。`DescribePushChange` 逐处比对：当前分支引用、
   要推送的那一份提交、上游三件套、发布远端名、发布 URL 清单、会被中和的那些设置的有无可变。
   工作区/索引的改动**不在**比对范围——推送本来就不碰它们，点头之后你又改了一个没暂存的文件
   不该让一次合法的推送作废。任何一处对不上就放弃执行并刷新。
7. **命令窗口里看得见真实过程**：实际执行的命令行、Git 的原生输出、需要口令时由 Git 自己提问
   （沿用你已有的凭据助手/SSH agent/交互提示），结束后窗口保留，本程序独立取退出码并刷新。
   命令与展示里出现的都是远端**名字**而不是 URL；凡是要显示 URL 的地方（`pushurl`、`get-url`
   的回答、核实目标）一律先把内嵌的 `user:password@` 掩成 `***@`，凭据不进界面、不进状态栏。
8. **成功与否以发布目标的实况为准**。命令窗口报结束后，界面另发只读
   `git ls-remote -- <发布 URL> <远端引用>`（逐个目标、后台线程、GUI 不冻结），
   把「刚推出去的那一份完整 ID」与对端那条引用的位置对照，结论分四种：
   已核实 / 与预期不符 / 部分核实（有目标没问到）/ 未能核实。
   `Git 报告成功` 但核不上时明确写“不把它算成推送成功”；命令失败而核到对端已经到了那份提交时写
   “以实况为准”。**本地远端跟踪引用看起来一致不算证据**：实测推送到独立 `pushurl` 成功后，
   Git 照样把本地的 `refs/remotes/origin/*` 挪到了新位置，而抓取的那个仓库根本没收。
   这一步本身要联网，认证失败或超时只说明“这一处没能核实”，不据此断言推送失败，也不自动重试。
9. **失败保留现场**：非快进被拒、目标地址不存在、hook 拒绝、认证失败时，
   本地分支与远端都停在原位，本程序不重试、不改用更激烈的参数、不 reset、不改配置，
   命令窗口里留着 Git 的完整输出。
10. **测试**。`tests/push_plan_tests.cpp` 用桩断言查询与命令的参数形态（含“参数不合格就返回空数组”）、
    `config --list --null` 的单值/多值/大小写/空值判读与“认不出来就整份拒用”、
    发布远端优先序、六种前提拒绝、风险清单、URL 凭据掩码、执行前复核的逐处比对、
    核实判读的四种结论与措辞边界（命令报成功却没核上不得写成成功）。
    `tests/push_fixture_tests.cpp` 用 `RemoteRig`（bare 远端 + A/B 两个本地工作区）驱动
    **生产预检编排与生产方案层**，把方案合成的那条命令原样交给真实 `git.exe`，再直接读 bare
    自己的引用库（`--git-dir` + `rev-parse`，不经传输所以不会被 `insteadOf` 改写）核对，逐项断言：
    正常领先后对端真的到了那一份且本地跟踪引用跟着前移、本地另有分支与标签时对端一字不多、
    `remote.origin.push`+`tagOpt`+`push.followTags`+`push.default=current`+`mirror=true`
    全都进不去（并且先证明不带中和的裸命令确实被 Git 拒绝）、已是最新时 `Everything up-to-date`
    而对端未动、非快进被 Git 拒绝且命令里没有 `--force`、无上游拒绝且不写配置、
    游离 HEAD 与尚无提交都拒绝、独立 `pushurl` 的场合发布目标收到而抓取的 bare 没收、
    `insteadOf` 改写时按改写后的地址展示与核实、多个 `pushurl` 每个都收到、
    目标地址不存在时命令失败而核实环节只说“没能问到”、外部改分支让执行前复核报出原因、
    非 ASCII（中文与 `%&+#`）分支名的 refspec 原样送达。
    每个用例都核对夹具那份「用户层」配置档案跑完仍然是空的——整条链路从不写配置。

> **联网边界**与 3.12/3.13 同一口径：用户点 `推送` 时访问的是**用户自己配置的远端**，
> 认证沿用其已有的凭据助手/SSH agent/交互提示，本程序不代管凭据也不写入任何配置；
> 自动化测试只在临时根内的本地 bare 仓库上跑同一条生产代码路径（夹具环境写死
> `GIT_ALLOW_PROTOCOL=file`，任何网络形态的 URL 在发起连接前就被 Git 拒绝），绝不接触网络。
>
> **本版本的边界**：没有上游时只提供“自己先把上游设好”的说明，不代为设置，也不提供
> “选一个远端推上去”的选择框（`fetch` 才有那个选择界面）——推到一个没被上游配置指向的远端
> 等于替用户决定仓库的历史往哪长。分支管理（改名、删除、重命名远端、设置 upstream）、
> 强制推送、推送标签与推送多个分支都不在本程序的职责里。
