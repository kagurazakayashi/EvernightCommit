# EvernightCommit —— Windows 原生 Git 提交工具

EvernightCommit 是一款只面向 Windows 的 Git 图形界面工具，原生 Win32 + Common Controls
编写，不依赖任何跨平台 GUI 框架。窗口标题为“Git 提交工具”。

它的设计取向是**看得见、不越权**：你主动触发的每一次 Git 操作（暂存、取消暂存、提交、
撤回、`fetch`、`pull`、推送、`status`）都在一个新开的命令窗口里执行**真实的 git 命令**，
命令行与 Git 的原生输出全部保留供你翻看；而程序本身绝不替你改 Git 配置、绝不写你的
凭据、绝不代为强推或丢弃改动。

## 支持平台与前提

- **操作系统**：仅支持 Windows x64（Windows 10 及以上）。其他平台或非 x64 架构在构建
  配置阶段就会直接报错，程序也不提供 ARM64 版本。
- **Git 命令行工具**：必须外部安装（推荐 [Git for Windows](https://git-scm.com/download/win)），
  本程序不携带、不安装 Git。启动时会自动在 PATH 里寻找 `git.exe` 并后台验证；也可以手动
  粘贴路径或用“浏览…”指定。没有验证可用的 Git 时，仓库识别与所有 Git 操作都不会开始，
  “任务状态”行会说明原因。
- **VC 运行库**：默认构建动态链接 VC 运行库；在没有安装 Visual Studio 的机器上运行，
  需要安装 Microsoft Visual C++ Redistributable (x64)。以静态运行库方式构建的产物
  就这一点而言免部署（如何构建见 [docs/building.md](docs/building.md)）。
  注意：静态运行库不等于零系统依赖——程序仍需要 x64 版 Windows 10+ 和可用的 `git.exe`。
- **系统区域设置**：不需要。本程序的数据链路不使用系统 ANSI 代码页，中文用户名、
  中文或含空格和 `&` 的仓库路径、含 `%`/`!`/emoji 的文件名、中文窗口标题都可以正常
  工作。你不必为此修改用户名、搬移仓库，也不必开关 Windows 的“Beta: 使用 Unicode UTF-8
  提供全球语言支持”。

## 获取与启动

当前版本**只以源代码形式提供**：没有发布地址，也没有安装器和自动更新渠道。获得程序的
方式是构建后直接运行产物：

```powershell
cmake --preset vs2026-x64
cmake --build --preset vs2026-debug
.\build\vs2026-x64\bin\Debug\EvernightCommit.exe
```

只有 Visual Studio 2022 时改用 `vs2022-x64` / `vs2022-debug` 预设；Ninja 与其他构建
开关见 [docs/building.md](docs/building.md)。产物是单个 `EvernightCommit.exe`，双击
即可启动（GUI 程序，无需命令行参数）。

## 快速上手：第一次提交

1. 启动程序。“任务状态”行会报告自动发现的 `git.exe` 与版本号；如果没找到 Git，安装
   Git for Windows 或在“Git 程序”下拉框里指认路径。
2. 在“本地仓库”里输入仓库目录（或点“浏览…”）。停顿约半秒后程序在后台**只读**识别：
   仓库类型、当前分支、上游都会显示在第二行。选中仓库的子目录会自动上溯到工作区根。
3. 识别成功后，中部左侧列表显示“未暂存的更改”，中间列表显示“已暂存的更改”。读取全程
   不弹窗、不访问远端，也不会替你暂存或提交任何文件。
4. 在“未暂存的更改”里**选中**要提交的文件（可多选），点“加入暂存区 →”。会弹出一个
   命令窗口执行真实的 `git add`——只加入你选中的那些；一行都没选时什么都不做。
5. 在提交表单里填写标题与描述。作者默认取自本仓库的有效 Git 配置（只读地问出来，
   绝不回写）；可以改，只影响这一次提交。需要合作者就“添加”`姓名 <邮箱>` 条目。
6. 需要修改提交时间就用两个时间控件（默认就是点击那一刻的实际时刻与偏移）。
7. 点“创建提交”。程序先后台重读仓库现状，弹出确认框：里面写着**实际要执行的命令**、
   这次将提交的暂存条目、不会进入本次提交的未暂存条目、提交信息与两个身份和时间。
   点“确定”后它还会再原样核对一遍，对不上就作废重来；核对通过才在命令窗口里执行
   真实的 `git commit`。
8. 命令窗口的 Git 结束后（窗口保留，可以继续翻看输出），程序按 **Git 的退出码**给出
   结论并自动刷新。“最近提交”列表里就能看到你刚提交的那条；双击它会在命令窗口里跑
   `git show` 看完整详情。

## 界面一览

- **第一行**：`本地仓库` 路径与 `浏览…`；`Git 程序` 可编辑下拉框与 `浏览…`；仓库级
  操作 `fetch` / `pull` / `status`。
- **第二行**：仓库类型、当前分支、上游、任务状态说明与程序版本。仓库类型取 Git 自己的
  回答（普通工作区 / 链接工作树 / 子模块仓库 / 裸仓库 / 位于 `.git` 内部 / 不是仓库 /
  未能识别）；分支尚无提交时显示“尚无提交（分支名）”，游离 HEAD 时显示短提交 ID；
  没有跟踪分支时显示“未设置上游”，这不算识别失败。裸仓库与 `.git` 内部识别算成功，
  但没有可用工作区，不会进入提交流程。
- **中部三栏**：`未暂存的更改`、`已暂存的更改`、`最近提交`，两条可拖动的分隔条调整
  栏宽。两个更改列表列为“状态 / 相对路径”，支持多选；状态列显示“修改/删除/新增/
  重命名/复制/类型变化/未跟踪/冲突/子模块”，重命名显示“旧路径 → 新路径”；同一文件
  两侧都有改动时会**同时出现在左右两块列表**，互不覆盖。中间一列是 `加入暂存区 →`
  与 `← 移出暂存区`。
- **最近提交**：从当前 HEAD 可达的最近最多 100 条，列为“提交（短 ID）/标题/作者/时间”，
  时间按本机时区显示；满 100 条时注明更早的历史未读取。
- **提交表单**：标题、多行描述、作者、合作者列表、作者时间与提交者时间（显示该时刻
  实际生效的 UTC 偏移）、`时间同步修改` 与 `恢复当前时间`。
- **底部**：`刷新`（后台只读重读，不弹窗口）、`创建提交`、`撤回最近提交`、`推送`，
  以及**两条各自独立的说明栏**：上方“任务状态”讲仓库与操作结论，底部说明栏讲表单
  自己的校验与合作者增删，互不覆盖。
- 每个按钮都带工具提示：写操作会写明它实际执行什么命令、以及哪些事它绝不替你做
  （例如绝不 `--force`、绝不代设上游、绝不写配置文件）。

窗口初始 1100×780（按 DPI 缩放），可自由缩放；刷新会尽量保留你的多选与滚动位置。

## 典型操作与它们的边界

下面每一节讲“点这个按钮实际会发生什么”。更细的行为规格（确认框内容、拒绝条件、
命令形态与其实测依据）见 [docs/git-behavior.md](docs/git-behavior.md)。

### 暂存与取消暂存（注意：暂存不等于提交）

“加入暂存区”只把**选中的**条目交给命令窗口里真实的 `git add`；“← 移出暂存区”只把
选中的已暂存条目退回索引，**磁盘文件一个字节都不动**（有提交时是 `git restore --staged`，
仓库还没有任何提交时改用同样只写索引的 `git reset -q --`）。已暂存的修改被退回后，
条目回到“未暂存的更改”，你磁盘上的最新内容原样保留。程序绝不使用 `git reset --hard`、
`git checkout --`、`git clean` 这类会丢弃改动的命令，也绝不在失败时换破坏性后备。
取消暂存对重命名会新旧路径成对处理；未合并（冲突）条目会被拒绝并解释该走的正路；
文件名里的 `[ ] # ! %` 等特殊字符按字面处理，不会多暂存别的文件。

**提交的范围就是索引里那一份**：只暂存不提交什么都不会发生；未暂存的改动不会混进
本次提交（程序不用 `git commit -a`，也不带任何路径参数）。

### 创建提交（`git commit`）

见上文“快速上手”第 7—8 步。补充几条底线：正文里的中文、行尾空格、连续空行、
`#` 开头的行都**一字不改**地进提交（`--cleanup=verbatim`）；`pre-commit` 等 hooks 与
签名照常生效，需要口令时命令窗口里的 Git 自己提问；提交成功后只清空你确认并提交的
那部分内容，你在等待期间新打的字会保留；失败时表单一个字都不动。仓库里有没走完的
merge/rebase 等流程时会被拒绝——那种状态下的提交与平常不是一件事，程序不接手也不
替你中止。

### 撤回最近提交（软撤回，不是反向提交）

`撤回最近提交` 把当前分支的最新一次提交挪回它的父提交，语义对应普通场景下的
`git reset --soft HEAD^`。要分清三件事：

- 它**不是** `git revert`：不生成一条反向提交，历史直接退一格；
- 它**不是** hard reset：**不丢弃任何改动**——索引与工作区一个字节都不动，原提交的
  改动相对退回去的 HEAD 表现为“已暂存的更改”，与你本来就暂存的内容合在一起（Git 不
  记录哪一行属于哪次提交，没法自动分开）；
- 它只移动**一个完整的分支引用**（命令里带预期旧值，被别人推进过就直接拒绝），且
  只针对当前分支的最新提交，与你在历史列表里选中了哪条无关。

特殊形态的处理：仓库的**第一个提交**没有父提交可退，撤回走删除该分支引用的受控形态
（回到“尚无提交”，原内容全部变成已暂存的新增，不创建空提交冒充）；**浅克隆**的历史
边界会被识别出来并拒绝——那看起来像“没有父”，其实是更早的历史不在本地，需要你自己
`git fetch --unshallow` 补全后再操作（程序不自动联网补历史）。

如果这条提交已被远端包含（或无法判断），会弹带 `强制撤回（仅本地）` 按钮的风险确认框；
这个“强制”只是确认越过本程序的风险提示，执行的命令与普通撤回一字不差，绝不自动
force push——远端要不要跟着退，由你之后自己决定。可靠的找回依据是结论里保留的
**原提交完整对象 ID**（连同可用的找回命令一起写明）。

### fetch（抓取，不会改动你的工作）

`fetch` 向一个明确的远端抓取：**只更新**那个远端在 `refs/remotes/<远端>/` 之下的
远端跟踪引用（`.git/FETCH_HEAD` 与对象库会按 fetch 本身的行为变化——它不是磁盘只读
操作），**不移动 HEAD、不改本地分支与本地标签、不动索引与工作区，也不顺带 pull**。
这正是 `fetch` 与 `pull` 的区别：`pull` = 先 `fetch` 再把远端整合进你的分支（见下节）。
抓取目标要么来自当前分支明确配置的远端，要么由你在远端选择界面里点选；一个远端也没有
时直接拒绝，不猜 `origin`。删除过期跟踪引用、写本地标签、递归子模块这些会被 Git 配置
悄悄打开的行为，都会被显式中和；如果你的仓库把该远端的 fetch 映射配置到允许命名空间
之外（例如会直接写你的本地分支），程序在执行前拒绝并点名那一句配置。

### pull（先获取，再整合，两个阶段都看得见）

`pull` 拆成两条可见的命令：先在命令窗口里执行与 `fetch` 按钮**同一条**抓取命令，然后
后台只读判出本地与远端的关系（已一致 / 可快进 / 本地领先 / 已分叉），按 Git 的原生
规矩读你的 `pull.rebase` / `branch.<分支>.rebase` / `pull.ff` / `merge.ff` 配置定下
整合策略——配置没定而双方分叉时由你当场选（默认偏向合并）。可快进时就直接快进，
**不会替你产生多余的合并提交**；配置写着 `merges` 的变基会真的保留合并结构；Git 自己
都会拒绝的取值（如 `interactive`）会被明确拒绝并点名那条配置，不悄悄换成别的策略。
分叉时先用不碰工作区与索引的 `git merge-tree` 预演冲突并把风险逐条列出（注意：预演会
向对象库写入不可达的结果对象，不是“完全不写仓库”；本地领先时则什么都不做，那是
推送要解决的方向）。整合失败或留下冲突时，程序读回现场如实说明，**从不**替你
`--abort` / `--continue` / `reset`，也不替你选冲突内容。
没有明确上游的分支会被拒绝并给出该自己执行的设置命令——程序不猜 `origin/main`。

### 推送（`git push`：上游与发布目标可能不是一个地方）

`推送` 只推当前分支这一条引用，且命令里钉死的是**你确认那一刻的完整提交 ID**（不是
分支名）：点头之后分支被别人推进，执行前复核会作废旧方案。没有 `--force`、不推标签、
不动子模块、非快进就让 Git 拒绝。

确认框会先把三样东西摆清楚：源分支在哪份提交、**实际发布 URL**（逐条展开）、远端那一侧
的目标引用名。注意“上游”与“发布目标”是两回事：推送远端按 Git 自己的优先序裁定
（`branch.<分支>.pushRemote` > `remote.pushDefault` > `branch.<分支>.remote`），
`pushurl` 与 `insteadOf` 改写也由 Git 解析后原样列出——发布目标和你平时抓取的那个仓库
可能不同，多个发布地址时每个都会推。解析不出真实地址就拒绝发起，绝不拿未解析的配置
原文凑数。

命令结束后，程序还会向**同一批发布目标**逐个发只读 `git ls-remote` 核实那条引用到底
停在哪儿：结论分为“已核实 / 与预期不符 / 已推送但未核实 / 未能核实”，Git 报成功但
核不上时不算推送成功；本地跟踪引用跟着前移也不算证据。凭据沿用你自己的凭据助手/SSH
agent/交互提示（都在命令窗口里原生发生），界面与结论中所有 URL 的内嵌账号口令一律
掩码显示。

### 子模块：父仓库只记录“指针”

父仓库对子模块只有一条 gitlink 记录：暂存/提交子模块目录，记下的是“子模块指向哪个
提交”，**不包括子模块内部的文件**；子模块内部的改动要进入那个仓库另行暂存与提交。
程序绝不递归进入子模块暂存、提交或推送，列表里也不会出现 `子模块内/某文件` 这种条目。
读到子模块变化时，状态条与工具提示都会说明这条范围限制。

### 命令完成 ≠ 窗口关闭；失败 ≠ 结果未知

- 每个操作以 **Git 的退出码**结案（通过操作目录里的结果文件独立取回），**不等保留的
  命令窗口关闭**：窗口开着供你翻看输出时，界面已经可以发起下一项操作。“窗口打开了”
  从来不算成功。
- 终态是分开的几种：启动失败 / 执行完成（含退出码）/ Git 未能启动 / **结果未知**
  （窗口被提前关闭、辅助进程未能开始、超过观察期限）。“结果未知”绝不写成成功，也
  绝不自动重试；正在运行的 Git 不会被程序终止。
- **失败的操作同样可能已经改动了仓库**（提交到一半、`push` 被拒、合并留下冲突），
  所以无论成败都会自动重读一次，状态栏同时给出“刚才的操作怎么样”与“仓库现在怎么样”。
  外部终端里改的仓库，点 `刷新` 即可回到 Git 的真实状态。

## 出错了怎么办

| 现象 | 含义 | 你可以做什么 |
| --- | --- | --- |
| “Git 程序”报找不到 / 验证失败 | PATH 里没有可用的 `git.exe`，或指定的文件不是 Git | 安装 Git for Windows；或在下拉框键入/浏览选择正确的 `git.exe`，改正后自动重新验证，无需重启 |
| 识别报 `safe.directory` 拦截 | Git 的目录所有权安全检查拒绝该仓库 | 按 Git 自己的提示，由你在终端里把它加入你自己的 `safe.directory`（程序绝不代改配置） |
| 提示 `index.lock` 已存在 | 另一个 Git 进程（编辑器、命令行）正持有索引锁 | 等那个操作结束或让它自然消失，然后点 `刷新`；程序绝不删锁 |
| 因 merge / rebase / cherry-pick 未走完而拒绝 | 仓库处于特殊流程中，那种状态下的提交/整合与平常不是一件事 | 自己完成或明确中止那个流程（`git merge --continue/--abort`、`git rebase --continue/--abort` 等），程序不代为决定 |
| `pull`/`推送` 报“没有明确上游” | 该分支没配置 `branch.<名>.remote` / `.merge` | 在终端里自己设好上游（如 `git branch --set-upstream-to=origin/<分支>`），程序不猜也不代设 |
| 推送被拒（non-fast-forward） | 远端有你本地没有的提交 | 先 `fetch`/`pull` 整合远端更新再推；程序不会为“让它成功”而强推。确需强推时自己在命令行做并自负后果 |
| 推送结论“已推送但未核实 / 与预期不符” | 命令终态已收到，但对端实际位置没问到或对不上 | 按确认框列出的发布地址自己核实（访问远端仓库或 `git ls-remote`），不要当作成功；程序不自动重试 |
| “Git 输出读取不完整” | 仓库过大、输出超出保留上限、或遇到非法编码字节 | 重新点 `刷新`；持续出现时在终端里核对 `git status`。程序宁可拒读也不给你半份列表 |
| fetch 被点名配置拒绝 | 仓库把该远端的 fetch 映射写到允许命名空间之外（会动本地分支/标签） | 核对 `remote.<名>.fetch` 配置；不想改配置的仓库请改用命令行 fetch |
| 命令窗口打不开 / 中文显示乱码 | 未验证过的系统代码页形态或环境差异 | 反馈时附上状态栏原文与操作目录里 `spec.txt` 的内容（目录路径在状态栏提示里），以便定位环节 |
| 不确定一次操作是否生效 | —— | 点 `刷新`；两个列表、分支行与“最近提交”都会按 Git 的当前回答重摆 |

## 已知限制

- **无发布渠道**：没有安装器、自动更新与发布地址；只能从源码构建。
- **不做配置持久化**：Git 路径、仓库路径、列表选择等都不落盘，每次启动从头来。
- **提交历史只读且限量**：从当前 HEAD 可达的最近 100 条；没有搜索、没有图形分支树、
  没有 checkout / reset / revert 入口（双击只能 `git show` 看详情）。
- **撤回只针对当前分支的最新提交**；没有 stash 功能；没有冲突解决编辑器（冲突会如实
  列出，处理靠你自己）。
- **推送边界**：不代设上游、不强制推送、不推标签、一次只推一条引用；没有“选一个远端
  推上去”的入口（`fetch` 才有远端选择）。分支管理（改名、删除、重命名远端、设置
  upstream）都不在本程序职责里。
- **fetch 范围**：只服务“跟踪引用落在 `refs/remotes/<远端>/` 之下”的常规仓库形态；
  映射特殊（单分支过滤可以，跨命名空间会被拒绝）的仓库请改用命令行。
- **以下环境形态未在实机上验证**（判定链路已不依赖它们，但缺真机核验，如实声明）：
  传统代码页（GBK 936 / 西文 1252、437）的机器、未安装 VC 运行库的干净机器、更旧
  版本的 Git（程序对版本差异有声明的退回路径，但只在较近的 Git for Windows 版本上
  实测过）、组策略禁用 `cmd.exe` 的机器、真实超大仓库（16 MiB 输出上限端到端）。
