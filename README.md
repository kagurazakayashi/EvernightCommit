# EvernightCommit —— Windows 原生 Git 提交工具

EvernightCommit 是一款只面向 Windows 的 Git 图形界面工具，原生 Win32 + Common Controls
编写，不依赖任何跨平台 GUI 框架。窗口标题为“Git 提交工具”。

它的设计取向是**看得见、不越权**：你主动触发的每一次 Git 操作（暂存、取消暂存、提交、
撤回、`fetch`、`pull`、推送、`status`）都在一个新开的命令窗口里执行**真实的 git 命令**，
命令行与 Git 的原生输出全部保留供你翻看；程序默认绝不替你改 Git 配置、绝不写你的
凭据、绝不代为强推或丢弃改动。唯一的例外由你亲手开启：分支还没有上游时，「首次推送」
向导会让你当场选目标，并**在你明确选择「推送成功后设置上游」时**才写入确认框上逐条列出的
那两把本地上游配置键（见下面「推送」一节）；不选就一个配置都不写，中途某一步失败也只写到
已经成功的那一条为止。

## 支持平台与前提

- **操作系统**：仅支持 Windows x64（Windows 10 及以上）。其他平台或非 x64 架构在构建
  配置阶段就会直接报错，程序也不提供 ARM64 版本。
- **Git 命令行工具**：必须外部安装（推荐 [Git for Windows](https://git-scm.com/download/win)），
  本程序不携带、不安装 Git。启动时会自动在 PATH 里寻找 `git.exe` 并后台验证；也可以手动
  粘贴路径或用“浏览…”指定。机器上装着好几个 `git.exe` 时，下拉列表按来源排档：
  `…\Git\cmd\git.exe` 这类命令行入口在最前，也就是默认选中的那一个；MSYS2 或 `…\usr\bin`
  下依赖 msys 运行时的那一套排在列表末尾（仍可选用，只是不抢默认）；其余形态居中。
  同一档内保持 PATH 的书写顺序。没有验证可用的 Git 时，仓库识别与所有 Git 操作都不会开始，
  “任务状态”行会说明原因。
- **VC 运行库**：默认构建动态链接 VC 运行库；在没有安装 Visual Studio 的机器上运行，
  需要安装 Microsoft Visual C++ Redistributable (x64)。以静态运行库方式构建的产物
  就这一点而言免部署（如何构建见 [docs/building.md](docs/building.md)）。
  注意：静态运行库不等于零系统依赖——程序仍需要 x64 版 Windows 10+ 和可用的 `git.exe`。
- **系统区域设置**：不需要。本程序的数据链路不使用系统 ANSI 代码页，中文用户名、
  中文或含空格和 `&` 的仓库路径、含 `%`/`!`/emoji 的文件名、中文窗口标题都可以正常
  工作。你不必为此修改用户名、搬移仓库，也不必开关 Windows 的“Beta: 使用 Unicode UTF-8
  提供全球语言支持”。

## 获取与启动

当前版本**只以源代码形式提供**：没有发布地址，也没有安装器和自动更新渠道。获得程序的
方式是构建后直接运行产物：

```powershell
cmake --preset vs2026-x64
cmake --build --preset vs2026-debug
.\build\vs2026-x64\bin\Debug\EvernightCommit.exe
```

只有 Visual Studio 2022 时改用 `vs2022-x64` / `vs2022-debug` 预设；Ninja 与其他构建
开关见 [docs/building.md](docs/building.md)。产物是单个 `EvernightCommit.exe`，双击
即可启动（GUI 程序，无需命令行参数）。

## 快速上手：第一次提交

1. 启动程序。“任务状态”行会报告自动发现的 `git.exe` 与版本号；如果没找到 Git，安装
   Git for Windows 或在“Git 程序”下拉框里指认路径。
2. 在“本地仓库”里输入仓库目录（或点“浏览…”）。停顿约半秒后程序在后台**只读**识别：
   仓库类型、当前分支、上游都会显示在第二行。选中仓库的子目录会自动上溯到工作区根。
3. 识别成功后，中部左侧列表显示“未暂存的更改”，中间列表显示“已暂存的更改”。读取全程
   不弹窗、不访问远端，也不会替你暂存或提交任何文件。
4. 在“未暂存的更改”里**选中**要提交的文件（可多选），点“加入暂存区 →”。会弹出一个
   命令窗口执行真实的 `git add`——只加入你选中的那些；一行都没选时什么都不做。
5. 在提交表单里填写标题与描述。作者默认取自本仓库的有效 Git 配置（只读地问出来，
   绝不回写）；可以改，只影响这一次提交。需要合作者就“添加”`姓名 <邮箱>` 条目。
6. 需要修改提交时间就用两个时间控件（默认就是点击那一刻的实际时刻与偏移）。
7. 点“创建提交”。程序先后台重读仓库现状，弹出确认框：里面写着**实际要执行的命令**、
   这次将提交的暂存条目、不会进入本次提交的未暂存条目、提交信息与两个身份和时间。
   点“确定”后它还会再原样核对一遍，对不上就作废重来；核对通过才在命令窗口里执行
   真实的 `git commit`。
8. 命令窗口的 Git 结束后（窗口保留，可以继续翻看输出），程序按 **Git 的退出码**给出
   结论并自动刷新。“最近提交”列表里就能看到你刚提交的那条；双击它会在命令窗口里跑
   `git show` 看完整详情。

## 界面一览

- **第一行**：`本地仓库` 路径与 `浏览…`；`Git 程序` 可编辑下拉框与 `浏览…`；仓库级
  操作 `fetch` / `pull` / `status`。
- **第二行**：仓库类型、当前分支、上游、任务状态说明与程序版本。仓库类型取 Git 自己的
  回答（普通工作区 / 链接工作树 / 子模块仓库 / 裸仓库 / 位于 `.git` 内部 / 不是仓库 /
  未能识别）；分支尚无提交时显示“尚无提交（分支名）”，游离 HEAD 时显示短提交 ID；
  没有跟踪分支时显示“未设置上游”，这不算识别失败。裸仓库与 `.git` 内部识别算成功，
  但没有可用工作区，不会进入提交流程。
- **中部三栏**：`未暂存的更改`、`已暂存的更改`、`最近提交`，两条可拖动的分隔条调整
  栏宽。两个更改列表列为“状态 / 相对路径”，支持多选；状态列显示“修改/删除/新增/
  重命名/复制/类型变化/未跟踪/冲突/子模块”，重命名显示“旧路径 → 新路径”；同一文件
  两侧都有改动时会**同时出现在左右两块列表**，互不覆盖。中间一列是 `加入暂存区 →`
  与 `← 移出暂存区`。
- **最近提交**：从当前 HEAD 可达的最近最多 100 条，列为“提交（短 ID）/标题/作者/时间”，
  时间按本机时区显示；满 100 条时注明更早的历史未读取。
- **空闲时界面不动**：没有 Git 操作在进行时，程序不做任何周期性重画——文本没变就不重设，
  格子没动就不重摆，因此不会出现「什么都没做却一块块矩形在闪」，正在展开的下拉列表也不会
  被自己收回去。轮询只在一个命令窗口操作真正跑起来的那几分钟内存在。
- **提交表单**：标题、多行描述、作者、合作者列表、作者时间与提交者时间（显示该时刻
  实际生效的 UTC 偏移）、`时间同步修改` 与 `恢复当前时间`。
- **中间那一栏的四个按钮**：`加入暂存区 →`、`← 移出暂存区`，以及子模块导航的
  `进入子模块`、`返回父仓库`（只对相关的场合有效，点了不合规会得到一句具体说明）。
- **底部**：`刷新`（后台只读重读，不弹窗口）、`创建提交`、`撤回最近提交`、`推送`，
  以及冲突与暂停流程的三个入口 `查看冲突状态`、`继续该流程`、`中止该流程`；
  再配上**两条各自独立的说明栏**：上方“任务状态”讲仓库与操作结论，底部说明栏讲表单
  自己的校验与合作者增删，互不覆盖。后两个入口不靠“灰掉”来表达“现在没有流程”，
  点下去会得到一句依据实据的说明（没有流程时不会生成任何中止命令）。
- **右下角的记录开关**：`保存记录`（总开关）与 `保存草稿` 两个复选框、`清除已存记录`
  按钮，以及 `记录操作历史` 复选框与 `操作历史…` 按钮。这些都不碰仓库、不需要 Git 可用，
  任何时候可点；详见下面「使用记录与提交草稿的保存」与「操作历史与恢复入口」两节。
- 每个按钮都带工具提示：写操作会写明它实际执行什么命令、以及哪些事它绝不替你做
  （例如绝不 `--force`、绝不在你没点头的情况下写配置文件；唯一的例外是你在
  「首次推送」里明确选了「设置上游」，那时写哪两把键、写成什么值都会先摆给你确认）。

窗口初始 1100×780（按 DPI 缩放），可自由缩放；刷新会尽量保留你的多选与滚动位置。

## 典型操作与它们的边界

下面每一节讲“点这个按钮实际会发生什么”。更细的行为规格（确认框内容、拒绝条件、
命令形态与其实测依据）见 [docs/git-behavior.md](docs/git-behavior.md)。

### 暂存与取消暂存（注意：暂存不等于提交）

“加入暂存区”只把**选中的**条目交给命令窗口里真实的 `git add`；“← 移出暂存区”只把
选中的已暂存条目退回索引，**磁盘文件一个字节都不动**（有提交时是 `git restore --staged`，
仓库还没有任何提交时改用同样只写索引的 `git reset -q --`）。已暂存的修改被退回后，
条目回到“未暂存的更改”，你磁盘上的最新内容原样保留。程序绝不使用 `git reset --hard`、
`git checkout --`、`git clean` 这类会丢弃改动的命令，也绝不在失败时换破坏性后备。
取消暂存对重命名会新旧路径成对处理；未合并（冲突）条目会被拒绝并解释该走的正路；
文件名里的 `[ ] # ! %` 等特殊字符按字面处理，不会多暂存别的文件。

**提交的范围就是索引里那一份**：只暂存不提交什么都不会发生；未暂存的改动不会混进
本次提交（程序不用 `git commit -a`，也不带任何路径参数）。

### 创建提交（`git commit`）

见上文“快速上手”第 7—8 步。补充几条底线：正文里的中文、行尾空格、连续空行、
`#` 开头的行都**一字不改**地进提交（`--cleanup=verbatim`）；`pre-commit` 等 hooks 与
签名照常生效，需要口令时命令窗口里的 Git 自己提问；提交成功后只清空你确认并提交的
那部分内容，你在等待期间新打的字会保留；失败时表单一个字都不动。仓库里有没走完的
merge/rebase 等流程时会被拒绝——那种状态下的提交与平常不是一件事，程序不接手也不
替你中止。

### 撤回最近提交（软撤回，不是反向提交）

`撤回最近提交` 把当前分支的最新一次提交挪回它的父提交，语义对应普通场景下的
`git reset --soft HEAD^`。要分清三件事：

- 它**不是** `git revert`：不生成一条反向提交，历史直接退一格；
- 它**不是** hard reset：**不丢弃任何改动**——索引与工作区一个字节都不动，原提交的
  改动相对退回去的 HEAD 表现为“已暂存的更改”，与你本来就暂存的内容合在一起（Git 不
  记录哪一行属于哪次提交，没法自动分开）；
- 它只移动**一个完整的分支引用**（命令是 `git update-ref --no-deref` 并带预期旧值：被别人
  推进过就直接拒绝；`--no-deref` 让它绝不追随符号引用去改另一条分支），且
  只针对当前分支的最新提交，与你在历史列表里选中了哪条无关。

特殊形态的处理：仓库的**第一个提交**没有父提交可退，撤回走删除该分支引用的受控形态
（回到“尚无提交”，原内容全部变成已暂存的新增，不创建空提交冒充）；**浅克隆**的历史
边界会被识别出来并拒绝——那看起来像“没有父”，其实是更早的历史不在本地，需要你自己
`git fetch --unshallow` 补全后再操作（程序不自动联网补历史）。另外两种形态也会被明确
拒绝，因为它们都不是“挪一条本地分支”：当前分支引用**本身**是一条符号引用（它指向另一条
分支），以及这条分支**正被另一个 `git worktree` 检出**（挪它等于隔空改动那个工作树的落点）；
这两条问不回来时同样不放行——“没问到”不等于“没问题”。

如果这条提交已被远端包含（或无法判断），会弹带 `强制撤回（仅本地）` 按钮的风险确认框；
这个“强制”只是确认越过本程序的风险提示，执行的命令与普通撤回一字不差，绝不自动
force push——远端要不要跟着退，由你之后自己决定。可靠的找回依据是结论里保留的
**原提交完整对象 ID**，结论同时给出找回这一步的三种表示：界面上执行的参数、逐段列出的
字段清单，以及按目标 shell 真实规则编排的可粘贴一行（分支名含该 shell 无法可靠表达的
字符时不提供粘贴行，只给字段清单并说明原因——不静默替换任何字符）。

### fetch（抓取，不会改动你的工作）

`fetch` 向一个明确的远端抓取：**只更新**那个远端在 `refs/remotes/<远端>/` 之下的
远端跟踪引用（`.git/FETCH_HEAD` 与对象库会按 fetch 本身的行为变化——它不是磁盘只读
操作），**不移动 HEAD、不改本地分支与本地标签、不动索引与工作区，也不顺带 pull**。
这正是 `fetch` 与 `pull` 的区别：`pull` = 先 `fetch` 再把远端整合进你的分支（见下节）。
抓取目标要么来自当前分支明确配置的远端，要么由你在远端选择界面里点选；一个远端也没有
时直接拒绝，不猜 `origin`。删除过期跟踪引用、写本地标签、递归子模块这些会被 Git 配置
悄悄打开的行为，都会被显式中和；如果你的仓库把该远端的 fetch 映射配置到允许命名空间
之外（例如会直接写你的本地分支），程序在执行前拒绝并点名那一句配置。

### pull（先获取，再整合，两个阶段都看得见）

`pull` 拆成两条可见的命令：先在命令窗口里执行与 `fetch` 按钮**同一条**抓取命令，然后
后台只读判出本地与远端的关系（已一致 / 可快进 / 本地领先 / 已分叉），按 Git 的原生
规矩读你的 `pull.rebase` / `branch.<分支>.rebase` / `pull.ff` / `merge.ff` 配置定下
整合策略——配置没定而双方分叉时由你当场选（默认偏向合并）。可快进时就直接快进，
**不会替你产生多余的合并提交**；配置写着 `merges` 的变基会真的保留合并结构；Git 会直接
死在那种取值上的配置（以及读不全、认不出的形态）会被明确拒绝并点名那条配置，不悄悄换成
别的策略。
说清是谁在拒绝：`pull.rebase=interactive`（以及 `i`）是 Git 自己支持的写法，它会起一个
交互式编辑器让你逐条改历史；本程序不给你开编辑器，也不猜你要不要编辑，所以在这种取值下
**由本程序**拒绝这次 pull（换成别的策略是不会替你做的）。想走交互式变基，请在终端里自己跑。
分叉时先用不碰工作区与索引的 `git merge-tree` 预演冲突并把风险逐条列出（注意：预演会
向对象库写入不可达的结果对象，不是“完全不写仓库”；本地领先时则什么都不做，那是
推送要解决的方向）。整合失败或留下冲突时，程序读回现场如实说明，`pull` 自己不替你
`--abort` / `--continue` / `reset`，也不替你选冲突内容；要看清或收尾那个已经停着的流程，
用的是下面「冲突与暂停流程」那三个按钮，每一步都要你亲手确认。
没有明确上游的分支会被拒绝并给出该自己执行的设置命令——程序不猜 `origin/main`。

### 推送（`git push`：上游与发布目标可能不是一个地方）

`推送` 只推当前分支这一条引用，且命令里钉死的是**你确认那一刻的完整提交 ID**（不是
分支名）：点头之后分支被别人推进，执行前复核会作废旧方案。没有 `--force`、不推标签、
不动子模块、非快进就让 Git 拒绝。

确认框会先把三样东西摆清楚：源分支在哪份提交、**实际发布 URL**（逐条展开）、远端那一侧
的目标引用名。注意“上游”与“发布目标”是两回事：推送远端按 Git 自己的优先序裁定
（`branch.<分支>.pushRemote` > `remote.pushDefault` > `branch.<分支>.remote`），
`pushurl` 与 `insteadOf` 改写也由 Git 解析后原样列出——发布目标和你平时抓取的那个仓库
可能不同，多个发布地址时每个都会推。解析不出真实地址就拒绝发起，绝不拿未解析的配置
原文凑数。

命令结束后，程序还会向**同一批发布目标**逐个发只读 `git ls-remote` 核实那条引用到底
停在哪儿：结论分为“已核实 / 与预期不符 / 已推送但未核实 / 未能核实”，Git 报成功但
核不上时不算推送成功；本地跟踪引用跟着前移也不算证据。凭据沿用你自己的凭据助手/SSH
agent/交互提示（都在命令窗口里原生发生），界面与结论中所有 URL 的内嵌账号口令一律
掩码显示。

**这条分支还没有上游时**（`branch.<分支>.remote` / `.merge` 都没配），而仓库里有配好
地址的远端，`推送` 会改走“首次推送”：先逐个远端问出 Git 自己展开的实际发布地址（本地
只读），再让你**当场选**目标远端、输入目标分支名（建议值是当前分支名，但绝不替你按下
确定），并决定要不要顺手设置上游。目标分支名交给 `git check-ref-format` 裁定，Git 说
不能用就直接拒绝，程序不改写它、不凑一个看起来对的。选定之后程序会向每个发布地址只读
问一次“那条引用在不在、停在哪”——这一步**会访问远端**（只读，不改任何一边）：

- 对端还没有那条引用：这次会在对端新建它。
- 对端已经有那条引用：明确列成风险要你点头。“首次推送”不是覆盖它的理由——命令里
  永远没有 `--force`，非快进时由 Git 自己拒绝，程序不重试、不加码，也不先替你抓取整合。
- 问不到（认证失败、没权限、网络不通）：措辞是“没能问清对端有没有”，绝不写成
  “对端没有”。这不构成拒绝理由，也不构成放行保证。

“推送”与“设置上游”是**两步、各有结果**：上游那两步是两条各自在命令窗口里跑的
`git config`（`branch.<分支>.remote = <你选的远端>`、`branch.<分支>.merge = <目标引用>`），
只在推送那一步报告成功之后才发，逐条报告成败；没写成就停下并说清写到第几条，
不自动重发、不自动回退。确认框里还写着配置文件落点（由 `git rev-parse --git-path config`
当场问回）。程序不用 `git push -u`：那种写法把“远端收到没有”和“本地配置写成没有”
揉进同一条命令，两个结果就分不开报告了。两条配置在发出之前还会再核一次前提——这条分支
还在、没换成别的分支、上游仍然没配：已经被设好且与要写的值相同就说“无需再写”，值不同就
拒绝覆盖，问不回来一律停手，绝不带着过期的前提去改配置。那时候推送本身的结果仍按它自己的
结论与核实说话，程序既不回退推送，也不把只写了一半的配置说成“上游已经设好”。

取消其中任何一步：那一步之后的事情不会再做——尚未执行的配置写入一条都不写，也不会自动
重推或自动回退已经做成的事。但要说清边界：**取消只能阻止还没执行的步骤**，已经完成的
推送、以及首次推送预检里那次联网的 `git ls-remote`（问对端有没有这条引用）都收不回来；
预检阶段本身就可能在联网，不是「点了以后才接触远端」。

### 子模块：父仓库只记录“指针”

父仓库对子模块只有一条 gitlink 记录：暂存/提交子模块目录，记下的是“子模块指向哪个
提交”，**不包括子模块内部的文件**；子模块内部的改动要进入那个仓库另行暂存与提交。
程序绝不递归进入子模块暂存、提交或推送，列表里也不会出现 `子模块内/某文件` 这种条目。
读到子模块变化时，状态条与工具提示都会说明这条范围限制。

#### 进入子模块工作，再回来更新父仓库的指针

列表里状态列写着「子模块」的那一条，可以点 `进入子模块`：界面绑定的仓库换成**那个子模块
自己的工作区**，状态、最近提交、分支与上游、作者默认值、提交表单全部按它自己读；改完点
`返回父仓库` 回到刚才那个父仓库（嵌套子模块就一层一层退）。

点下去之前先在后台只读核对三件事，任何一条不过就明确拒绝并说明是哪一条：

- 那个目录在不在（被移走、被删掉是一种；同名的是文件不是目录又是一种）；
- Git 认不认它是**当前这个**父仓库登记的子模块（`--show-superproject-working-tree` 答的
  必须是现在这个父仓库）——独立 clone 来的同名仓库、被移动过的仓库都进不去；
- 父索引里那条记录真的是 `160000` gitlink（界面显示与索引事实不是同一件事时拒绝）。

**还没有初始化的子模块进不去**：那种目录里没有 `.git`，Git 从它往上找到的是父仓库本身。
初始化/更新要联网并改动工作区，绝不在点导航时隐式触发；程序只把该自己跑的那句
`git submodule update --init -- <路径>` 说给你听。

换仓库时表单不会被悄悄清空或串用：离开某个仓库时那份未提交的草稿（标题、描述、作者、
合作者、两个时间）由导航**代管**，回到同一个仓库时原样交回；如果交回时界面上又写了新东西，
会先问一句怎么处理，两份内容都不会被覆盖。作者栏按“你自己写的字”对待，回来时不会被那个仓库
的默认身份盖掉。

回到父仓库后自动再问三份位置并给提示：父索引里那条 gitlink、父提交里记的那一份、
子模块现在的 HEAD。三者一致就说“这一条显示干净”（同时提醒：**干净不证明子模块那次提交
已经推到任何远端**）；指针没进索引就提示你选中它点 `加入暂存区`；问不成就说“没问全”，
不猜也不说干净。整个过程**不 add、不 commit、不 push、不联网**，也不递归处理任何子模块。

### 冲突与暂停流程：看清现场，再决定继续还是中止

仓库已经停在某个 Git 流程里（合并冲突、变基停在半路、拣选/撤销序列中途）时，底部三个
按钮负责这一件事：`查看冲突状态`、`继续该流程`、`中止该流程`。三个入口都先在后台做一次
**只读**的现场读取——Git 目录里的痕迹（`MERGE_HEAD`、`rebase-merge\`、`rebase-apply\`、
`CHERRY_PICK_HEAD`、`REVERT_HEAD`、`BISECT_LOG`、`SQUASH_MSG`、`index.lock` 等）、
`git diff --name-only -z --diff-filter=U` 问回的未合并条目、以及当前分支与 HEAD 现在的
位置——然后才决定要不要动任何东西。

`查看冲突状态` 只说不改：流程是哪一种、当前分支与目标（合并进来哪一份提交、变基要把哪条
分支落到哪、走到第几步）、未合并的文件（超过 8 个只报个数并列前 8 个）、继续的前提，
以及“继续/中止现在各能不能用、为什么”。看冲突文件的原生差异仍是**双击**“未暂存的更改”
里带「冲突」的那一行：那是 Git 的组合差异（`diff --cc`），窗口里看得见原文。

`继续该流程` 把 `merge --continue` / `rebase --continue` / `cherry-pick --continue` /
`revert --continue` 中对应的那一条交进命令窗口（子命令按读回的痕迹选，程序不猜）。
要点是**这一步由 Git 建立提交**：程序不传 `--no-verify`、不传 `--no-edit`、也不传 `-m`，
所以钩子（按 Git 文档这一步跑的是 `pre-commit` 与 `commit-msg`；`prepare-commit-msg`
本来也不受 `--no-verify` 影响）、提交签名（`commit.gpgsign`）以及**是否打开编辑器**
都由 Git 与你的配置决定。取消编辑器或钩子非 0 退出都会让这一步停下来，流程痕迹与你
写好的内容原样留着。索引里还有未合并条目时，这条命令不会生成，程序也不谎称“可以继续”——
先把冲突解决（内容你自己写）并 `加入暂存区`。

`中止该流程` 交出去的是对应的 `--abort`。它会**改动你的工作区与索引**，因此走风险确认框，
逐条写明按 Git 文档会发生什么：`merge --abort` 是“终止冲突解决过程、试图重建合并开始前的
状态”（`MERGE_HEAD` 存在时等同于 `git reset --merge`，有 `MERGE_AUTOSTASH` 时改为把那份
自动 stash 应用回工作区；文档明确写着合并开始前就存在的未提交改动某些情况下无法重建）；
`rebase --abort` 把 HEAD 复位回原来的分支，已重放出来的提交不再被那条引用指向；
`cherry-pick`/`revert` 的 `--abort` 取消整条序列并回到序列开始前的状态。你在冲突文件里
已经写好的解决内容会随之丢弃。只想撤掉痕迹而保住工作区里已写好的东西，Git 那边另有
`--quit`——那不是这个按钮做的事，程序不代为执行。

三条硬性边界：

- 程序**没有内置合并器**：从不选 `ours/theirs`、不跑 `merge-file`、不动 rerere，也不替你
  暂存或退回任何文件；它只负责让你看清现场，并把那一条你点头的 Git 命令放进可见窗口。
- 认不出或不一致的现场只报告、不猜：多种流程痕迹并排、只有 `rebase-apply\` 却读不回
  `head-name`/`onto`（分不清是变基的 apply 后端还是 `git am`）、只有 `SQUASH_MSG` 却没有
  `MERGE_HEAD`、停在 `BISECT_LOG`——这些都不生成任何命令；Git 目录问不成的那轮说的是
  “问不到”，绝不是说成“没有流程停着”。
- 无论命令失败、结果未知，还是执行前复核发现现场变了（例如外部终端已经把工作走完），
  程序都不做自动恢复：不 `reset --hard`、不 `clean`、不 `stash`、不删 `index.lock`、
  不自动重试，你写在提交表单里的字一个字不动；现场会被重新读回来如实说明，接下来怎么做
  由你决定。

### 命令完成 ≠ 窗口关闭；失败 ≠ 结果未知

- 每个操作以 **Git 的退出码**结案（通过操作目录里的结果文件独立取回），**不等保留的
  命令窗口关闭**：窗口开着供你翻看输出时，界面已经可以发起下一项操作。“窗口打开了”
  从来不算成功。
- 终态是分开的几种：启动失败 / 执行完成（含退出码）/ Git 未能启动 / **结果未知**
  （窗口被提前关闭、辅助进程未能开始、超过观察期限）。“结果未知”绝不写成成功，也
  绝不自动重试；正在运行的 Git 不会被程序终止。
- **失败的操作同样可能已经改动了仓库**（提交到一半、`push` 被拒、合并留下冲突），
  所以无论成败都会自动重读一次，状态栏同时给出“刚才的操作怎么样”与“仓库现在怎么样”。
  外部终端里改的仓库，点 `刷新` 即可回到 Git 的真实状态。

## 使用记录与提交草稿的保存

这是可选功能。第一次启动时程序会用一个对话框把“保存哪些内容、保存在哪”一次说清，
你再决定；没做过选择之前，程序一个字节都不会写。

**保存什么**：

- 最近识别成功的仓库目录（按 Git 答出的工作区根，最多 10 条）；
- 这次启动验证过（`git --version` 成功）的 Git 程序路径；
- 窗口的位置、大小、是否最大化，以及两条分隔条的列宽比例；
- 每个仓库一份**未提交的提交表单草稿**：标题、描述、作者、合作者，以及你挑过的
  作者/提交者时间（时间连同「这是不是你亲手挑的时刻」一起记录——没人挑过就不会
  把上次那个旧时刻当成这次的时间意图）。

**不保存什么**：口令、令牌、带凭据的 URL、进程环境变量、你的 Git 配置——一概不写。
草稿是你自己写的文字，可能存在私人内容，保存与删除的入口都在界面上。

**存在哪**：当前用户的漫游应用数据目录，`%APPDATA%\EvernightCommit\state.prefs`。
不写进项目目录、不写进 Git 配置、也不碰开发记录。开关悬浮提示和对话框里都会显示
完整路径；想彻底删掉，点 `清除已存记录` 或直接删除那个文件即可。

**怎么反悔**：

- 取消 `保存记录`：程序既不读也不再写（已有内容保留，要删请用 `清除已存记录`）；
- 取消 `保存草稿`：已保存的草稿立刻从记录文件里删除（屏幕上的字不动），其余照常；
- `清除已存记录`：删掉全部用户内容（最近仓库、Git 路径、布局、草稿），对这台机器上
  所有 EvernightCommit 窗口生效；两个开关的选择会保留。

**恢复时的规矩**（上次有效不等于本次授权）：

- 上次记下的仓库路径与 Git 路径都只作为输入框初值，本次照样要走完整的后台验证
  （`git --version`、仓库识别）；路径失效会明说，不会拿坏路径去执行任何命令。
- 草稿按工作区身份分开恢复：同一项目的不同 worktree 各自一份，互不覆盖；
  只有屏幕上没有你正在输入的内容时才会恢复，两边都有内容时程序只提醒、不替你挑。
- 恢复的草稿里，作者一栏按“你写的字”对待：仓库配置变化后，默认身份不会悄悄盖掉它；
  想改回默认身份，清空作者栏即可。时间方面：你挑过时间就恢复你挑的那个时刻；
  没挑过就回到此刻，而不是上次保存时的那个旧时刻。
- 提交成功后，草稿里只清掉“这次真的提交掉的那部分”；命令窗口跑的那段时间里
  你新写的字会留在新草稿里。提交失败、取消或结果未知时，草稿一个字不动。

**异常退出的后果**：编辑中的草稿最多丢最近 1.5 秒的改动（防抖写入）；异常退出本身
不丢更早保存的内容。多个窗口同开时：写入前会重读盘上最新记录并合并，**别的窗口
保存得更晚的草稿会被保留并明确报告**，最后一个写入者不能悄悄盖掉另一个窗口的新草稿。
记录文件损坏时原件会被改名保留在旁边再重新开始；文件是更高版本写的，本版本不会
读它也不会覆盖它。

## 操作历史与恢复入口

这是与「保存记录」各自独立的可选功能。默认关闭；勾上右下角的 `记录操作历史` 才开始记录，
没勾之前一个字节都不写。

**记什么**（只记「做过什么」的元数据，不记「内容本身」）：

- 每次写操作一条：唯一 ID、时间、仓库工作区、操作类型（创建提交 / 撤回 / 抓取 / 拉取 /
  推送 / 首次推送 / 冲突继续 / 冲突中止 / 按记录恢复）；
- 你在确认框上点头的**那一份**：本地分支与远端引用、完整对象 ID、发布远端名与逐条发布地址；
- 命令窗口**启动当场**就先落一条「已启动，未见结果」并立刻写盘，之后用同一个 ID 补上终态。
  所以进程被强杀、你允许命令继续跑而关掉界面、或完成通知没送到，历史里也还有这一条可查，
  不会把「做过操作」读成「什么都没发生」；没等到终态的记录各有各的说法——程序整个没了就停在
  「已启动，未见结果」，拿到了观察端「问不出结果」的结论就写成「结果未知」，两种都不猜它成功、
  失败或已撤销；
- 启动与终态：成功 / 失败 / 已取消 / 启动失败 / Git 未创建 / **结果未知**——各归各的，
  绝不把「没问到」写成「没有」，也不把「结果未知」当成成功或失败；
- 推送的逐目标核实结果，以及供你判断恢复方式的引用级线索。

**不记什么**：完整文件内容、提交正文（标题/描述/合作者正文都不进这里）、口令、令牌、
带凭据的 URL（发布地址落盘前先掩码 userinfo，查询串与 `#` 之后的片段整段去掉——
对象存储型远端常把签名令牌放在查询串里）、进程环境变量、Git 的原始输出。导出走同一份
脱敏文本，所以导出也不含上面这些。

**存在哪**：`%APPDATA%\EvernightCommit\history.prefs`（与 `state.prefs` 分开的两份文件、
各一份写锁），不进项目目录、不进 Git 配置，也不与开发用的进度记录混在一起。`操作历史…`
入口和开关提示都会给出完整路径。

**能做什么**（都在 `操作历史…` 里）：查看这些记录、导出脱敏副本、查看存储位置、清除全部
历史、调整保留天数与条数上限（默认保留 90 天、最多 1000 条，按先满足者淘汰最旧的）。
多个窗口同开时，写入前会重读并**按记录 ID 合并**：一条操作只保留它真正拿到的那个终态，
不会被另一个窗口较弱的信息悄悄改写；崩溃或读到损坏文件时，原件会被改名保留在旁边再
重新开始，半条记录绝不会被当成一次已完成的操作。

**恢复入口**：选中一条记录之后——

- 只有「引用级可回退」的记录（撤回最近提交、以及按记录做的恢复）才提供恢复：程序先在后台
  重新预检这一组事实——这条分支现在到底指着什么、这个引用名**本身**是不是符号引用、这条
  分支有没有被别的 `git worktree` 检出、要挪回去的对象在本地读不读得到、有没有
  merge/rebase 停着——判明可行才弹确认。你点头之后仍要把同一组事实再核一次（分支没被挪走、
  没有新出现的流程、引用形态与占用仍然放行），才在命令窗口里发一条
  **带预期旧值且 `--no-deref` 的 `git update-ref`**：只按你确认的那一个本地分支引用名移动它，
  不追随符号引用去改别的分支，也不碰索引与工作区。
  绝不会因为记录里当年写着「可恢复」就照旧命令直接执行；分支已被移动或删除、要挪回去的对象
  在本地读不到（读不到不等于「一定已被回收」，也可能只是这份历史不完整）、目标是一条符号
  引用、这条分支正被另一个工作树用着、或现场根本读不回来，都会被如实判明为不可自动恢复，
  只把现状说清楚。标签、远端跟踪引用这类不在「本地分支」范围内的名字，即使出现在历史文件里
  也会被拒绝，不会被当成可自动恢复的目标。
- 涉及已推送到远端的记录只解释协作影响，并把**说明与目标信息**交给你**复制**后自行判断；
  本程序**绝不自动 force push、hard reset、clean 或批量撤销**，也不会把「本地回退了」说成
  「远端也回退了」。可复制的恢复命令按目标 shell 的真实规则编排：分支名或路径里有该 shell
  无法可靠表达的字符（例如 cmd 中的 `%`）时，程序**不提供**那一行粘贴文本，改为复制逐段列出
  的字段清单，并说明为什么——不会静默替换任何字符，也不会假定你用的是别的 shell。走界面
  执行的那条链路始终以参数数组提交，不受此影响。抓取、拉取整合、冲突继续/中止这类会重写
  多提交或工作区的操作，不产生「挪回一个引用」就能还原的形态，程序只说明现状、不自动撤销。

**反悔**：取消 `记录操作历史` 之后不再新增记录，盘上已有的保留不动；要清空就在
`操作历史…` 里选「清除全部历史」（这一步会先要求确认，且不会撤销任何已经做过的操作）。

## 出错了怎么办

| 现象 | 含义 | 你可以做什么 |
| --- | --- | --- |
| “Git 程序”报找不到 / 验证失败 | PATH 里没有可用的 `git.exe`，或指定的文件不是 Git | 安装 Git for Windows；或在下拉框键入/浏览选择正确的 `git.exe`，改正后自动重新验证，无需重启 |
| 识别报 `safe.directory` 拦截 | Git 的目录所有权安全检查拒绝该仓库 | 按 Git 自己的提示，由你在终端里把它加入你自己的 `safe.directory`（程序绝不代改配置） |
| 提示 `index.lock` 已存在 | 另一个 Git 进程（编辑器、命令行）正持有索引锁 | 等那个操作结束或让它自然消失，然后点 `刷新`；程序绝不删锁 |
| 因 merge / rebase / cherry-pick 未走完而拒绝提交/整合 | 仓库处于特殊流程中，那种状态下的提交/整合与平常不是一件事 | 要看清或收尾那个流程就用底部的 `查看冲突状态` / `继续该流程` / `中止该流程`（每一步都要你确认，中止还会改动工作区）；不愿意用按钮就在终端里自己跑 `git merge --continue/--abort` 等，程序绝不代为决定 |
| `继续该流程` 说“还有 N 个未合并的文件” | Git 在这种状态下自己也会拒绝 `--continue`，程序不谎称可以继续 | 双击那些带「冲突」的行看原生差异，自己写好解决内容，选中后点 `加入暂存区`，全部解决完再点 `继续该流程` |
| `中止该流程` 被拒绝且说“没有流程停在进行中” | 那个流程已经在别处（外部终端、别的程序）走完或中止了；没有流程时程序不生成任何 `--abort` | 点 `刷新` 看现状即可，不需要也不会有任何东西被改动 |
| 三个入口说“问不到”/“互不相容”/“分不清是变基还是 git am” | 现场读不全或形态认不出（含停在 `BISECT_LOG`、只有 `SQUASH_MSG` 的情况） | 程序不猜恢复方式：按它列出的痕迹自己在终端里核对；要动的是 `git am`/`git bisect` 那一类，命令由你自己下 |
| `pull` 报“没有明确上游” | 该分支没配置 `branch.<名>.remote` / `.merge` | 在终端里自己设好上游（如 `git branch --set-upstream-to=origin/<分支>`），或先用 `推送` 的首次推送把分支推上去并让它写入上游；`pull` 自己不猜也不代设 |
| `推送` 报“没有设置上游”且没走出首次推送 | 这个仓库里一个配好地址的远端也没有，或当前分支/提交不满足向导前提 | 先由你自己 `git remote add`（或 `git push -u`）建好目标与上游，程序绝不替你加远端、不猜 `origin/main` |
| 推送被拒（non-fast-forward） | 远端有你本地没有的提交 | 先 `fetch`/`pull` 整合远端更新再推；程序不会为“让它成功”而强推。确需强推时自己在命令行做并自负后果 |
| 推送结论“已推送但未核实 / 与预期不符” | 命令终态已收到，但对端实际位置没问到或对不上 | 按确认框列出的发布地址自己核实（访问远端仓库或 `git ls-remote`），不要当作成功；程序不自动重试 |
| `进入子模块` 被拒绝 | 那条路径不是当前父仓库登记的子模块：目录不见了、是文件、还没初始化（里面没有 `.git`）、或它是另一份克隆/独立仓库 | 按状态栏点名的那一条处理；要初始化由你自己在终端跑 `git submodule update --init -- <路径>`（会联网并改动工作区，程序不代做），然后点 `刷新` |
| 回到父仓库后提示“指针未暂存” | 子模块已经走到别的提交，父索引里那条 gitlink 还是旧的 | 在“未暂存的更改”里选中那条子模块记录，点 `加入暂存区`，再在父仓库创建提交；程序不会替你在导航里 add/commit/push |
| “Git 输出读取不完整” | 仓库过大、输出超出保留上限、或遇到非法编码字节 | 重新点 `刷新`；持续出现时在终端里核对 `git status`。程序宁可拒读也不给你半份列表 |
| fetch 被点名配置拒绝 | 仓库把该远端的 fetch 映射写到允许命名空间之外（会动本地分支/标签） | 核对 `remote.<名>.fetch` 配置；不想改配置的仓库请改用命令行 fetch |
| 命令窗口打不开 / 中文显示乱码 | 未验证过的系统代码页形态或环境差异 | 反馈时附上状态栏原文与操作目录里 `spec.txt` 的内容（目录路径在状态栏提示里），以便定位环节 |
| 不确定一次操作是否生效 | —— | 点 `刷新`；两个列表、分支行与“最近提交”都会按 Git 的当前回答重摆 |

## 已知限制

- **无发布渠道**：没有安装器、自动更新与发布地址；只能从源码构建。
- **持久化只覆盖少数几项**：保存的是最近仓库、验证过的 Git 程序路径、窗口布局与
  按仓库分开的提交草稿；列表选中项、滚动位置、提交历史范围等仍每次从头来。
  详见“使用记录与提交草稿的保存”一节。
- **提交历史只读且限量**：从当前 HEAD 可达的最近 100 条；没有搜索、没有图形分支树、
  没有 checkout / reset / revert 入口（双击只能 `git show` 看详情）。
- **撤回只针对当前分支的最新提交**；没有 stash 功能；没有冲突解决编辑器（冲突会如实
  列出，解决内容由你自己写）。
- **冲突与暂停流程只做「看清 + 把那一条命令交出去」**：没有内置合并器，不选 `ours/theirs`，
  不接手 `git am`（分不清与变基共用的那层目录时直接拒绝）、`git bisect`、`--squash` 那种
  没有 `MERGE_HEAD` 的停法，也不提供 `--skip`/`--quit`；`--continue` 是否打开编辑器、跑哪些
  钩子、要不要签名都由 Git 与你的配置决定，程序不替你压掉任何一项。
- **推送边界**：不强制推送、不推标签、一次只推一条引用。会写配置文件的只有
  「首次推送」这一种入口，而且必须你当场选定目标远端与目标分支、并明确同意设置上游；
  推送没成功时一条配置都不写。分支管理（改名、删除、重命名远端、给已有上游的分支
  改上游）都不在本程序职责里，`pull` 也仍然拒绝没有上游的分支。
- **fetch 范围**：只服务“跟踪引用落在 `refs/remotes/<远端>/` 之下”的常规仓库形态；
  映射特殊（单分支过滤可以，跨命名空间会被拒绝）的仓库请改用命令行。
- **以下环境形态未在实机上验证**（判定链路已不依赖它们，但缺真机核验，如实声明）：
  传统代码页（GBK 936 / 西文 1252、437）的机器、未安装 VC 运行库的干净机器、更旧
  版本的 Git（程序对版本差异有声明的退回路径，但只在较近的 Git for Windows 版本上
  实测过）、组策略禁用 `cmd.exe` 的机器、真实超大仓库（16 MiB 输出上限端到端）。
